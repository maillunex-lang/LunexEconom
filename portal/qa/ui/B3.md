# B3. Отчёт исполнителя, приёмка и обзор проектов

## Реализовано
- Панель сданной задачи: текст отчёта и отправка через `GET/POST /api/projects/{slug}/tasks/{id}/report`; отображение количества доработок, пяти пунктов приёмки, PR из ответа при наличии.
- Основная кнопка «Принято, в архив» заблокирована до отметки всех пяти пунктов и при красном CI. Отдельная «Принять вручную» требует повторного подтверждения и отправляет `manual: true`, `reason` на сервер. Оба действия работают через `POST .../review`, без обхода проверки старым маршрутом `/status`.
- Возврат исполнителю требует непустых замечаний, отправляет `action: return` и `notes` на сервер; можно скопировать исходный промпт с замечаниями. Счётчик доработок берётся только с сервера.
- Обзор проектов: «Требует вашего внимания», «Скорость и здоровье», метрики и столбики недель по `GET /api/metrics`. В случае отсутствия данных или API показывается честное состояние «нет данных» или ошибка, без выдуманных чисел.
- Светлая и тёмная темы, 390×844 и 1440×900, русские тексты, безопасный вывод через `textContent`, кнопки с подсказками. Новых зависимостей нет.

## Допущения
1. В свежем `main` нет `docs/gdd/07_*.md`, поэтому прочитаны все имеющиеся `06_*.md`, `DECISIONS_APPROVED.md`, `docs/AI_RULES.md`, профильные `docs/portal/06_REPORTS_REVIEW.md`, `08_DATA_API.md`, `mockups/overview.svg` и `task_review.svg`. Документы не изменялись.
2. Спецификация 08 перечисляет пути API v2, но не задаёт JSON-формат их тела. Для мока приняты: отчёт `{report:{text},checks:[{item,done}],revisions}`, запись `{text}`, приёмка `{action:'accept',checks:[{item,done}],manual,reason}` либо `{action:'return',notes}`; обзор `{attention:[{project_name,project_slug,task_id,reason}],metrics:{accepted_week,avg_issue_to_submit,avg_issue_to_accept,return_rate,waiting_owner,red_ci,weekly}}`. Эти формы требуется согласовать с серверной линией A до реального включения.
3. При недоступности GET отчёта кнопки сохранения, приёмки и возврата заблокированы. При отсутствии API метрик показана ошибка, не фиктивная статистика. Новые функции фактически выключены до появления API; никакой клиентский feature flag не включает их сам.
4. Для ручного принятия выбран безопасный вариант: два нажатия с пояснением и запись причины в запрос. Красный CI блокирует и обычную, и ручную приёмку; сервер должен независимо проверять все ограничения и писать аудит. При успешном POST `review` клиент только перечитывает состояние проекта, не устанавливает статус сам.
5. Чек-лист сохраняется на сервере одним запросом приёмки; без контракта отдельного сохранения отметок локальные отметки не считаются постоянными. Показанный счётчик доработок приходит с сервера, не увеличивается оптимистично.
6. Никакие файлы сервера, эталонные данные, B1/B2 или `docs/**` не изменялись; все изменения в разрешённой зоне B3.
