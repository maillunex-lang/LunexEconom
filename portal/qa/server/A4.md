# A4. Уведомления MAX и Telegram

## Реализация

- За флагом `notifications_enabled=False` добавлена миграция SQLite v5 и модуль `portal/notify/`. Каждый канал имеет независимую привязку, переключатель и предпочтения по событиям.
- Адаптер MAX: `POST https://platform-api2.max.ru/messages?chat_id=...`, заголовок `Authorization: <token>`, JSON `{"text":...}`. Telegram: `sendMessage`. Только стандартная библиотека, таймаут 10 секунд, инъекция HTTP-клиента для тестов.
- Секреты читаются только из внешних файлов с правами 0600, пути через `PORTAL_MAX_TOKEN_FILE` и `PORTAL_TELEGRAM_TOKEN_FILE`; в SQLite и ответы API токены не записываются.
- `POST /api/notifications/code` выдаёт 8-значный одноразовый код, в БД сохраняется только SHA-256 кода и срок 600 секунд. `POST /api/notifications/poll` по авторизованному запросу читает входящие сообщения бота и привязывает чат только при точном совпадении неистёкшего кода. Повторное использование и повторные update_id отвергаются.
- `GET/POST /api/notifications/settings`, `POST /api/notifications/unlink`, `POST /api/notifications/test`, `POST /api/notifications/process`, `GET /api/notifications/log`. Все маршруты требуют сессию, POST требует CSRF.
- Очередь отправки сохраняется в SQLite, антишум 3600 секунд по каналу, событию и ключу; при неудаче повтор через 300 секунд, не более трёх повторов после первой попытки; журнал хранит только тип, канал, статус и номер попытки.
- Обработка событий PR, ошибок CI и плана из журнала GitHub, входа с нового устройства; просроченная приёмка обнаруживается при вызове `/process`. Содержимое отчётов и токены не отправляются.
- Для развёртывания включить `PORTAL_NOTIFICATIONS_ENABLED=1`, создать два файла токенов с правами 0600 вне репозитория и настроить регулярный защищённый вызов `POST /api/notifications/process` с действующей сессией и CSRF. По умолчанию отправки выключены.

## Проверки

- `python3 -m unittest portal.tests.test_notifications_a4 -q`: 50 новых тестов, без сетевых запросов.
- Полный набор `python3 -m unittest discover -s portal/tests -q`: см. итоговый отчёт сдачи.
- Реальный API не вызывался, токены не запрашивались, production не изменялся.

## Допущения

- `docs/gdd/08_*.md` отсутствует в main; изучены доступные документы, `docs/portal/05_INTEGRATIONS.md`, `docs/AI_RULES.md` и решения.
- Вариант привязки для первого этапа: **long polling по запросу авторизованного владельца**. Документация MAX рекомендует production webhook; отдельный HTTPS webhook с проверкой подлинности и настройкой подписки потребуется перед постоянной эксплуатацией. MAX и Telegram нельзя считать автоматически подключёнными до получения реального кода от бота.
- Состояние «ошибка резервной копии» предусмотрено в перечислении событий, но автоматический мониторинг backup не подключён, поскольку это потребовало бы изменения вне разрешённой зоны и отдельного расписания.
- Для повторов принято четыре попытки суммарно: первая + три повторные. При повторном событии в пределах часа новая запись в очереди не создаётся.
- Необязательный SMTP не реализован.
- Для безопасности произвольные тексты из GitHub не попадают в уведомления, только имена проекта/идентификаторы задачи и фиксированные сообщения.
