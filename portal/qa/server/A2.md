# A2. GitHub webhook, PR/CI, автоприёмка

## Реализация

- `POST /hook/github` публичный, без сессии, **только** при `PORTAL_WEBHOOK_ENABLED=1`; проверка `X-Hub-Signature-256` через HMAC-SHA256 и постоянное сравнение, секрет читается из `PORTAL_WEBHOOK_SECRET_FILE`, хранится вне репозитория. Лимит тела 1 МБ, неизвестные события и некорректный JSON отклоняются. `X-GitHub-Delivery` дедуплицируется в транзакции.
- `push` в основную ветку проекта обновляет план из GitHub с проверкой валидатором. При неудаче старый план не трогается, в events пишется `plan.sync_failed`.
- `pull_request` привязывается к ID задачи из ветки либо заголовка; запоминаются номер, ветка, базовая ветка, SHA, состояние. Слияние в основную ветку выставляет `merged` и `sha` задачи без немедленной смены статуса.
- `check_suite` и `workflow_run` сохраняются по SHA и имени проверки. Статус CI `success` только при наличии хотя бы одной завершённой успешной проверки и отсутствии неуспешных или незавершённых. Необязательный `required_checks` в настройках требует явного присутствия названий. Автоприёмка срабатывает только при `merged` PR в ветку проекта и зелёном CI на merge SHA. Закрытая вручную задача не меняет статус, повторная доставка не создаёт повторного автозакрытия.
- `GET /api/projects/{slug}` включает `state[id].pr` и `state[id].ci`; `GET /api/projects/{slug}/events` выдаёт 200 последних событий; `GET/POST /api/projects/{slug}/settings` управляет `auto_accept`, `auto_accept_require_checklist`, `required_checks` под сессией и CSRF для POST.
- Миграция 3 создаёт `events`, `pr_links`, `webhook_deliveries`, `project_settings`, `ci_checks`, добавляет `projects.branch` с `main` по умолчанию. Схема создаётся только при включённом флаге вебхуков, чтобы не ломать совместимость A1.

## Допущения

1. `PORTAL_WEBHOOK_ENABLED` по умолчанию выключен. Не настраивались GitHub webhook в репозитории и реальный сервер. Для развёртывания нужен секрет в отдельном файле 0600 и разрешение владельца на часть C.
2. `project.branch` добавлен в схему с дефолтом `main`; отдельного маршрута изменения ветки не предусмотрено. Применяется только к уже существующим проектам с `repo` равным GitHub `repository.full_name`.
3. Проверки CI идентифицируются именем workflow (`workflow_run.name`) или приложением (`check_suite.app.slug`), поскольку событие check_suite не перечисляет отдельные названия проверок. Отсутствующие обязательные проверки запрещают автоприёмку.
4. GitHub доставляет события асинхронно, а API вебхука не знает, сколько ещё проверок запланировано на SHA. При пустом `required_checks` учитываются все **уже наблюдавшиеся** проверки, минимум одна; возможна поздняя доставка красного CI после первой зелёной. Для строгого «все проверки» следует заполнить `required_checks` и при необходимости добавить запрос GitHub API на полный список checks отдельной задачей.
5. `auto_accept_require_checklist=true` консервативно блокирует автоприёмку: таблица чек-листов и API проверки находятся вне зоны A2. Для автоприёмки оставить `false`.
6. Вебхук не отправляет сообщения в мессенджеры, поскольку уведомления реализуются отдельным заданием; вместо этого события и аудит доступны интерфейсу.
7. События `push` выполняют сетевое чтение плана при получении вебхука. При ошибке синхронизации ответ остаётся 200 и событие `plan.sync_failed`, что предотвращает бесконечные повторные доставки GitHub.
8. `SHA` проверяется как 40-символьный lowercase hex; недостоверный SHA не вызывает автоприёмку. Для PR из форков привязка не производится, чтобы исключить подмену задачи по внешней ветке.

## Проверки

`python3 -m unittest discover -s portal/tests` и `git diff --check`. Прогон на установленном Python 3.14; Python 3.12 на сервере отсутствует, нужна дополнительная проверка CI. Только изолированные временные SQLite. Реальный VPS, nginx и GitHub webhooks не менялись.
