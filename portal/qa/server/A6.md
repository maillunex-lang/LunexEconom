# A6. Мастер старта проекта: сервер и интерфейс

## Выполнено
- Ветка `portal/a6-launch-wizard`, сервер и UI в одном пакете, отдельный рабочий клон свежего `origin/main`.
- SQLite миграция v7: отдельное `wish` до 4000 символов. GitHub URL нормализуется в `owner/repo`, вредные адреса и неправильные типы отклоняются. Нет хранения токенов или сетевых запросов при создании.
- `GET /api/projects/{slug}/launch` возвращает единый промпт из `portal/launch/PROJECT_LAUNCH_PROMPT.md`, 4 шага и признаки наличия плана/задач. `POST /api/projects/{slug}/launch-step` фиксирует ручное подтверждение шагов 1–3, под CSRF и сессией. Шаг 4 определяется загрузкой плана. Старые bootstrap-маршруты сохранены.
- UI: создание проекта с тремя полями, автозаполнение названия, живой контроль GitHub URL; карточки запуска, копирование, «Поделиться», «Показать текст», синхронизация и переход к задачам. На «Сегодня» и в списке проектов без плана доступно «Продолжить запуск проекта».
- `GET /api/portal-dev-guide` возвращает неизменённый файл `portal/templates/PORTAL_DEV_GUIDE.md`. Копия файла включена в скелет, во вкладке «Ещё» есть «Развитие портала» с тремя действиями.
- На телефоне название текущего экрана теперь видно в верхней панели.
- Новый API за флагом `PORTAL_LAUNCH_ENABLED=1`, по умолчанию выключен. Деплой и работающие службы VPS не затрагивались.

## Проверки
- `python3 -m unittest discover -s portal/tests -q`: 328 тестов OK, 29 новых.
- JavaScript `node vm.Script`: синтаксис OK.
- Headless Chromium из уже существующей изолированной среды: 16 снимков в `portal/ui_tests/shots/a6-*.png`, 390×844 и 1440×900, светлая/тёмная темы, реальные тестовые WSGI/SQLite, без необработанных JS-ошибок.
- `git diff --check`, проверки зоны файлов и включения шаблона в скелет.

## Допущения
1. Проверка доступности репозитория через GitHub API необязательна. Сделана инъекция `launch_check_repo` для тестов; в стандартном рабочем режиме сетевой проверки при создании нет. Синхронизация остаётся существующей реализацией GitHub GET из файла токена на сервере.
2. Факт создания/слияния PR нельзя достоверно вывести из `plan_json`. Владелец подтверждает шаги 1–3 вручную; шаг 4 отражает загруженный план. Пустой `packages` означает, что план загружен, но задач нет.
3. Сохранены `description` и два старых bootstrap-промпта ради совместимости. Новый мастер использует один единый промпт и отдельное `wish`.
4. Название предлагается из имени репозитория, описание при новом создании пустое. Slug латинский по старому контракту. Конфликт slug даёт 409 и ничего не перезаписывает.
5. `portal/templates/**`, `docs/**`, `tools/**`, `README.md` и прочие запрещённые зоны не изменены. При недоступном сервере UI не имитирует успешное сохранение.
