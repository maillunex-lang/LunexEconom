# A6. Мастер старта проекта: сервер и интерфейс

## Выполнено
- Ветка `portal/a6-launch-wizard`, сервер и UI в одном пакете, отдельный рабочий клон свежего `origin/main`.
- SQLite миграции v7/v8: отдельное `wish` до 4000 символов. GitHub URL нормализуется в `owner/repo`, вредные адреса и неправильные типы отклоняются. Нет хранения токенов или сетевых запросов при создании.
- `GET /api/projects/{slug}/launch` возвращает единый промпт из `portal/launch/PROJECT_LAUNCH_PROMPT.md`, 4 шага и признаки наличия плана/задач. `POST /api/projects/{slug}/launch-step` фиксирует ручное подтверждение шагов 1–3, под CSRF и сессией. Шаг 4 определяется загрузкой плана. Старые bootstrap-маршруты сохранены.
- UI: создание проекта с GitHub, названием, адресом, пожеланиями и путем к плану, автозаполнение названия, живой контроль GitHub URL; карточки запуска, копирование, «Поделиться», «Показать текст», синхронизация и переход к задачам. На «Сегодня» и в списке проектов без плана доступно «Продолжить запуск проекта».
- `GET /api/portal-dev-guide` возвращает неизменённый файл `portal/templates/PORTAL_DEV_GUIDE.md`. Копия файла включена в скелет, во вкладке «Ещё» есть «Развитие портала» с тремя действиями.
- На телефоне название текущего экрана теперь видно в верхней панели; учтён отступ под нижнюю навигацию, для скелета используется иконка скачивания.
- Новый API за флагом `PORTAL_LAUNCH_ENABLED=1`, по умолчанию выключен. Деплой и работающие службы VPS не затрагивались.

## Дополнение владельца к A6
- На пустой доске доступны без панели инструментов три крупные кнопки: **«Загрузить план файлом»** (JSON с телефона, максимум 900 КБ), **«Вставить план текстом»** (развёрнутое поле с проверкой JSON) и **«Синхронизировать»**. Ошибки остаются видимыми, при неудаче план не заменяется.
- `plan_path` хранится отдельно для каждого проекта: `docs/work_plan.json` (по умолчанию) или `docs/portal/work_plan.json`. Выбор есть при создании и в настройках; изменение через `GET/POST /api/projects/{slug}/plan-settings` с проверкой сессии/CSRF и фиксированным белым списком путей. Промпт директора учитывает выбранный путь.
- Ручная синхронизация, подписанный push webhook (при единственном проекте на репозиторий) и дополнительный фоновый опрос используют `plan_path`. Опрашивается не более 10 проектов на тик и не чаще интервала 5/10/30 минут (при включенном A6 и фоновом GitHub worker); проверяются `wp.validate`, тела до 900 КБ, старый план сохраняется при ошибке. При отключённом флаге A6 опрос плана не запускается. `portal/backup/**` не изменялся, добавлен `portal/launch/plan_poll.py`.
- Адрес проекта в форме можно редактировать, автоматически приводится к нижнему регистру; поле с невалидным адресом подсвечивается. Отдельно подсвечивается неверный GitHub URL.

## Допущения
1. Проверка доступности репозитория через GitHub API необязательна. Сделана инъекция `launch_check_repo` для тестов; в стандартном рабочем режиме сетевой проверки при создании нет. Синхронизация остаётся существующей реализацией GitHub GET из файла токена на сервере.
2. Факт создания/слияния PR нельзя достоверно вывести из `plan_json`. Владелец подтверждает шаги 1–3 вручную; шаг 4 отражает загруженный план. Пустой `packages` означает, что план загружен, но задач нет.
3. Сохранены `description` и два старых bootstrap-промпта ради совместимости. Новый мастер использует один единый промпт и отдельное `wish`.
4. Название предлагается из имени репозитория, описание при новом создании пустое. Slug латинский по старому контракту. Конфликт slug даёт 409 и ничего не перезаписывает.
5. `portal/templates/**`, `docs/**`, `tools/**`, `README.md` и прочие запрещённые зоны не изменены. При недоступном сервере UI не имитирует успешное сохранение.

6. Автоматическая загрузка плана из push вебхука при нескольких проектах, привязанных к одному GitHub-репозиторию, использует первый совпавший `plan_path`; для различающихся путей рекомендуется отдельная синхронизация/фоновый опрос конкретного проекта.
