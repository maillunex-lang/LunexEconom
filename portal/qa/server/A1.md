# A1. Безопасность и аудит сервера портала

## Реализация

- Флаг `PORTAL_SECURITY_V2=1` включает POST `/api/password`, POST `/api/sessions/revoke`, GET `/api/audit` и часовую блокировку входа. По умолчанию выключен. Старый лимит 8 неудач за 15 минут остаётся включённым.
- Смена пароля требует сессию, CSRF, текущий пароль и новый пароль длиной 14–300 символов; текущая сессия сохраняется, её CSRF меняется, остальные сессии владельца удаляются. Повтор того же запроса отвергается. Новый пароль нельзя приравнять старому.
- Отзыв сеансов требует текущего пароля, удаляет **все** сессии пользователя, включая текущую, и очищает cookie.
- Аудит: не более 200 записей (новые первыми). Запись и выдача содержат только явно разрешённые поля действий. Сохраняются успешный вход, неверный вход, блокировка и IP-лимит, смена пароля, отзыв сеансов, создание проекта, импорт плана, синхронизация, изменение статуса задачи. Неизвестные и старые поля очищаются при выдаче, чтобы не раскрыть случайно накопленные секреты.
- SQLite-схема: `schema_versions(version, applied_at)`, транзакционные последовательные миграции 1 (уже существующая схема, идемпотентный `IF NOT EXISTS`) и 2 (индексы). Неизвестные/пропущенные версии отклоняются. Старые таблицы и данные сохраняются.
- `/health` делает `SELECT 1` к БД; возвращает `503`/`{"ok":false}` при недоступности.

## Допущения

1. В документе v2 не указан формат JSON. Принят `{ "current_password": "…", "new_password": "…" }` для смены пароля, `{ "current_password": "…" }` для отзыва сеансов и `{ "entries": [ … ] }` для аудита. Успешная смена возвращает новый `csrf` для продолжения текущей сессии. Интерфейс в задании не меняется.
2. Под «сбросить остальные сеансы» понимается сохранить текущий сеанс после смены пароля; отдельная операция сброса завершает также текущий сеанс.
3. Часовой лимит считается по доверенному `REMOTE_ADDR`. `HTTP_X_REAL_IP` из WSGI не принимается без выделенного доверенного прокси-контура. За nginx все пользователи могут иметь один IP: конфигурацию доверенного IP-проброса следует отдельно согласовать при развёртывании.
4. Блокировка после 20 ошибок реализована дополнительным лимитом по IP, а не перманентной блокировкой аккаунта, иначе атакующий мог бы бессрочно заблокировать владельца. Уже существующий лимит 8/15 минут не даёт быстро набрать 20 ошибок. Событие `login.locked` служит сигналом для будущих уведомлений; отправку владельцу не включаем, поскольку отсутствует настроенный канал и его секреты.
5. Двухфакторный TOTP не входит в A1 и не реализован. Удаление проектов, события v2 и другие функции из API-контракта вне зоны текущего задания.
6. Схема обновляется при `db.connect()` независимо от feature-флага, поскольку это необходимо для воспроизводимости и безопасной миграции существующей базы. Сами новые операции API выключены до явного включения.
7. Существующий административный `set-password` оставлен без изменения: он сбрасывает все сессии по старому контракту.
8. Проверки выполнены на изолированной SQLite через Python 3.14 (установлен на VPS). Для требования Python 3.12 нужна отдельная проверка в CI с 3.12; версии 3.12 в среде нет. На боевой базе миграции не запускались.

## Приёмка

`python3 -m unittest discover -s portal/tests`: полный набор существующих и новых тестов (результат отражён в отчёте PR). Работа с боевыми сервисами и данными не выполнялась. Для включения после отдельного релизного решения выставить `PORTAL_SECURITY_V2=1` и перезапустить портал только после резервной копии БД и проверки плана обновления.
