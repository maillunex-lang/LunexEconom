# V2-SEC1. Аудит безопасности API и бухгалтерии

Дата: 2026-11-16. Отдельная ветка `v2/security-audit`, база PostgreSQL 16 в отдельном временном Docker-контейнере, доступ только `127.0.0.1`; V1/V2 production, nginx, systemd, ops, ключи, каталог, клиент и web не изменялись. Перед слиянием в `main` требуется приёмка директора.

## Принятые допущения

- «Столкновение 20 разных игроков на одной клетке» интерпретировано как попытки строительства в одном участке, который принадлежит ровно одному игроку: один успех, остальные `409 parcel_not_owned`. Это проверка разграничения владения, а не конкурентного создания участков с одинаковым владельцем.
- «Одновременные PUT supply и cells» проверены на одном **полевом** предприятии: PUT supply принимает пустую конфигурацию, PUT cells возвращает `409 not_retail_store`. Для проверки двух успешных параллельных изменений нужен магазин и валидные ячейки.
- Детерминированные 300-шаговые серии используют **синтетические** записи предприятий и переводов в тестовой БД, включая имитацию суточного receipt. Они подтверждают инварианты ledger, но не все игровые HTTP-переходы, реальные денежные начисления от продаж или исполнение всех tick handlers.
- Устойчивость на 100 виртуальных игроков проверена только на локальном HTTP/Waitress. `--simulate-ips` допустим только на изолированном тестовом экземпляре, где специально включено `LUNEX_TRUST_PROXY_REAL_IP=1`. На production этот режим не использовать.
- Отрицательный ответ `409` при создании здания по случайной позиции считается отказом игровой валидации, а не доказательством корректного строительства.

## Что проверено

- Базовая полная проверка до изменений: `114 tests`, `OK`, примерно 58,8 с на изолированной PostgreSQL 16.
- 20 одновременных заявок на одно строительство с общим `request_id`: ровно один `201`, остальные `200` идемпотентны, один `enterprise:build`-платёж, `reconcile.ok=true`.
- 20 одновременных заявок разных игроков на одну клетку: один `201`, девятнадцать `409`, одна запись занятости; ограничение трактовки указано выше.
- Покупка одного участка двумя игроками: один `201`, один `409`, одна продажа, `reconcile.ok=true`.
- Два PUT одного предприятия: supply и retail cells, без раскрытия чужих данных; ограничение по типу здания указано выше.
- 50 одновременных переводов в противоположных направлениях с независимыми PostgreSQL-соединениями: нет отрицательных балансов и повторных денежных записей, сумма двух кошельков неизменна, `reconcile.ok=true`.
- 20 одинаковых админских компенсаций: один `request_id`, одна проводка, одинаковые `transfer_id`.
- Обход маршрутов `Registry` без токена: административные маршруты отвечают `403`, закрытые пользовательские маршруты требуют Bearer access-токен. В реестре на текущем `main` 172 маршрута, из которых 43 POST, 3 PUT, 50 административных. Регистрацию, чтение каталога/мира и `POST /admin/login` проверяли как исключения из правила обязательной пользовательской авторизации.
- Чужое предприятие по известному ID и несуществующее предприятие при GET/POST/PUT возвращают одинаковый `404 not_found`. Просроченные, заблокированные и неизвестные access-токены возвращают `401` в выборочных защищённых маршрутах.
- Проверки фальшивых целых: `null`, bool, float, отрицательные, `>2**63`, вложенные объекты, управляющие символы, Unicode, SQL-текст в полях username и координатах строительства; нет публичной трассировки. Невалидный/не-JSON, тело больше 64 КиБ, отсутствие Content-Length отрабатывают на входном HTTP-мидлваре (400, 413, 411). Нет `Access-Control-Allow-Origin: *`, в WSGI-ответе нет заголовка `Server`, Content-Type JSON.
- Две детерминированные серии по **300 операций** с seed 20261116 и 20261117: сумма счетов 0, каждый transfer суммой 0, отсутствие отрицательных пользовательских кошельков, уникальность `request_id`, `reconcile.ok=true`.
- Rate-limit входа и регистрации подтверждён существующими тестами платформы и нагрузкой с одного IP; ротация и повторное использование refresh подтверждены новым тестом; блокировка учётной записи и истечение access-токенов проверены отдельно.

Локальный тестовый Waitress 16 потоков, пул PG максимум 15, PostgreSQL 16, без production. Первоначально IP-защита отклонила 92 регистрации из 100 (429). Повтор при `--simulate-ips` на isolated loopback: **592 запроса**, 100 успешных регистраций и входов, **0 сетевых ошибок**, `p50=90,09 мс`, `p95=3213,68 мс`, `p99=3379,47 мс`, 32,51 с всего, 18,21 запроса/с. HTTP-коды: `200×300`, `201×192`, `409×100`. Подробности и запуск: `docs/loadtest.md`.

## Что не сделано и что проверить до открытой беты

1. **Высокий приоритет:** полное дифференциальное фаззинг-покрытие **каждого** POST/PUT с действительной учётной записью, на всех допустимых типах полей, и автоматическая проверка отсутствия ответов 500/503 на пользовательскую ошибку. Текущий набор покрывает только часть маршрутов и форматов.
2. **Высокий приоритет:** доказать двойное конкурентное владение именно одной клеткой в редких конфликтных состояниях, успешные конкурентные изменения supply и retail cells настоящего магазина, проверить отдельную фикстуру реальной массовой стройки.
3. **Высокий приоритет:** стресс с реалистичным количеством активных магазинов, учёт SQL timeouts, deadlocks, p95/p99 в продолжительном прогоне. Здесь есть только короткая демонстрация 100 регистраций и базовых операций.
4. **Высокий приоритет:** детерминированный E2E-цикл 300 операций через реальные HTTP-эндпоинты с фактическими тиками, снабжением, продажами, сносом, компенсациями, одновременным reconcile после каждой фазы. Текущие 300-шаговые тесты являются **моделью целостности бухгалтерии**, а не такой E2E-проверкой.
5. **Средний приоритет:** проверить все реакции на устаревшие/заблокированные/чужие токены по **каждому** защищённому маршруту, цепочки множественных сессий, админский IP и журналы при ошибках. Исходные лог-файлы существующих сервисов сознательно не читались, чтобы не просматривать секреты других проектов.
6. **Средний приоритет:** заголовки реального внешнего nginx не тестировались, только локальный WSGI. Не следует считать отсутствие `Server` в WSGI-ответе доказательством настройки внешнего proxy.
