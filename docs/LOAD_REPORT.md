# Нагрузочная проверка gpt5: изолированная SQLite

Дата: 2026-11-15. Код: tools/load_probe.py; воспроизводимый seed 20261115, 200 виртуальных пользователей, 20 активных городов. Запуск только на отдельной временной SQLite, не на боевой базе и не через публичный домен.

## Нагрузка и результат

- Создание исходной карты в отдельной тестовой базе: 20 городов, 330 домов, 148 подъездных клеток за **840,30 мс**. Это не запуск боевой первой генерации, wipe не выполнялся.
- 200 попыток игроками создать здание, 160 успешных, 40 отвергнуты как `occupied` из-за пересечений координат сценария. Строительные отклонения ожидаемые и не являются ошибкой целостности.
- 200 заявок биржи принято: 100 продажи и 100 покупки, **62 сопоставления**. Разные виртуальные IP для исключения ложного ограничения 120 действий в минуту для одного адреса. Это синтетические операции, а не одновременные сетевые сессии.
- Чтение 200 чанков и 200 снимков `/economy/regions` выполнено прямым вызовом функций сервера.
- Итог: **20 активных городов**, 490 зданий, 1588 дорог, 200 заявок. Несбалансированных финансовых проводок **0**; сумма кошельков **0**.

## Узкие места и рекомендации для Grok

1. **Периодический выброс времени обзора регионов ~1,71 с.** `regions.overview` запрашивает население, цены, доставки по городам отдельными SQL-запросами, строит 20×19 направлений. Проверить `EXPLAIN QUERY PLAN`, добавить batch-запросы `region_population` и `market_prices_region`, кэшировать неизменную географию, профилировать отдельно холодный и прогретый кэш. Без профилировщика причина 1,71 с **не доказана**.
2. **Глобальная последовательная обработка команд.** `game_server.LOCK` на уровне мира и инициализация схемы при каждом `game_server.connect()` может ограничить конкурентную обработку. Для PostgreSQL изучить транзакционные блокировки по объекту/рынку и connection pooling, сохранив финансовую целостность. Изменения сервера не вносились.
3. **Схема биржи расширяется при первом обращении** в разрешённом `server/exchange.py`. Вынести ADD COLUMN в полноценную версионированную миграцию под контролем Grok, после отдельной копии и согласования. Предусмотреть индекс `(product,city,status)` и транзакционное тестирование конкурентных покупателей.
4. **Запросы региональных сводок** могут расти квадратично по числу городов при выдаче всех маршрутов. Делать выборку регионов по видимой карте и изменённому месяцу, не запрашивать всю экономику при каждом кадре.
5. Для реального подтверждения 200 одновременно подключённых Android-игроков необходим отдельный сетевой стенд с логинами, имитацией RTT, CPU/ОЗУ, пиковой нагрузкой, PostgreSQL `lunex_ci`, 10+ повторов месячного шага и лимитами нагрузки. Публичный VPS в этой проверке намеренно не подвергался 200 одновременным запросам.

## Команда воспроизведения

`/home/gamedev/projects/LunexEconom-server/.venv/bin/python tools/load_probe.py --players 200 --output /tmp/lunex_gpt5_load_report.json`.

Скрипт разрешает только 200 игроков и создаёт базу через `tempfile.TemporaryDirectory` на диске VPS. Не затрагивает живую PostgreSQL и не требует токенов. Это именно нагрузочный **зонд логики**, а не проверка пропускной способности HTTP, nginx или устройств. Никакие серверные модули вне `server/exchange.py` не изменены.
