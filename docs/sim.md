# Эталонный симулятор цепочки M1

Самодостаточная модель без сервера и без базы. Она прогоняет поле, мельницу, пекарню и магазин по правилам GDD и печатает целые числа, с которыми потом сверяют модули поставок и розницы. Это не сервер и не замена `server/enterprises`.

Код только на стандартной библиотеке. Деньги и коэффициенты целые: базисные пункты, промилле и деление вниз, как в `docs/proposals/INTEGER_MATH.md`. Случайности нет. Два прогона одного сценария дают один и тот же отчёт.

## Что считается

Порядок суток как в `docs/gdd/00_OVERVIEW.md`: выпуск, связи поставки, городской рынок, розница, затем стройка. В день, кратный 30, после суточного тика идёт месячный шаг (`month_index = day // 30`). Так устроены часы платформы. Фраза GDD «в первый день месяца» здесь читается как граница месяца после 30-х суток, а не как утро дня 1: иначе зарплата снялась бы до выпуска.

Счета: `player:<id>`, `system:treasury`, `system:market`, `system:upkeep`. Сумма проводки 0. Сумма всех счетов 0. Кошелёк игрока не уходит ниже нуля: если денег не хватает, платёж не проводится. Для стройки это пауза стадии. Для зарплаты, содержания и НДС это просрочка, и производство стоит, пока долг не погашен целиком (D-55). Частичных платежей нет.

Стройка идёт четырьмя стадиями, оплата при входе в стадию (D-10, D-53). Доли черновые, D-58 не утверждён. Срок 250/350/300/100 ‰, стоимость 300/400/200/100 ‰ — те же кортежи, что `server/enterprises/core.py`. Срок режется накопительными границами `дни * накопленная_доля // 1000`. Цена: первые три взноса `build_cost * доля // 1000`, ввод получает остаток, чтобы сумма совпала с ценой. Платёж уходит в `system:treasury`. При `build_days = 1` три первые стадии длятся 0 суток, и оплаченное здание становится рабочим в тот же день, после выпуска. Первый выпуск — на следующие сутки.

Нехватка денег на следующий взнос не создаёт долг и не двигает прогресс: здание остаётся на уже оплаченной стадии (`enterprise_build_waits` на сервере). Заказ без денег на фундамент сервер отклоняет. Симулятор такой заказ не теряет: он пробует его снова каждый следующий день. Это поведение игрока в сценарии, не очередь сервера. В одни сутки сначала оплачиваются все фундаменты в порядке сценария, и только потом здания проходят дальнейшие стадии — так же, как `POST /enterprises` до суточного тика. Раньше симулятор достраивал одно здание до конца, прежде чем заложить следующее. На капитале, которого хватает на всю цепочку в один день, итог тот же. На тесном капитале нет: см. `docs/proposals/BALANCE_M1.md`.

Загрузка считается как в `docs/enterprises.md` и `server/enterprises/core.py`: персонал, сырьё, свободный склад, остаток дробной единицы переносится. Качество выпуска 50 без входов или целочисленно взвешено по входам. Зарплата: `jobs * ставка * укомплектованность // 10000`, затем индекс зарплаты города. Ставка читается из флага `enterprise_salary_worker_draft`, а не из константы в коде симулятора. Для Уфы индекс 10000 bp, поэтому произведение совпадает с текущим сервером.

Связь: до трёх поставщиков, приоритет, доля, порог качества и потолок цены. Внутри одного игрока товар идёт по трансфертной цене 0 и не создаёт выручку. Чужой игрок получает цену связи или эталон каталога. Нехватку закрывает городской рынок. Цена клиринга лежит в коридоре 25–250 % эталона. Если игроки ничего не предложили, цена — верх коридора. Объём город всё равно добирает.

Розница: ячейка, рейтинг `R` из весов каталога, бренд M1 равен 50, ценовая привлекательность `100 * эталон // цена` (множитель `k` из GDD не утверждён, принят 1). Спрос района делится между ячейками пропорционально привлекательности. В M1 острота конкуренции `s = 1`. Продано не больше запаса. Покупатели платят со `system:market` (D-04). НДС 1000 bp сидит в цене полки (D-18): база `выручка * 10000 // 11000`, налог — остаток, платёж в казну в месячном шаге. Оптовый рынок НДС не платит.

Каталог читается из `server/data/*.json` при каждом запуске. Числа рецептов, цен и зданий в код не скопированы.

## Упрощения

- Один район на весь город (`pop_permille = 1000`) и один слой дохода (`layer_share_permille = 1000`, `income_index = 1000`). Четыре корзины и карта районов не считаются. При выпуске пекарни 100 хлеба в сутки это не меняет продажи: спрос города намного больше полки.
- Нет рынка труда, порчи, покупки земли, налога на имущество, порта, фрахта между городами и договоров. Износ записывается, но загрузку не режет.
- Персонал равен флагу `enterprise_staffing_bp_draft` (сейчас 10000), если сценарий не задал `staffing_bp` в диапазоне 0..10000. Рекламный множитель 1000. Привлекательность магазина 1000 ‰. Надбавка трафика `traffic * 10` ‰; в сценариях трафик 0. Сценарий может подменить ставку ключом `salary_worker` и цены стройки ключом `build_cost_overrides`: это только прогон баланса, каталог на диске не меняется.
- Цель пополнения производственного входа — одни сутки рецепта. Для полки без `min_stock` — суточный выпуск поставщика.
- Заказы стройки в одни сутки: сначала фундамент каждого заказа по списку сценария, затем дальнейшие стадии в том же порядке. Золотые сценарии этого различия не видят: капитала хватает закрыть все стадии в тот же день.

## Как запускать

Из корня репозитория:

```
python -m tools.sim run tools/sim/scenarios/m1_basic.json --days 30
python -m tools.sim golden
python -m tools.sim balance
python -m unittest discover -s tools/tests -p 'test_sim_*.py' -v
```

`golden` перезаписывает `tools/sim/golden/*.json` числами текущего каталога. После правки `server/data` эталон нужно пересобрать и просмотреть diff: тесты сравнивают прогон с файлом байт в байт по значениям JSON. V2-G-SIM2 золотые файлы не менял: три сценария на текущих ценах дают прежний отчёт, расхождение порядка оплаты видно только на капитале ниже суммы стройки.

`balance` печатает сетку окупаемости M1. Числа и определения — в `docs/proposals/BALANCE_M1.md`. Команда не пишет файлы.

CI: `.github/workflows/sim-check.yml`, Python 3.12, те же тесты, на push и pull_request по `tools/sim/**`, `tools/tests/test_sim_*.py`, `server/data/**`.

## Как читать таблицу

Колонки: сутки, игрок, деньги на конец суток, выпуск за сутки, проданные штуки, выручка розницы, НДС этих продаж (начислен, не обязательно уплачен). Уплата НДС и зарплаты видна в строке ИТОГ (`налог_уплачен`, `зарплата_и_содержание`) и в падении денег в день, кратный 30. Прочерк в выпуске значит ноль. Для `m1_basic` последняя строка — вердикт приёмки.

Сценарии:

| Файл | Смысл |
|---|---|
| `m1_basic.json` | Один игрок, капитал 1 000 000 ₽, заказ поля, мельницы, пекарни и магазина, внутренние связи, цена полки = эталон хлеба |
| `m1_underfunded.json` | Капитал ровно равен стройке поля. Зарплату платить нечем. На 70-е сутки казна даёт 20 000 ₽ |
| `m1_two_players.json` | Двое делят цепочку через городской рынок муки. Магазин не покупает хлеб дороже эталона |

## Что получилось на черновых числах

Цены каталога, которые читает симулятор: поле 150000, мельница 250000, пекарня 300000, магазин 200000, сумма 900000. Это те же числа, что в `server/data/buildings.json`. Стадии 300/400/200/100 ‰ для этих четырёх цен: 45000/60000/30000/15000, 75000/100000/50000/25000, 90000/120000/60000/30000, 60000/80000/40000/20000.

Приёмка M1 (все четыре здания введены и выручка за 10 суток больше нуля) на `m1_basic` **достигается**. Капитал 1000000. После стройки в сутки 1 на счёте 100000, все четыре стадии 4. Сутки 2 пекарня берёт 80 кг муки у города по потолку коридора 112, это 8960, потому что мельница ещё не смолола: выпуск поля в эти сутки только доезжает до мельницы. Деньги падают до 91040. Первая продажа 100 хлебов по эталону 90 — сутки 3, выручка 9000. За 10 суток выручка 72000, налог ещё не уплачен. За 30 суток: хлеб 2800, мука 2240, зерно 2900, выручка 252000, НДС уплачен 22932, зарплата и содержание 24500, деньги 295608. Кошелёк не уходил ниже 91040.

Окупаемость всей цепочки при этих числах — сутки 125, это 6000 реальных минут, или 100 часов. Цель владельца 15–30 игровых суток (12–24 реальных часа) на каталоге не выполняется. Разбор, сетка и черновые рекомендации: `docs/proposals/BALANCE_M1.md`.

`m1_two_players` по-прежнему кормит пекарню мукой с городского клиринга, когда мельница уже предлагает объём. `m1_underfunded` по-прежнему останавливает поле просрочкой содержания, пока казна не даст 20000 на 70-е сутки.

## Сверка с сервером стройки

Исправлено в симуляторе, сервер не менялся.

- Формула цены стадии. Раньше симулятор резал стоимость накопительными границами в базисных пунктах (`split_by_bp`). Сервер берёт три независимых `// 1000` и отдаёт остаток последней стадии. На всех текущих `build_cost` каталога, включая четвёрку M1, ряды совпали, поэтому золотые прогоны не сдвинулись. Расходятся некратные суммы: 3 ₽ дают на сервере 0/1/0/2, а старый ряд был 0/2/0/1. Теперь симулятор вызывает ту же схему, что `stage_costs`.
- Порядок денег в одни сутки. Сервер списывает фундамент в момент заказа, а следующие стадии — в тике, по зданиям по очереди. Симулятор делал наоборот: доводил первое здание до эксплуатации и только потом закладывал второе. Для `m1_basic` (1000000 при сумме 900000) оба пути оплачивают всё в сутки 1. Для 200000 пути разные: серверный порядок оставляет три фундамента и 20000 на счёте, ни одного работающего здания; старый порядок построил бы поле целиком.
- Ожидание взноса. Прогресс замирает на оплаченной стадии, долг стройки не пишется. Просрочка зарплаты и содержания по-прежнему гасит выпуск этого здания (D-55).

Не трогал, хотя с сервером не совпадает побуквенно. На золотых прогонах и на прибыльной полке расхождение не проявляется.

- НДС симулятор режет с каждой продажи. Сервер розницы режет один раз с суммы месяца. Полный месяц полки 270000 даёт 24570 в симуляторе и 24546 на сервере, разница 24.
- Неоплаченный НДС в симуляторе останавливает все здания игрока. На сервере выпуск и полку глушит только `enterprise_arrears` (зарплата и содержание), счёт НДС лежит отдельно.
- Симулятор умножает зарплату на индекс города. `close_month` сервера — нет. У Уфы индекс 10000, произведение то же.
- Острота конкуренции в сценариях M1 равна 1, серверная розница возводит привлекательность в квадрат. Магазин один, делёж спроса ни при чём.

## Чего симулятор не делает

Нет PostgreSQL, HTTP и клиента. Нет четырёх слоёв дохода, порчи, земли, порта, рынка труда и износа, влияющего на выпуск. Платёж стройки идёт стадиями, как на сервере после слияния оплаты стадий; симулятор не повторяет отклонённый заказ сам по себе, кроме повтора внутри сценария, описанного выше. Формула загрузки с сервером совпадает.
