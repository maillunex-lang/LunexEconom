# V2-02. Единый серверный каталог (balance: draft)

## Реализовано

Источник данных: `server/data/products.json` (41 товар), recipes.json (41 рецепт), buildings.json (42 здания). Все названия и описания товаров/зданий перенесены из `docs/content/*.ru.md` без переименования ID. Все экономические числа и цены **черновые**, целые игровые рубли. `schema.json` содержит независимые схемы JSON Schema Draft 2020-12 для трёх массивов, строгие типы, запрет неизвестных полей. Каждая запись имеет `balance: draft`.

Сервер при создании реестра валидирует содержимое до подключения к БД. Проверяются типы, уникальность ID и ключей JSON, диапазоны качества, сумма весов рейтинга = 100 целочисленных процентов, все ссылки, число рабочих, производственная обеспеченность входов, ацикличность товарной сети, рецепты всех производственных зданий и сквозная M1. `GET /catalog` отдаёт весь снимок с `version` (SHA-256 от канонического JSON трёх массивов), заголовком `ETag` и статусом `304 Not Modified` на совпавший `If-None-Match`. `GET /catalog/products/<id>` и `/catalog/buildings/<id>` возвращают единичную запись. Каталог не копируется в клиент. Единицы: `kg`, `liter`, `barrel`, `m3`, `piece`. Суточные объёмы рецептов целые. Магазины задают `retail_cells` и `allowed_goods`.

Схема полей: цена товара `reference_price`, срок хранения `storage_life_factor` (целочисленный игровой коэффициент, не готовая модель порчи), качество `quality_range`, тип `type`; у здания `build_days`, `build_cost`, `size.width/height`, `jobs`, `storage_capacity`, `zones`; у рецепта `building`, `inputs`, `outputs`, `workers`, `technology_level`. У рецептов без входов предполагается добыча/выращивание из источника, который проверит будущий модуль производства.

| `docs/content/buildings.ru.md`: `field`, `quarry` | Одно здание производит несколько разных товаров | Отдельные рецепты зерно/овощи и песок/камень |

## Проверки

Без БД: `python tools/validate_catalog.py` (с обязательной зависимостью `jsonschema`); `python -m unittest server.tests.test_catalog_v2 -v`. Интеграция: изолированная PostgreSQL 16 по `LUNEX_TEST_DATABASE_URL`, затем `python -m unittest discover -s server/tests -v`. Не направлять тесты на боевую БД.

## Не реализовано в V2-02

Не внедрены экономика, цены региона, расчёт НДС, затраты сырья и материалов на стройку, моделирование качества и сроков хранения, реальное обеспечение неописанных ресурсов, выбор рецепта предприятием, торговые рейтинги, полноценные 8–10 розничных специализаций. Для этих направлений требуется согласованная спецификация и последующие модули. Числа не являются производственным балансом и не должны использоваться как подтверждённые реальные цены.

### Найденная проблема за пределами зоны V2-02

`server/tests/test_integration.py::TestClockCatalog.test_catalog` всё ещё ожидает пустые три массива (`assertEqual(load(name), [])`). После заполнения каталога такой тест закономерно падает. Файл вне выделенной зоны, поэтому **не менялся**. Для зелёного общего `server-check` директору необходимо разрешить минимально обновить ожидания этого устаревшего теста (проверка непустоты, схемы и целостности вместо равенства `[]`).

## CAT1. Полные производственные цепочки

Каталог заменён предложением из tools/sim/data/chains_proposed: **41 товар,
42 здания, 41 рецепт**. Старые ID сохранены, хлебная цепочка M1 не
изменена. Схема server/data/schema.json осталась прежней. Проверка
источников, потребителей и циклов проводится валидатором
tools/validate_chains_proposal.py на server/data с sinks.json.
Разделы logistics и utility в sinks.json только хранятся, не исполняются.

У двадцати исходных зданий сохранены все значения build_cost,
upkeep_month, jobs и size из прежнего server/data (например, поле 39000,
мельница 65000, пекарня 78000, продуктовый 52000 игровых рублей).
Новым 22 зданиям присвоены цены по формуле
**build_cost = предложенная стоимость × 260 // 1000**. Например,
лесосека 104000 → 27040; шахта 234000 → 60840. Остальные экономические
поля и цены товаров оставлены как в предложении. Все числа черновые,
не реальные рыночные цены; SHA-256 каталога изменился.

### Допущения CAT1

1. build_materials_required: целый draft-флаг 0/1, по умолчанию 0,
   виден через существующий реестр административных настроек.
2. При включённом флаге новый заказ резервирует клетки сразу,
   но первоначальный денежный взнос и стройматериалы фундамента
   списываются вместе только после поступления на склад предприятия.
   Автоматическая дорога, если требуется, оплачивается при заказе
   отдельно по существующему правилу.
3. Если денег и материалов одновременно недостаточно, причина ожидания
   money имеет приоритет, а поле missing фиксирует обе недостачи.
   Ожидание фундамента считается стадией 0. Повтор тика того же дня
   не удваивает дни ожидания.
4. Оплаченные раньше стадии, включая фундамент старых предприятий,
   не оплачиваются повторно и не расходуют материалы задним числом.
   Если флаг выключен до оплаты отложенного фундамента, его
   первоначальный взнос всё равно должен быть оплачен по прежнему
   request_id, уже без проверки материалов.
5. Никакой автоматической покупки материалов нет. Снос не возвращает
   стройматериалы, а денежные правила продажи/сноса сохранены.
6. Дополнительная стандартная миграция
   server/migrations/202611160900_enterprises_materials.sql необходима,
   поскольку прежняя таблица ожиданий запрещала стадию 0, а
   build_transfer_id имел ограничение NOT NULL. Регистрация этой миграции
   в enterprises/__init__.py является вынужденным узким исключением
   из первоначального ограничения на файлы; старые данные не удаляются.
7. Стоки топлива логистики и городского газа не активируются и не
   реализуются в CAT1.
