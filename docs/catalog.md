# V2-02. Единый серверный каталог (balance: draft)

## Реализовано

Источник данных: `server/data/products.json` (25 товаров), `recipes.json` (17 рецептов), `buildings.json` (20 зданий). Все названия и описания товаров/зданий перенесены из `docs/content/*.ru.md` без переименования ID. Все экономические числа и цены **черновые**, целые игровые рубли. `schema.json` содержит независимые схемы JSON Schema Draft 2020-12 для трёх массивов, строгие типы, запрет неизвестных полей. Каждая запись имеет `balance: draft`.

Сервер при создании реестра валидирует содержимое до подключения к БД. Проверяются типы, уникальность ID и ключей JSON, диапазоны качества, сумма весов рейтинга = 100 целочисленных процентов, все ссылки, число рабочих, производственная обеспеченность входов, ацикличность товарной сети, рецепты всех производственных зданий и сквозная M1. `GET /catalog` отдаёт весь снимок с `version` (SHA-256 от канонического JSON трёх массивов), заголовком `ETag` и статусом `304 Not Modified` на совпавший `If-None-Match`. `GET /catalog/products/<id>` и `/catalog/buildings/<id>` возвращают единичную запись. Каталог не копируется в клиент. Единицы: `kg`, `liter`, `barrel`, `m3`, `piece`. Суточные объёмы рецептов целые. Магазины задают `retail_cells` и `allowed_goods`.

Схема полей: цена товара `reference_price`, срок хранения `storage_life_factor` (целочисленный игровой коэффициент, не готовая модель порчи), качество `quality_range`, тип `type`; у здания `build_days`, `build_cost`, `size.width/height`, `jobs`, `storage_capacity`, `zones`; у рецепта `building`, `inputs`, `outputs`, `workers`, `technology_level`. У рецептов без входов предполагается добыча/выращивание из источника, который проверит будущий модуль производства.

## Таблица несовпадений / вопросы директору

| Источник / ID | Различие | Принятое решение до утверждения |
| --- | --- | --- |
| GDD 03 `goods.json`, `/catalog/goods` | Архитектура и задание требуют `products.json`, `/catalog/products/<id>` | Основным оставлен `products.json`; альтернативный endpoint не добавлен |
| GDD 03 `catalog_version` | Задание требует SHA-256 от канонического JSON | Поле `version` и ETag вычисляются автоматически, ручной версии нет |
| GDD 03 типы товара | GDD перечисляет raw/intermediate/consumer/industrial, задание также construction | `type` включает `construction`, список категорий и тип разделены |
| GDD 03 рейтинг сумма = 1 | По заданию все числа целые, коэффициенты дробного типа запрещены | Храним вес как целочисленные проценты, сумма = 100; потребителю API нужно делить на 100 |
| GDD 03 `build_months`, GDD 04 строительство стадиями по месяцам | V2-02 требует срок в игровых днях | `build_days` используется для игровых сроков, `build_months` оставлен совместимым черновиком |
| GDD 03 `retail.json`, 8–10 специализаций | В `docs/content/buildings.ru.md` перечислены только 3 розничных здания | Модели магазинов находятся в `buildings.json`, `retail_cells` и `allowed_goods`; отдельный `retail.json` отложен |
| `docs/content/buildings.ru.md`: `sawmill` | Лесопилка «пилит лес в доски», но `boards` отсутствует среди товарных ID | Временный рецепт с выходом `wood`, новое `boards` не выдумано; требует отдельного товара |
| `docs/content/buildings.ru.md`: `slaughter`, `steel_mill`, `electronics_plant` | Нет описанных в `products.ru.md` входных продуктов (животные, руда, комплектующие) | Черновые рецепты-добыча с пустыми входами; нельзя считать реалистичным балансом |
| `docs/content/buildings.ru.md`: `textile` | Здание производит и ткань, и одежду | Два взаимоисключаемых рецепта, выбор режима выпуска определяет модуль предприятий |
| `docs/content/buildings.ru.md`: `field`, `quarry` | Одно здание производит несколько разных товаров | Отдельные рецепты зерно/овощи и песок/камень |
| `docs/content/products.ru.md`: `sugar`, `butter`, `cheese`, `eggs`, `fish`, `gas`, `plastic`, `chemicals` | Нет однозначных производственных зданий / рецептов в текстовом списке | Товары уже объявлены; источники и реалистичные цепочки добавляются следующими модулями, не создаём новые здания |
| `docs/gdd/00_OVERVIEW.md` и `docs/spec/TIME_MODEL.md` | Игровой календарь определяет тики, но каталог хранит суточные объёмы | Рецепты в единицах на игровой день, календарь не переопределён |

## Проверки

Без БД: `python tools/validate_catalog.py` (с обязательной зависимостью `jsonschema`); `python -m unittest server.tests.test_catalog_v2 -v`. Интеграция: изолированная PostgreSQL 16 по `LUNEX_TEST_DATABASE_URL`, затем `python -m unittest discover -s server/tests -v`. Не направлять тесты на боевую БД.

## Не реализовано в V2-02

Не внедрены экономика, цены региона, расчёт НДС, затраты сырья и материалов на стройку, моделирование качества и сроков хранения, реальное обеспечение неописанных ресурсов, выбор рецепта предприятием, торговые рейтинги, полноценные 8–10 розничных специализаций. Для этих направлений требуется согласованная спецификация и последующие модули. Числа не являются производственным балансом и не должны использоваться как подтверждённые реальные цены.

### Найденная проблема за пределами зоны V2-02

`server/tests/test_integration.py::TestClockCatalog.test_catalog` всё ещё ожидает пустые три массива (`assertEqual(load(name), [])`). После заполнения каталога такой тест закономерно падает. Файл вне выделенной зоны, поэтому **не менялся**. Для зелёного общего `server-check` директору необходимо разрешить минимально обновить ожидания этого устаревшего теста (проверка непустоты, схемы и целостности вместо равенства `[]`).
