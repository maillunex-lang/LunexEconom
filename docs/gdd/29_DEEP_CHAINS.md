# GDD 29. Глубокие производственные цепочки

**Статус:** дизайн + детерминированная офлайн-симуляция, `balance: draft`. **Решение:** D-95 (`docs/gdd/DECISIONS_APPROVED.md`). Реализация сервера, клиента и изменение канонического каталога в это задание **не входят**. Данные: `tools/sim/data/deep_chains_proposed/`, симулятор `tools/sim/chains_deep/`, отчёт `docs/qa/deep_chains_design.md`.

## 1. Область и модель

Сырьё реально проходит несколько разных предприятий: `feed → dairy (milk) → dairy_processing_plant → grocery_store`; `quarry (sand) + quartz_mine (quartz) + gas → glass_plant (glass) → glass_plant (glass_bottle) → dairy_processing_plant`, с независимым рынком тары. Бутылку нельзя создать при розливе бесплатно. Для полноты: `oil → chemicals → plastic`, `wood → pulp_paper_plant (paperboard) → packaging_plant (milk_carton, cardboard_box, paper_label)`, а жестяная банка из `steel`. Цены остаются черновыми, физические единицы и рецептурные пропорции будут балансироваться отдельно.

В текущем V2 уже существуют `dairy` (ферма), `creamery` (маслосырзавод), `glass_plant`, `milk`, `glass`, `plastic`, `cheese`, `kefir`. Предложение **сохраняет все прежние ID** и добавляет `dairy_processing_plant` (молочный комбинат). Нельзя переименовать `milk` в фасованное молоко, иначе уничтожится совместимость старых партий, контрактов и магазинов. Фермерское молоко остаётся сырьём; в рознице постепенно заменяется фасованными продуктами.

## 2. Несколько рецептов в здании

- `recipes.json` сохраняет обязательный `building`. Опциональное `alternative_recipe: true` отмечает новую альтернативу для уже существующей категории здания. Валидация: уникальный `id`, `recipe.building == enterprise.building_id`, выбранный рецепт входит в разрешённый список рецептов здания; `workers ≤ jobs`. Список `allowed_recipes` вычисляется из всех строк `recipes` по `building`, без дублирования в `buildings.json`. Не все рецепты запускаются одновременно.
- `enterprises.recipe_id` уже существует: ровно **один активный рецепт на предприятие**. `GET /enterprises/{id}/recipes` возвращает список разрешённых, состав, качество, доступность и предполагаемую загрузку; `PUT /enterprises/{id}/recipe` с `request_id` и `recipe_id` меняет активный. Настройка применяется **со следующего игрового дня**, только после исполнения текущего тика; не чаще одного изменения за игровые сутки на предприятие. Запрос с тем же `request_id` идемпотентен; повторный новый запрос в тот же день возвращает `recipe_change_cooldown`. Проверять право владельца, `stage=4`, флаг, валидность каталога.
- Готовые партии, сырьё, тара, резервы и контрактные обязательства сохраняются при смене; ссылки поставок на старые входы **не удаляются**, но неиспользуемые помечаются неактивными, новые входы требуют настройки и допускают до 3 поставщиков на продукт. После обновления рецепта вернуть список дефицитных входов, не покупать их автоматически без правил supply.
- Незавершённый WIP: базовая реализация меняет рецепт только **между завершёнными суточными тиками**. Если в будущем появится долгая партия, она сначала завершается, либо её остановка переводит явно списываемую часть входов в отходы с записью ledger/себестоимости. В этой симуляции WIP отсутствует, `switch_lost_batches=0`; потеря 5% не моделируется, так как без WIP это было бы создание несуществующих убытков.
- Месяц в симуляторе = 30 условных игровых суток для сравнения сценариев; календарная скорость реального игрового мира берётся исключительно из `docs/spec/TIME_MODEL.md` (7 реальных дней = год), не из симулятора.

## 3. Упаковка и розница

**Выбор:** отдельные конечные SKU по виду фасовки, например `milk_glass_bottle`, `milk_carton_pack` (с сохранением сырьевого `milk`). Это явно учитывает спрос, склад, логистику, цену и качество, не требует сложного ключа `(product, packaging)` для всех существующих API и рейтинга. Минус: больше ID, ручная настройка ассортимента; в бете простота миграции важнее.

`glass_bottle`, `milk_carton`, `tin_can`, `cardboard_box`, `paper_label` самостоятельные оптовые товары (`piece`, `consumer: false`). Потребление тары задаётся в `inputs` точно в штуках: 40 `glass_bottle` + 40 `paper_label` + 40 `milk` → 40 `milk_glass_bottle` (упрощение: одна штука упакованного товара соответствует условному кг сырья). Каждая единица тары списывается, никогда не генерируется на стороне розницы. `glass_plant` имеет альтернативы `sand+quartz+gas → glass` и `glass → glass_bottle`, но конкретное предприятие выбирает только одну. Новый `quartz_mine` специализируется на кварцевом сырье; старый `quarry_sand` остаётся.

Пакеты: `wood → paperboard`, `oil → chemicals → plastic`, затем `paperboard + plastic → milk_carton`; этикетка и коробка из картона; банка из стали. Отдельный `packaging_plant` делает несколько типов тары на выбор, не одновременно. Условное `paperboard` из 20 кг `wood` → 40 кг отражает сырую технологическую гипотезу, а не физически достоверную массу. Розничный `allowed_goods` расширяется только в предложении. Существующее `milk` пока сохраняется в магазинах ради совместимости, последующая миграция ассортимента требует решения.

## 4. Множественные выходы и затраты

Пример сыра: `milk: 60 + paperboard: 8 → cheese: 14 + whey: 38`. Пример бойни: `feed: 40 → meat: 35 + animal_hides: 6 + offal: 8` (пока без отдельного скота: см. «Допущения»). В `outputs` уже допустимо несколько ключей; добавить необязательное `output_cost_allocation_bp: {product_id: bp}` с суммой **ровно 10000**. Пример сыр/сыворотка: `9000/1000` от общей стоимости партии; мясо/шкуры/субпродукты `8300/1000/700`. У каждого выхода своя складская партия с количеством, качеством и капитализированной себестоимостью.

`batch_cost_rub = Σ(inputs_qty × фактическая цена закупки) + зарплата партии + переменные производственные расходы`. Стоимость выхода `floor(batch_cost_rub × allocation_bp / 10000)`; остаток рублей присваивается первому по алфавиту ID. Сумма себестоимости выходов **строго равна** стоимости входов + услуг. Выручка возникает только при продаже, не от появления побочного продукта; при продаже признаётся его себестоимость, остатки остаются активом. Утилизация списывает остаточную себестоимость и оплачивает отдельный сбор. Если все выходы не помещаются в склад **после вычета потреблённых входов**, партия не запускается; альтернативно, при явно включённой утилизации разрешена транзакционная утилизация с учётом затрат и услуг. По умолчанию стоп, без бесплатной пропажи ценностей.

Момент резервирования: проверить входы, вместимость всех выходов, доступные связи и права; затем атомарно списать входы, сформировать все выходы и проводки. Никаких отрицательных запасов, повторы тиков не создают партии. FIFO-учёт в симуляторе; реальный сервер может применять партийный учёт, сохраняя точность и инварианты.

## 5. Смеси и качество

Смеси реализуются обычными `inputs` и `outputs`: например `milk: 40 + cocoa_powder: 4 + glass_bottle: 40 + paper_label: 40 → cocoa_milk: 40`, либо `milk + fruit_puree + milk_carton → fruit_yogurt`. Дополнительное `ingredient_shares_bp` описывает нормированную рецептурную пропорцию **вместе с тарой** в базовой единице рецепта и должно давать 10000 (для пищевой рецептуры желательно в будущем разделить ингредиенты и упаковку). При расчёте качества тара не должна искусственно улучшать пищевое качество: вводится `quality_input_weights_bp`, где сумма 10000 только по качественно значимым ингредиентам, упаковка имеет вес 0 для вкуса; тара может задавать отдельный `package_quality` и учитываться рейтингом только после отдельного решения.

Текущий сервер использует `weighted_inputs_or_base`: `q = floor(Σ(input_units × input_quality) / Σinput_units)` или 50 без входов. Для совместимости это правило сохраняется по умолчанию. Для нового `quality_input_weights_bp` рекомендуем `q = floor(Σ(q_i × weight_i)/10000)`, строго целочисленно; `minimum_input_quality` задаёт порог по каждому критическому входу. При `q_i < min` партия не запускается без расхода запасов. Отдельные атрибуты безопасности пищи, температуры, срока годности и микробиологии в данной фазе не реализуются; `storage_life_factor` остаётся источником срока хранения.

**Особенность предложения:** `ingredient_shares_bp` присутствует в двух демонстрационных JSON-рецептах для описания рецептурной доли, но симулятор использует фактические `inputs`; качество рассчитывается по текущему `weighted_inputs_or_base`, как и в server/enterprises. Перед серверной реализацией добавить независимый массив весов качества, после определения рейтингов/продуктовых характеристик.

## 7. Данные и проверки

`products.json`, `buildings.json`, `recipes.json` внутри `deep_chains_proposed` являются **полной будущей копией** формата `server/data`, с сохранением прежних ID; `patch.json` содержит аддитивные изменения и список изменяемых разрешений. Итого: 58 товаров (41 + 17), 48 зданий (42 + 6), 58 рецептов (41 + 17). Предусмотрен 6-рецептурный молочный комбинат: молоко-стекло, молоко-пакет, кефир, йогурт, сыр+сыворотка, какао-молоко. Из первоначального задания 4–5 выбран расширенный набор **6** ради проверки смеси с какао и отдельного кисломолочного продукта; при первом релизе можно оставить 5, отключив какао, без схемных изменений.

Исходный валидатор `tools/validate_catalog.py --data-dir TEMP` **ожидаемо отклоняет** полные JSON из-за `additionalProperties: false` в `server/data/schema.json`, начиная с `alternative_recipe`. После временного удаления *только новых метаданных* схема и граф проходят: `products: 58`, `buildings: 48`, `recipes: 58` и `OK`. Это доказывает совместимость старой модели ID и графа, **не доказывает** готовность нового расширения schema. Следующий этап должен расширить schema + cross-validator, затем вновь прогнать полную копию. `tools/validate_enterprises.py` без аргумента `--data-dir`, читает только живой `server/data` и поэтому не может проверить временную расширенную копию. Каноническая версия его теста прошла. Для будущей проверки добавить CLI путь временной копии или инъекцию каталога в test-fixture, не подменять `server/data` на работающем VPS.

## 8. Симуляция 24 игровых месяцев

Модель `tools/sim/chains_deep/model.py` делает 30 условных дневных циклов в месяц, одна партия на день, целые деньги/шт/кг, стоимость каждой выходной партии, FIFO-продажи, закупки с реальным ограничением места, зарплату, фиксированное/переменное содержание, явную утилизацию, учёт отсутствующей тары. Продуктовая прибыль `cash_delta + себестоимость остатков входов + себестоимость готовых партий`, без переоценки активов по будущей цене продажи. Ограничения: нет биржевого матчинга GDD28, транспортировки, реального спроса жителей, налогов, порчи, кредитов, масштаба всего города; это проверка правил, не прогноз финансов реального игрока. `golden_24_months.json` хранит **все 24 месячных состояния** для четырёх сценариев.

| Сценарий | Загрузка bp | Прибыль ₽ за 24 мес | Сырьевые остатки | Утилизировано ед. | Дней дефицита тары |
| --- | ---: | ---: | ---: | ---: | ---: |
| Один рецепт стеклянного молока | 10000 | 1060800 | 5880 | 0 | 0 |
| Смена рецепта в месяцы 9 и 17 | 10000 | 974400 | 19880 | 0 | 0 |
| Сыр + сыворотка с оплачиваемой утилизацией | 10000 | 1298400 | 0 | 27360 | 0 |
| Бутылки как узкое место | 680 | 27460 | 6000 | 0 | 671 |

Средняя загрузка в basis points (10000 = 100%). В сценарии с сывороткой прибыль положительна несмотря на стоимость отходов **только из-за черновых цен реализации сыра**; это не разрешение бесплатной утилизации. Для бутылочного дефицита закупки других входов заполняют склад, поэтому узкое место усиливается складским ограничением.

## 9. Решения для владельца

| Вопрос | Рекомендация | Основание |
| --- | --- | --- |
| Несколько рецептов | **Да, 1 активный из списка здания**, смена 1 раз/игровые сутки, с завтрашнего тика | Не ломает текущий `recipe_id`, сохраняет запасы |
| Фасовка | **Да, отдельные SKU по таре**, старый `milk` остаётся сырьём | Цены, спрос, склад и рейтинг прозрачны |
| Побочные продукты | **Да, `outputs` с несколькими ID**, распределение себестоимости 10000 bp | Себестоимость не возникает из воздуха |
| Переполненный склад | **Стоп** до обеспечения вместимости, утилизация лишь явно выбранная с оплатой | Нет отрицательных запасов или бесплатного уничтожения |
| Смеси | **Да, через обычные входы**, качественный порог, отдельные веса пищевого качества позже | Целочисленно и совместимо с `weighted_inputs_or_base` |
| Потери при переключении | **0 на первом этапе**, так как суточный тик атомарен; правило WIP позже | Иначе ложные потери партии |
| Активировать в игре сейчас? | **Нет**, после серверной задачи, миграций и тестов, за выключенным флагом | Каноническая схема ещё не поддерживает новые метаданные |

Все решения предметно рекомендованы в рамках D-95; внедрение и экономический баланс требуют отдельной приёмки.

## 10. План реализации

1. **CAT-DEEP:** согласовать ID, качество, физические единицы; добавить опциональные поля в schema, графовый валидатор и тесты временного каталога; не менять старые ID или хлеб M1.
2. **ENGINE-DEEP:** миграции `enterprises`/партии/выходы/утилизации, защищённый флаг, смена рецепта с идемпотентностью, атомарная проверка всех выходов, сохранение carry по рецептам, транзакционные ledger-проводки.
3. **SUPPLY-DEEP:** сохранение до 3 ссылок на активный вход, dormant-связей, оформление всех выходов в режимах GDD28, реальная себестоимость поступающих партий.
4. **RETAIL-DEEP:** отдельные упакованные SKU, ассортимент, рейтинг, рыночная ликвидность вторичных выходов, существующие стройматериалы/зарплаты/содержание.
5. **CLIENT-DEEP:** экран выбора рецепта/ожидания следующего тика/побочных продуктов в Android landscape, строки на русском, UI-тесты.
6. **QA/BETA:** полный PostgreSQL интеграционный тест, 24 месяца golden, смежные тесты supply/sales/строительства/розницы, нагрузки и CI; только потом включать флаг на тестовом окружении. Без автоматического включения на VPS.

## Допущения

1. Схема единиц текущего каталога неоднородна (`milk` кг, `kefir` литр). Эксперимент использует **условные единицы партии**, не реальную плотность молока; промышленная нормализация единиц является будущей задачей.
2. `quartz_mine` добавлен как новый специализированный объект, хотя заказчик допустил обычную шахту. Это позволяет сохранить старый `mine` и рецепты неизменными.
3. Какао-порошок в демонстрационных данных производится из `chemicals`: это **не пригодная для пищевого производства цепочка**. Демонстрационный рецепт существует исключительно как технический тест смеси и до релиза должен получать какао от отдельного импортного/сельскохозяйственного источника. **Не использовать рецептуру как факт или баланс.** Фруктовое пюре из `vegetables` столь же условное, нужен отдельный фруктовый товар.
4. В старом каталоге нет живого скота, потому вариант бойни использует уже существующий `feed` как технологическую заглушку. Мясо/шкуры/субпродукты требуют отдельной животноводческой цепочки перед запуском.
5. Суточный тик и месяцы симулятора синтетические; прибыль без налогов, доставки, порчи и рыночной ликвидности, случайности нет.
6. `ingredient_shares_bp` отражает доли фактических входов включая тару, поэтому эта пропорция нужна для интерфейса, но не равна пищевой рецептуре. Качественные веса нужно хранить отдельно.
7. Утилизация по умолчанию выключена; сценарий с сывороткой явно включает её для проверки расходов, не является стандартной политикой предприятия.
8. Каталог предложений (17 новых товаров/17 рецептов) демонстрационный и может пересекаться с идущей параллельно веткой `v2/catalog-chains`. При реализации выполнить сопоставление с **новым** main и не перезаписать чужой каталог.
