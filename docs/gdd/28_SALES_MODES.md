# GDD 28. Режимы продаж продукции и выбор поставщика

**Статус: предложение на утверждение, balance: draft.** V2-SUPPLY-SALES. Только новые документы и изолированный эксперимент `tools/sim/sales/`; **не серверная реализация**. Числа, сценарии, оценки прибыли и портовый потолок условны. Обязательная совместимость: `docs/AI_RULES.md`, `docs/supply.md`, `docs/gdd/06_RETAIL.md`, `18_CHAINS.md`, `21_AI_PLAYERS.md`, `25_RETAIL_REACH.md`, `27_DEMAND.md`, `server/supply/core.py`, `api.py`, `docs/spec/TIME_MODEL.md`.

## Принцип

Игрок владеет шахтой и выбирает, кто имеет право покупать **железную руду**. Политика задаётся **для пары `(enterprise_id, product_id)`** и действует только на реально произведённый товар. Модель не создаёт руду, покупателей, реальную выручку без ledger или второй спрос. Публичный ассортимент определяется каталогом фактических `outputs` рецепта; склад-посредник может продавать лишь подтверждённый запас с отдельным источником приобретения. В холдинге нужен достоверный `beneficial_owner_id`, а не совпадение названий компаний.

## 1. Четыре режима и время

| Режим | Право покупки | Распределение |
| --- | --- | --- |
| `private` | Только свои предприятия одного бенефициара | Товар резервируется под внутренние заявки, внешняя оферта нулевая |
| `public` | Любой покупатель, включая ИИ | После внутренних подтверждённых заявок по умолчанию публичная оферта, цена назначается продавцом |
| `mixed` | Свои и внешний рынок | `reserve_bp` 0..10000 для собственных; неиспользованный резерв не продаётся самовольно, публичная часть `stock - reserved_quota`, после внутренних перемещений |
| `invited` | Перечисленные `buyer_owner_id` и/или активные договоры | Только разрешённые идентификаторы; договорная часть имеет приоритет перед разовыми приглашениями |

**Точность трактовки `public`:** собственные заявки не получают автоматического бесконечного приоритета над публичными: приоритет своих действует для забронированных внутренних заявок до внешнего клиринга, а не для произвольно изменяемых после начала суток запросов. При `public` внутренний лимит задаётся уже подтверждёнными производственными потребностями; при `mixed` внутренний лимит дополнительно ограничен резервом. Если владелец хочет гарантию, выбирает `mixed`. Самоперемещение не генерирует фиктивной прибыли или расхода на покупку.

Изменения `mode`, `reserve_bp`, приглашений и `posted_price` сохраняются в очереди `effective_day = current_day + 1`; в пределах игровых суток активна неизменная версия, а повторный `request_id` отдаёт прежний ответ. Цена меняется не чаще **1 раза за игровые сутки**, включая переключение режима. Открытые договоры, уже оплаченные отгрузки, партии в пути, подтверждённые остатки и зарезервированные клиринговые операции не удаляются. Переключение в `private` блокирует **новые** внешние оферты, но не отменяет действительные договорные обязательства. При конфликте «private vs контракт» изменение отклонить с понятным предпросмотром или исполнить после завершения договора, а не silently нарушать его.

## 2. Ценообразование и доставка

`reference_price` берётся по SKU из актуального каталога (для `iron_ore` на момент проекта **80 игровых ₽/кг**). Допустимый диапазон объявления **50–300%** от эталона: `min = reference_price * 5000 // 10000`, `max = reference_price * 30000 // 10000`, шаг **1 игровой ₽** (всё в JSON). Эти границы ограничивают **ввод**, не гарантируют спрос. Цена на воротах, продавец получает `qty * posted_price`; **покупатель** оплачивает отдельно транспорт и при включённом флаге `logistics_fuel_required` топливо согласно существующему `server/supply`. Все суммы через ledger, единицы целые; НДС, если применим к товару, не начислять второй раз.

**Эффективная цена:** `gate_price + transport_per_unit + fuel_per_unit + tariff_per_unit`; перед оплатой показать точную котировку и общий кошелёк. Для проверки внешнего предела сравнивается **полная стоимость доставки** у частного поставщика и внешнего порта в ту же точку назначения. Цена порта в эксперименте `104` ₽ и качество `50`: условная ценовая альтернатива, а **не** подтверждённая государственная тарифная ставка или бесконечный товар. Выбор порта ограничен доступностью, бюджетом, сроком доставки, качеством и общими правилами склада. Оферт выше порта не удалять: показывать, что они неконкурентоспособны; покупатель по умолчанию не берёт. Ценовой сговор невозможно определить одними совпадающими ценами; дополнительно нужны сигналы (доля рынка, отсутствие альтернатив, синхронная динамика) для аналитики, но без автоматических санкций по одному сигналу.

## 3. Рейтинг поставщика и выбор

Отдельный от розничного рейтинга GDD06, **без бренда** и без создания дополнительного спроса. Перед сравнением отсеять: отсутствие публичного или договорного разрешения, недоступный остаток, `quality < max(buyer.min_quality, minimum_quality)`, просроченный контракт, невозможность доставки или отсутствие денег, цена **выше полностью доставленной цены внешнего порта**, score ниже `score_cutoff`. При несовместимом качестве внешнего порта или недоступном порте порог сравнения с ним не применяется (доступная альтернатива нужна, не фиктивная).

```
Q = quality(0..100) * 10
P = min(1000, reference_price * 1000 // effective_unit_price)
R = fulfilled_units_30d * 1000 // ordered_units_30d
    # если нет истории: нейтральное 700, пометка «мало данных»
D = 1000 * (10 + distance_units) // (10 + 2*distance_units)
S = (2500*Q + 4000*P + 2000*R + 1500*D) // 10000
покупать только при S >= 570
```

Вес суммы строго 10000 bp; все числа и приоритеты в `parameters.json`. `distance_units` есть **приближение** в симуляторе: сервер подставляет подтверждённые стоимость маршрута, топливо и ETA из `server/world`/`server/supply`, без повторного применения транспортного штрафа в цене. При одинаковом рейтинге: меньшая полная цена, больший подтверждённый остаток, затем стабильный ID. Не выдавать симуляторную эффективность транспорта за действительную географию. Надёжность считать по **доставленным/обещанным единицам**, не по числу кликов, со скользящим окном 30 суток; вынужденные отказы по вине покупателя (недостаток денег) не портят репутацию продавца. ИИ использует **те же публичные** значения, что человек, и виден с пометкой «Управляется ИИ».

**До трёх входных поставщиков:** рейтинг составляет короткий пул кандидатов, затем агрегатор выбирает максимум 3 действительных `source_type=enterprise|market|port`, с уникальными `priority` 1..3 и суммой `share` ≤1000‰. Городской рынок и порт занимают слот, а не создают четвёртую невидимую связь. `batch-switch`/`redirect` остаются **проектом**, выполняются только с owner auth **покупателей**, dry-run, атомарной заменой и предварительным сохранением `supply_links`/версионности. При массовой смене не устраивать 100 одновременных повторных переводов: версионированные группы, дедупликация, один клик по каждому предприятию и журнал изменений. Выбранные доли не увеличивают физическую потребность `27_DEMAND`/`25_RETAIL_REACH`: логистика обслуживает уже существующий спрос; розница распределяет его один раз.

## 4. Очерёдность при дефиците

На границе суток заморозить реальный склад и активные политики. Вычесть в отдельных корзинах **подтверждённые** собственные нужды, затем договорные отгрузки в пределах заранее зарезервированного договорного объёма, затем равноправные публичные/приглашённые заявки. Внутри одного приоритета применяется **max-min water filling**, отсортированный стабильным `buyer_id`, с выдачей остатков по ID; при равных запросах разница не более 1 ед. Между сутками возможно вращение стартового `buyer_id` по фиксированному `hash(day,sku)` для борьбы с вечным предпочтением младшего ID. У отсутствующей договорной брони нет права забрать чужой оплаченный заказ; дефицит показывается как `unfilled`. Просроченный договор не создаёт запас из воздуха. Правило `mixed` не продаёт зарезервированные под своих товары до изменения политики со следующих суток.

**Защита от монополии:** для спотовой закупки у одного продавца максимум 40% *доступного конкурентного суточного рынка* данного SKU/города одному покупателю (в bp, параметр; считать весь холдинг как одну группу). Для ИИ дополнительно действует существующее ограничение `21_AI_PLAYERS.md` ≤40% доступного рынка в городе; нельзя обойти разбиением на три завода/аккаунта одного холдинга. Договорные гарантии не должны нарушаться задним числом; их объёмы должны быть вычтены до оценки свободного рынка, а исключение из cap раскрыто в интерфейсе. Никакого автоматического искусственного удешевления цен и никаких «штрафов за доминирование» без решения владельца.

## 5. Видимость, деньги, безопасность

Покупатель видит публичную цену на воротах, качество агрегированного SKU, **классы** доступного остатка (`нет`, `мало`, `есть`, `много`), поставки за 30 дней, надёжность, расстояние, ETA, примерные фрахт/топливо, допуск к покупке и статус ИИ. **Точный конкурентный склад, остаток денежных средств, приватные договоры и внутренние планы не раскрываются.** Собственник продавца видит точные остатки, резерв, прогноз производства, спрос, принятые/отклонённые заявки по причине, потерянные продажи и упущенную выручку как **оценку**, а не как проведённый доход.

Серверная транзакция: проверить auth владельца, право на SKU/режим, `request_id`, количественный лимит, качество, заморозку склада и версии, цену и деньги; запереть нужные строки в стабильном порядке; скорректировать фактический остаток/резервы и один раз сделать атомарный ledger transfer; затем `shipment` или немедленное поступление; `receipt` возвратить на повторы. Двойная бухгалтерия = сумма проводок 0, ни склад, ни остатки кошельков не отрицательны. Собственное предприятие того же бенефициара: **внутреннее перемещение 0 ₽ без искусственного дохода**; покупка у собственного второго аккаунта для накрутки запрещена через граф бенефициара. ИИ использует ровно тот же API без исключений. Запрет недействительных цен, ID чужого предприятия, непризнанного инвентаря, переполнения 64-битных чисел, переподписки на один остаток и непокрытых обещаний. Внутри одной дневной фиксации проверять инвариант `начальный запас + физический приход - реальное потребление - отгрузки = конечный запас`.

## 6. Симулятор, результаты и границы

`python3 -m tools.sim.sales.model` или `from tools.sim.sales import run`: 24 **игровых месяца** по 30 условных суток. Сценарии и все параметры версионированы JSON в `tools/sim/data/sales_proposed`, полный по-месячный детерминированный эталон `golden_24_months.json`. Тесты `tools/tests/test_sales_sim.py`: режимы, score, пороги, качество, fair allocation, положительная маржа при нормальной цене, отсутствие внешней продажи при private, обратная связь цены, целые числа, сохранение запаса, нулевой баланс журналов имитации.

**Внимание:** модель аналитическая, не серверная миграция. Для компактности считает единственную шахту `iron_ore`, 30-дневные пакеты производства, постоянные запросы заводов, не моделирует экологию, рабочую силу, фактические поездки, склад межмесячных партий, налоги/НДС, контрактные штрафы, банкротства и движения денег за собственное конечное изделие. `seller_profit` = денежная выручка за проданную руду минус условные затраты шахты **плюс оценка сэкономленных закупок собственных заводов**, это условный консолидированный эффект, не бухгалтерская прибыль шахты. `buyers_profit` = оценочная маржа дальнейшей переработки, не фактический ledger-платёж за продукт. В журнале имитации отображаются только оплаты руды и перевозки между явно существующими кошельками и транспортным получателем; расходы/маржа аналитические. `capacity_utilization_bp` = произведено/мощность, `sold_capacity_utilization_bp` = собственное использование + внешние продажи / мощность. Завышенная цена раз в каждые 30 дней нулевых продаж снижает котировку на 10% (округление вниз), но не ниже нижней границы. **Это поведение условного алгоритма ИИ-продавца**, не автоматическое вмешательство сервера в цену человека. `lost_sales_units` = оценка запросов, не заключённых в сделки, даже когда оферта неконкурентна, а не подтверждённые заказы.

## 7. Решения для владельца

| Вопрос | Варианты | Рекомендация (`draft`) |
| --- | --- | --- |
| Границы цены | Свободно / 50–300% / 80–150% | **50–300%** для свободы игрока; качество/порт обрезают спрос, но не ввод |
| Шаг и задержка | 1 ₽ / 5 ₽; сразу / завтра | **1 ₽, раз в игровые сутки, применение со следующих**; блокировать гонки заявок |
| Кто платит доставку | Продавец / покупатель / согласованно | **Покупатель**, совпадает с действующим `supply` и топливом; позже договорные INCOTERMS-подобные условия |
| Видимость цен | Публичные все / скрытые / по приглашению | **Публичные оферты видны всем**, контракты и приватные цены только сторонам; склад как класс |
| Договоры | Просто whitelist / бронь / штрафы | **Договор с ограниченным объёмом, сроком, резервом и журналом**, штрафы только после отдельного баланса |
| Рыночный потолок | Жёсткий глобальный / внешняя альтернатива | **Только потолок конкурентоспособности при реально доступном порте**, не запрет объявлять дорогой товар |
| Доля рынка | Нет / 40% / 60% | **40% спотового объёма холдингу-покупателю**; без обхода через дочерние компании |

## Допущения

1. **Все новые цены/веса/пороги/лимиты JSON = balance: draft**, включая нулевое стартовое количество исторических отказов и условную надёжность 930‰ у шахты. Реальный порт недоступен по модели без подтверждения его цены/товара/ETA; в эксперименте он всегда считается условной сравнимой альтернативой.
2. Один игровой месяц условно равен 30 игровым дням. В **актуальном `docs/spec/TIME_MODEL.md`** описано 1 игровой месяц = 24 реальных часа, 12 дней = год, тогда как владелец отдельно высказывал изменение времени. Симулятор не переводит месяцы в реальные дни и не выбирает новую шкалу; директор должен синхронизировать ADR с последним решением владельца до серверной интеграции.
3. При `invited` whitelist привязан к бенефициару; в симуляторе он заменён короткими ID заводов для обозримости. Это не готовый договорный механизм.
4. В опыте нереализованы много-SKU рецепты, ограничение до трёх источников на вход (описано как интеграционный инвариант), реальная 30-суточная история надёжности и стабильность при 24-месячных банкротствах. Фиксированное качество и надёжность, геометрия/перевозки приблизительны.
5. Имитация не меняет продакшен-склады и не запускает алгоритм ежедневной торговли: месячные сделки агрегированы и имеют месячные уникальные ID; смена режима «завтра» проектируется и тестируется только на уровне спецификации, не через реальный clock API.
