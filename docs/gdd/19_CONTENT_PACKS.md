# GDD 19. Графика и контент

**Статус:** предложение, `balance: draft`. Сервер и клиент в этой ветке не менялись. Проверяемые примеры лежат в `tools/sim/data/content_proposed/`. Проверка: `python tools/validate_content_manifest.py`.

Решение владельца: графику можно менять из админки, но админка не подписывает пакеты и не принимает загрузки. Приватный ключ манифеста остаётся только секретом GitHub Environment `manifest-signing`. На VPS его нет и не будет. Конвейер собирает и подписывает набор, синхронизация кладёт неизменяемые файлы на сайт, админка выбирает, какая уже подписанная версия активна.

## Допущения

1. Единица активации — целый подписанный выпуск, а не смесь пакетов из разных выпусков. У всех пакетов одного `content.json` одна и та же версия, и она равна целому полю `release`.
2. Новых таблиц нет. Указатель живёт во флагах `registry.flag`, как остальные настройки: код → `LUNEX_FLAG_*` → `runtime_config` / `runtime_revisions`. Аудит — уже существующая таблица `audit`.
3. Общий `POST /admin/settings` эти ключи не принимает. Для них отдельные маршруты, потому что перед записью сервер сам скачивает публичный манифест и проверяет подпись. Иначе админ мог бы записать произвольную строку.
4. Роли: `support` и `viewer` только смотрят. `admin` переключает канал test. `owner` переключает stable, пол отката и список тестеров. Сейчас `WRITE_SETTINGS` — это owner и admin вместе; для этих ключей правило строже.
5. Список тестеров — строка логинов через запятую, не id устройств и не отдельная таблица. Пустая строка значит «тестеров нет».
6. Сервер не хранит байты пакетов. Он хранит номер выпуска и при показе админки может держать в памяти уже проверенную сводку. После перезапуска сводка заново берётся публичным GET.
7. Счётчик «кто уже на новой версии» — число запросов `GET /api/content/active` с запуска процесса, ключ только `(канал, выпуск)`. Без аккаунта, без устройства, без записи в базу. Это не число игроков.
8. Старые клиенты по-прежнему берут корневые `content.json` и `content.json.sig`. Их обновляет ручной шаг VPS, когда stable уже указывает на этот выпуск. Новые клиенты ходят в версионный путь и корневой файл не ждут.
9. Схема манифеста остаётся `schema: 1`. Поля `release`, `kind`, `label` старые клиенты не читают и не отвергают: `valid_content` смотрит только известные поля. Имена и версии остаются допустимыми для Godot (`is_valid_identifier`, `is_valid_filename`).
10. Подпись — тот же ключ, что у `content.json` сейчас: RSA PKCS#1 v1.5 / SHA-256, канонический JSON (`sort_keys`, компактные разделители, перевод строки в конце). Это не ключ APK и не третий ключ.
11. `min_version_code` пакета и пол отката `content_min_release` — разные числа. Первое сравнивает клиент со своим `versionCode`. Второе сравнивает сервер с номером выпуска контента.
12. Примеры в `content_proposed` — не настоящие пакеты. SHA-256 в них заглушки ровно из 64 шестнадцатеричных знаков. Валидатор файлы по URL не качает.
13. Звуки включены отдельным видом. Если папки звуков нет, выпуск просто без этого пакета. Игра не обязана их ждать.
14. Подсказки загрузки не едут внутри пакета. Они остаются во встроенных строках, источник `docs/content/loading_tips.ru.md`, и видны, даже когда пакет ещё не скачан.
15. Все лимиты — целые числа байт. Дробей нет.
16. `pipeline_test` не публикует Release, не трогает окружение `manifest-signing` и не выходит на VPS. Как у альфы.
17. Каталог `client/content/<набор>/` в этой ветке не создаётся. Это задание реализации.

## Модель контента

| Вид | Имя набора | Приоритет | Зачем |
|---|---|---|---|
| `icons_goods` | `icons_goods` | background | иконки товаров, `goods/<id>.webp` |
| `icons_buildings` | `icons_buildings` | background | иконки зданий |
| `ui_theme` | `ui_theme` | required | оформление интерфейса, единственный обязательный пакет |
| `map_tiles` | `map_tiles` | background | плитки карты |
| `season` | `season_<слово>`, например `season_winter` | background | сезон поверх темы и карты |
| `sounds` | `sounds` | background | музыка и эффекты, форматы ogg/wav/mp3 |

Правила имени: несезонный пакет называется так же, как вид. Сезонный начинается с `season_`. В одном выпуске каждый несезонный вид встречается не больше одного раза, сезон не больше одного.

Зависимости по имени набора внутри того же манифеста. Сезон зимы зависит от `ui_theme` и `map_tiles`. Циклов нет. Чужого имени нет.

Совместимость: у каждого пакета `min_version_code`. Клиент с меньшим `versionCode` этот пакет пропускает и рисует встроенную картинку. В примерах стоит 1001, потому что альфа считает `versionCode = 1000 + N`, а первый выпуск — 1001. Сборка без `build_info.json` считает код 1 и тоже остаётся на встроенном.

Запасной вариант, по порядку, и игра не падает ни на одном шаге:

1. Проверенный пакет этого выпуска.
2. Уже лежащий в `user://packs` пакет с тем же именем и совпавшим SHA-256.
3. Встроенные заглушки клиента.

Если обязательный `ui_theme` не прошёл проверку, весь манифест этого выпуска отвергается. Фоновый пакет, который не скачался, пропускается один; остальные ставятся.

## Канал и активация

Флаги, типы совпадают со значением по умолчанию:

| Ключ | Тип | По умолчанию | Кто пишет |
|---|---|---|---|
| `content_enabled` | bool | `false` | owner |
| `content_stable_version` | string | `""` | owner |
| `content_test_version` | string | `""` | admin и owner |
| `content_testers` | string | `""` | owner |
| `content_min_release` | int | `1` | owner |

Пустая версия или `content_enabled = false` значит «только встроенное». Непустая версия — десятичная запись целого без нуля впереди, от 1 до 2000000000, не ниже `content_min_release`. Список тестеров: не больше 32 логинов, каждый уже есть в `accounts`, строка не длиннее 1024 знаков.

Пол отката только растёт обычной кнопкой. Опустить его может только откат ревизии настройки, и этот откат для ключей `content_*` тоже только owner. Нельзя поднять пол выше уже включённого stable: сначала переключи выпуск, потом пол.

### Что делает сервер перед записью

`POST /admin/content/activate` с телом `{ "channel": "test"|"stable", "release": <int>, "confirm": true }`.

1. Роль подходит каналу, `confirm` именно `true`.
2. `release` целое, `content_min_release <= release <= 2000000000`.
3. Сервер сам делает GET `https://rikagro.ru/lunexeconom/v2/content/v/<release>/content.json` и соседний `.sig`. Чужой хост отвергается.
4. Подпись проверяется публичным ключом из `client/config/update_public.pem`. Приватного ключа на сервере нет.
5. Манифест проходит те же правила, что `tools/validate_content_manifest.py`: схема, целые, лимиты, зависимости, циклы, URL пакетов только `.../packs/<имя>-<версия>.pck`.
6. Поле `release` в файле равно запрошенному номеру. Версия каждого пакета равна строке этого номера.
7. Только после этого `settings.change` пишет строку номера в нужный флаг, `apply_at=now`, аудит `content.activate` со старым и новым значением.

Откат: `POST /admin/content/rollback`, канал, `confirm: true`. Предыдущий выпуск = текущий минус 1. Если он ниже пола или подпись не сходится, отказ, указатель не меняется. Дырки в номерах нет: выпуск, которого нет на сайте, просто не проходит шаг 3.

Сервер не умеет подложить неподписанный файл: указатель — это номер, а байты клиент берёт с публичного хоста и проверяет сам ещё раз.

### Протокол для клиента

`GET /api/content/active`. Без входа — канал stable. С входом, если логин есть в `content_testers` и тестовая версия непустая, — канал test. Иначе stable. Ответ не содержит байтов пакетов.

```json
{
  "schema": 1,
  "channel": "stable",
  "release": 2,
  "manifest_path": "content/v/2/content.json",
  "signature_path": "content/v/2/content.json.sig"
}
```

Встроенный режим: `channel` = `builtin`, `release` = 0, оба пути — пустые строки.

Заголовки: `Cache-Control: no-store`, `ETag` — SHA-256 канонических байт этого JSON в кавычках. Повтор с `If-None-Match` даёт 304 и пустое тело. Тело 304 не кешируется как пакет.

Порядок на клиенте:

1. Запросить `/api/content/active`. Короткий таймаут. Сеть пропала — оставить то, что уже смонтировано, иначе встроенное. Не падать.
2. Если `release` = 0, пакеты этого канала не качать.
3. Собрать URL только через `PublicBase.url`. Путь манифеста обязан быть `content/v/<release>/content.json`.
4. Скачать манифест (не больше 65536 байт) и подпись. Проверить RSA тем же `update_public.pem`. Чужой ключ не принимается.
5. `schema` = 1, `release` совпал с указателем, дальше правила текущего `valid_content`: уникальное имя, URL пакета, SHA-256, размер 1..104857600, зависимости внутри манифеста.
6. Несовпадение подписи, номера или хоста: этот выпуск выбросить. Один раз попробовать старый корневой `content.json` (для клиента, который ещё не знает указателя). Тоже не сошлось — встроенное.
7. Качать пакеты как сейчас: докачка, SHA-256, атомарное переименование, `wifi_only`. Обязательный пакет раньше фоновых. Фоновый ждёт 5 секунд без касаний, это уже есть.
8. По сотовой за один заход не больше 20971520 байт. Сначала `ui_theme`, если он влезает в этот бюджет. Остальное ждёт Wi-Fi. Галочка «только Wi-Fi» по-прежнему запрещает сотовую совсем.
9. Пакет с `min_version_code` выше своего `versionCode` пропустить.
10. Зависимость не смонтирована — зависимый пакет не монтировать.
11. Ошибка монтирования не сносит уже проверенный кеш.

Смена версии посреди сессии: указатель обновляется раз в час и при возврате в игру, как `update.json`. Новые файлы качаются в фоне. Картинка меняется на следующем входе, чтобы интерфейс не мигал. На экране загрузки монтировать сразу. Если новый пакет не встал, остаётся предыдущий проверенный, иначе встроенный.

Кеш клиента прежний: 524288000 байт в `user://packs`. Старые версии того же имени удаляются после успешного монтирования новой, как сейчас.

## Конвейер

Workflow в этой ветке не добавляется. Ниже описание для отдельного задания. Образец — `.github/workflows/android-alpha-release.yml`.

Имя: `content-release`. Запуск: `workflow_dispatch` только с `main`. Входы: `release` (целое, без `v`), `notes` (русская строка 1..300), `pipeline_test` (bool, по умолчанию false).

`concurrency.group`: `content-release-${{ github.repository }}`, `cancel-in-progress: false`.

Права: `contents: read` до публикации. Окружение подписи: `pipeline_test` → `ci-test` и одноразовый RSA; иначе `manifest-signing`. На `pipeline_test` нет GitHub Release, нет выкладки, нет VPS.

Шаги боевого прогона:

1. Checkout `main`, без сохранённых учётных данных в шаге сборки.
2. Проверить дерево `client/content/`: нет симлинков, нет `.gd`, `.tscn`, скриптов; только png, webp, jpg, jpeg, glb, ogg, wav, mp3; файл не больше 60 МиБ (это уже `tools/build_packs.py`). Плюс имена и виды из этой спецификации.
3. Собрать `<имя>-<release>.pck`. В манифест записать `schema`, `release`, и у каждого пакета `kind`, `label`, `version` = строка выпуска, `priority`, `dependencies`, `min_version_code`.
4. Прогнать `tools/validate_content_manifest.py` по собранному манифесту и лимитам.
5. Подписать канонические байты секретом `MANIFEST_SIGNING_KEY`. Публичный PEM сверить с `client/config/update_public.pem`.
6. Создать GitHub Release, тег `content-v<N>`, не draft и не prerelease. Файлы: `content.json`, `content.json.sig` и все `.pck`. Повтор того же тега запрещён. Уже лежащий файл с тем же именем и другим SHA-256 — отказ.
7. CI на VPS ничего не копирует. Ключа SSH у workflow нет, как у альфы.

Тег контента `content-vN` не пересекается с тегом APK `v0.1.N`.

### Как добавить картинку с телефона

1. Открыть репозиторий в мобильном GitHub, ветку от `main`.
2. Загрузить файл в будущий каталог, например `client/content/icons_goods/goods/<id>.webp`. Не в админку.
3. Открыть pull request. Проверка CI смотрит тип и размер, без подписи и без публикации.
4. После слияния в `main` с телефона же запустить `workflow_dispatch` у `content-release`. `pipeline_test=true`, если нужно только посмотреть артефакт.
5. Боевой прогон сам подписывает и кладёт Release.
6. Человек с доступом к VPS запускает уже описанную синхронизацию. Потом owner в админке включает test и, когда всё сошлось, stable.

Если править файл на GitHub неудобно, тот же путь делает исполнитель: ветка, PR, dispatch. Загрузка через админку не появляется.

### Синхронизация VPS

Менять `ops/partc/release_common.py`, новый скрипт не заводить. Приватный ключ туда не попадает. Проверка — публичным PEM из репозитория, та же `verify_signature`.

Новая функция рядом с `publish`:

- Скачать ассеты тега `content-vN` только с `https://github.com/maillunex-lang/LunexEconom/releases/download/...`.
- Отказаться, если подпись, хост, размер или SHA-256 не сошлись.
- Положить неизменяемый каталог `DEST/.signed-content/content-vN/`: `content.json`, `content.json.sig`, пакеты.
- Если каталог уже есть и хоть один файл отличается — отказ, не перезапись.
- Выложить в публичный корень версии: `content/v/N/content.json`, `content/v/N/content.json.sig`, и плоские `packs/<имя>-<N>.pck`. Плоский путь обязателен: текущий клиент склеивает URL именно так. Заголовки пакетов: `Cache-Control: public, max-age=31536000, immutable`. Манифест версии: `no-store`, как корневой.
- Корневые `content.json` и `.sig` этой функцией не трогать.
- Вторая операция, `publish_content_pointer`: прочитать публичный `GET /api/content/active` без секрета. Если канал stable и выпуск N, атомарно (как сейчас symlink у APK) скопировать уже проверенные байты `content/v/N/` в корневые `content.json` и `.sig` для старых клиентов. Если указатель `builtin`, корень не затирать.
- Держать на диске не больше 8 последних выпусков. Каталог не удалять, если на него смотрит stable, test или пол. 8 × 64 МиБ = 512 МиБ.
- `dry` ничего не пишет. Черновик и prerelease не публикуются, это уже есть в `github_release`.

## Админка

Раздел «Графика и контент» в существующей панели, без новой базы.

`GET /admin/content` для owner, admin, support, viewer:

- пять флагов и кто имеет право их менять;
- сводка активного stable и test, если публичный манифест скачался и подпись сошлась: номер, дата заголовка HTTP, размер каждого пакета, подпись, `min_version_code`, сумма байт;
- предупреждение одной фразой: клиент с `versionCode` ниже `min_version_code` пакета останется на встроенной графике. Число таких телефонов не показываем, мы его не собираем;
- счётчики запросов с запуска процесса по каналу и номеру. Подпись: «это запросы, не игроки»;
- последние строки аудита `content.activate`, `content.rollback`, `content.floor`, `content.testers`.

Кнопки:

- «Включить на test» — admin и owner, просит номер и подтверждение;
- «Сделать stable» — только owner;
- «Откатить» — предыдущий целый номер своего канала, та же роль, что и включение;
- «Поднять пол» — owner, новое целое не ниже текущего пола и не выше текущего stable;
- «Тестеры» — owner, строка логинов.

Чужой номер, битая подпись, цикл, чужой URL, номер ниже пола — кнопка не записывает флаг, на экране русская ошибка. Журнал всё равно пишет неуспех без тела пакета и без секретов.

На телефоне 360 px те же правила, что в GDD 17: без горизонтальной прокрутки.

## Безопасность

| Риск | Что делаем |
|---|---|
| Подмена пакета | URL только с `rikagro.ru`, точный путь, SHA-256, подпись манифеста. Клиент повторяет проверку, даже если сервер уже сказал «да». |
| Неподписанный манифест из админки | Админка пишет номер, не байты. Номер принимается только после проверки публичной подписи. |
| Отравление полей | Схема `additionalProperties: false` на конвейере и в валидаторе предложения. Лишние поля старый клиент игнорирует, но новый выпуск их не подписывает. |
| Откат на дырявый выпуск | Нельзя активировать номер ниже `content_min_release`. Клиент дополнительно молча пропускает пакет, если `min_version_code` выше его `versionCode`. |
| DoS большим пакетом | Потолок пакета 100 МиБ уже в клиенте; у вида потолок меньше; сумма выпуска не больше 64 МиБ; манифест не больше 65536; пакетов не больше 8; сотовая квота 20 МиБ. |
| Слежка | Нет id устройства, нет счётчика по аккаунту, нет новой таблицы визитов. Логин читается только чтобы решить, тестер ли это. |
| Кража ключа с VPS | Ключа там нет. Утечка VPS позволяет подменить файлы только до проверки подписи; клиент их отвергнет. |
| Admin включает stable | Маршрут stable смотрит роль owner, не общий `WRITE_SETTINGS`. |
| Повторная отправка | `confirm: true` и аудит. Повтор того же номера — пустая смена, новая ревизия не нужна, ответ `ok` без второй записи, если значение то же. |

## Критерии приёмки

1. `python tools/validate_content_manifest.py` печатает `OK`. Три хороших примера проходят, `incompatible.json` отвергается за цикл и чужой хост.
2. `python -m unittest tools.tests.test_content_manifest` зелёный.
3. При выключенном флаге клиент играет на встроенной графике и не падает без сети.
4. Указатель test видит только логин из списка. Остальные получают stable.
5. Сервер отказывается записать выпуск с битой подписью, чужим хостом или номером ниже пола.
6. Owner откатывает stable на предыдущий целый номер одной кнопкой, если подпись того номера жива. Ниже пола кнопка не работает.
7. Support открывает раздел и не видит рабочих кнопок записи.
8. `pipeline_test` не создаёт GitHub Release и не кладёт файлы на сайт.
9. Повторная выкладка того же `content-vN` с другим SHA-256 останавливается.
10. В репозитории нет приватного ключа, токена и секрета.
11. По сотовой за заход уходит не больше 20971520 байт, при «только Wi-Fi» — ничего.
12. Смена выпуска во время сессии не перерисовывает уже открытый экран; новая графика появляется на следующем входе.

## Открытые вопросы

1. Нужен ли второй сезон в одном выпуске (зима и праздник сразу)? Рекомендация: нет, один сезон. Второй выпуск дешевле, чем развилка в клиенте.
2. Менять ли картинку сразу, а не на следующем входе? Рекомендация: нет. Мигание интерфейса хуже, чем ожидание перезахода.
3. Писать ли корневой `content.json` самим игровым процессом? Рекомендация: нет. Игровой процесс не пишет статику. Корень обновляет ручной шаг VPS по публичному указателю.
4. Хранить ли счётчик запросов в базе? Рекомендация: нет в первой версии. Память процесса честнее и не следит.
5. Отдельный ключ подписи контента? Рекомендация: нет. Уже есть ключ манифеста, APK-ключ остаётся другим. Третий ключ — лишняя ротация в APK.
6. Звуки в первом боевом выпуске? Рекомендация: каталог завести, пакет не класть, пока нет файлов.
