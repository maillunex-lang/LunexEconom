# GDD 27. Слои населения, возраст и потребительский спрос

**Статус:** проект на утверждение директора, **balance: draft**. Ветка `v2/demand-design`. Сервер, клиент, существующие данные каталога и M1/M2 не изменены. Реализация эксперимента: `tools/sim/demand/model.py`, 24-месячный эталон `tools/sim/data/demand_proposed/golden_24_months.json`.

## Цель и источники

Вместо одинаковой «средней семьи» моделировать возраст, доход, структуру зарплат, пенсий и пособий, изменение покупательских привычек и осторожную мобильность доходных слоёв. Расчёт один раз **по городу и району** в начале игрового месяца, без перечисления каждого NPC. Месячный агрегат делится на дневные части только на стыке с розницей; новая модель **не заменяет** существующий суточный M2, пока не включена отдельным согласованным флагом `demand_layers_enabled` (предлагаемое имя, не зарегистрировано).

Исходные спецификации: [07_POPULATION](../proposals/07_POPULATION.md), [DEMAND_M2](../proposals/DEMAND_M2.md), [INTEGER_MATH](../proposals/INTEGER_MATH.md), [RETAIL_REACH 25](25_RETAIL_REACH.md), [REALESTATE 23](23_REALESTATE.md), [REAL_PRICES](../research/REAL_PRICES.md), действующий `server/data/products.json`. Первичная ссылка на **цены**, уже собранная в исследовании: [Башкортостанстат, январь 2026](https://02.rosstat.gov.ru/storage/mediabank/ceny-01-2026.pdf). Для долей бюджетов домохозяйств подтверждённых ссылок нет, и модель не выдаёт прогнозы за статистику. **Оговорка:** REAL_PRICES содержит уровни цен, а не статистически обоснованные доли расходов по 12 группам. Указанные ниже промилле **созданы как сценарные гипотезы**, не приписываются Росстату. Без документированного обследования семейных бюджетов утверждать соответствие реальным долям потребления нельзя.

### 1. Доходы и возраст

Четыре доходных слоя: `poor` (бедные), `lower_middle` (низкий средний), `middle` (средний), `affluent` (обеспеченные). Возрасты: `youth` (молодёжь), `families` (трудоспособные семьи), `pensioners` (пенсионеры). Доли каждой оси города в **базисных пунктах**, сумма каждой = **10 000**. Население пары `layer,age` получается сначала разбиением города по доходам, потом внутри слоя по возрасту. Остатки `//` отдаются по наибольшей дробной части и стабильному ID. Сумма жителей сохраняется до единицы.

Сценарные городские профили:

| Город | Бедные / нижний средний / средний / обеспеченные, bp | Молодёжь / семьи / пенсионеры, bp | Население |
|---|---|---|---:|
| Рабочий | 2800 / 4200 / 2500 / 500 | 2200 / 5900 / 1900 | 120 000 |
| Курорт | 1600 / 2800 / 4000 / 1600 | 2600 / 4900 / 2500 | 35 000 |
| Административный центр | 1300 / 2900 / 4400 / 1400 | 2400 / 5700 / 1900 | 250 000 |
| Село | 4000 / 3700 / 2000 / 300 | 1400 / 4400 / 4200 | 12 000 |

Числа искусственные, города типовые, **не** фактические данные Уфы или районов Башкортостана. Возраст и доход на первом этапе независимы условно внутри города; позднее заменить совместной матрицей, калиброванной статистикой. Межгородская миграция и смертность **не моделируются**: фиксированное население здесь проверяет отсутствие алгоритмического «вымирания», но не гарантирует демографическую устойчивость игры.

Доход пары за месяц на одного условного жителя, целые игровые ₽:

```
salary = salary_layer * salary_weight_age * salary_index_city // 1000000
pension = pension_layer * pension_weight_age // 1000
benefit = benefit_layer * benefit_weight_age // 1000
income = max(1, salary + pension + benefit)
goods_budget = income_total * goods_budget_layer_permille
               * goods_budget_factor_age_permille // 1000000
goods_budget = min(goods_budget, income_total - savings)
savings = income_total * savings_permille // 1000
housing_and_utilities = income_total * housing_utilities_permille // 1000
```

В сумме для слоя `goods_budget + savings + housing_and_utilities` не должен превышать доход при возрастном множителе (в будущем проверять после агрегирования), остаток является прочими тратами. В экспериментальном генераторе жилья и коммунальных платежей **нет**: эта строка резервируется, но никуда не переводится. Для `youth` повышающий множитель товарного бюджета 1050‰, для пенсионеров 950‰; фактический товарный бюджет обязательно ограничен доходом за вычетом сбережений.

`server/enterprises/__init__.py` уже содержит `enterprise_salary_worker_draft=100`, а `server/enterprises/core.py` принимает `salary_per_worker=100` игровых ₽ за занятое место в месяц. Не менять баланс зарплат. Платёж компании работнику через существующий ledger, и только **оплаченные** места агрегируются в месячный фонд. Нельзя одновременно считать эту зарплату и дополнительную бесплатную эмиссию рынка: `system:market` используется только как существующий платёжный источник с отдельной сверкой бюджетов при серверной интеграции. Зарплатный фонд экспериментального симулятора лишь индикатор, а не проведённые деньги.

**Месячная миграция доходных слоёв:** сигнал от индекса зарплаты и оплаченных мест, ограниченный `750..1250‰`, `move_bp=min(90,abs(signal-1000)//3)`. Только соседние слои; движения по каждому ребру за месяц ограничены 90 bp; перенаправление делается из **одного снимка** слоёв. При сигнале выше 1000 переход `poor→lower_middle→middle→affluent`; ниже 1000 обратный. Порог бедности (защитный технический пол) 600 bp при росте. Никакого «телепорта» из бедных в обеспеченные, числа и инварианты проверены тестом. Это **не** эмпирически выведенная мобильность и не замена миграции людей между городами; изменение доходных групп не изменяет численность города.

### 2. Корзина, цена, премиум и сбережения

Данные: `profiles.json` содержит 12 полных карт `shares_permille` **ровно на все 41 SKU**, сумма по каждой строке = **1000‰**. Для 21 промышленного/промежуточного SKU покупки домохозяйств равны 0. Для 20 `consumer=true` доли корректируются по возрасту и доходу, затем целочисленно нормируются с правилом наибольшего остатка. К каждой покупке применяется отдельная целочисленная эластичность слоя.

Рассматриваемые **условные предпочтения**, не моральные характеристики настоящих жителей: у молодёжи выше доля кваса, медовухи и электроники; у пенсионеров выше доля рыбы, копчёной рыбы и кефира; у семей молока, хлеба, овощей и техники. Пиво и селёдка **отдельными товарами отсутствуют** в 41-SKU каталоге: медовуха и копчёная рыба здесь только тестовые доступные заменители, они не переименованы в пиво или селёдку. При добавлении соответствующих SKU каталог и корзины потребуют новой версии.

У бедных условные премиальные товары `car, electronics, appliances, furniture, mead` имеют 0‰; у обеспеченных их доли существенно выше, но даже они ограничены целым бюджетом. Нельзя раздать покупки без действительного наличия, охвата и цены. Товарная корзина не создаёт бесплатно статус «обеспеченного» за сам факт покупки.

```
sku_budget = split_largest_remainder(goods_budget, sku_shares_permille)
price = max(1, reference_price * local_price_index_permille // 1000)
price_response_permille = clamp(
    1000 - (local_price_index_permille - 1000)
             * elasticity_layer_permille // 1000, 300, 1500)
wanted_units = sku_budget * quantity_per_1000_budget
               * price_response_permille // (1000 * price)
```

В этом эксперименте `quantity_per_1000_budget=1000`, то есть расход в игровых ₽ / цену с поправкой на эластичность; это условная **покупательская потребность**, не платежная ведомость. После оценки цена и наличие определяют фактические продажи, они не могут превышать доступные единицы. Эластичность: бедные 1450, нижний средний 1150, средний 850, обеспеченные 550‰. Никаких `float` и случайных выборок. Замечание о границах: постоянные зарплаты и индекс цен при горизонте больше 24 месяцев требуют социальной политики и калибровки; тесты на 24 месяца **не** доказывают долгосрочного равновесия.

### 3. Стыки с существующими модулями (только проект интерфейса)

1. **07 → M2/06, единственный источник спроса:** при расчёте `(city_id,district_id,layer_id,age_id,sku,month_index)` получить базовую целую потребность. Разложить только месячный агрегат на дневные части по календарю из `docs/spec/TIME_MODEL.md`, сохраняя остатки. Существующий M2 остаётся владельцем спроса до отдельной миграции и flag. В 06 раздавать **тот же пул**, а не суммировать новый и старый.
2. **Радиус 25:** применить `store_reach_changed`, `radius`, `fade`, `fame`, `A²`, лимиты касс и **внешнюю опцию** из GDD25 к уже определённым целым единицам спроса. Одна заявка домохозяйства не увеличивается от количества магазинов или этажей. При отсутствии магазина спрос становится неудовлетворённым, не выручкой.
3. **Полка и рейтинг 06:** выбирать продавца по физической доступности, цене, наличию и `R`, с ограничением `min(demand,stock,capacity)`. Новая эластичность относится к **желанию купить на рынке**; реакцию `R` на цену нельзя повторно применять как ещё один мультипликатор количества. Рейтинг меняет выбор продавца, а не создаёт второй пул.
4. **Городской газ `city_gas_utility`:** `server/market/city_gas.py` рассматривается как отдельная услуга коммунального бюджета домохозяйства/здания, а `gas` в каталоге имеет `consumer=false`. **Не** добавлять газ в корзину розницы. Если флаг активен, коммунальные расходы могут уменьшить свободный товарный бюджет только один раз, после расчёта действительного списания. При отключённом флаге поведение M2 прежнее. Сценарий здесь газовых счетов **не проводит**.
5. **Аренда 23:** расходы магазинов `area_m2 * rent_rate_rub_m2_month` и налоги уменьшают прибыль продавца, а не доход NPC и не доступный спрос города. Если когда-нибудь реализована аренда квартир населению, ее счёт учитывать только в `housing_and_utilities`, не списывать дублирующе. НДС уже включён в полку согласно D-18; новые доходные слои не создают отдельный налог на продажу.

**Идемпотентность:** месячная версия `(city_id,district_id,month_index,catalog_version,profile_version)`; повторный расчёт возвращает прежний результат. Эталонные входы только с сервера; приватные зарплаты компаний и составы конкретных семей в клиент не отправлять. Привязка жителя к клетке не требуется: районы и охват от 25 дают агрегатную геометрию.

### 4. Изолированный симулятор: что реально проверяется

`tools/sim/demand/model.py` считает 4 города × 24 месяца, массивы из 41 SKU, без индивидуальных жителей. В нём:
- Фиксированные население и возраст для отделения зарплатного эффекта от демографии; месячная мобильность ограничена.
- Чистый индекс цены подстраивается медленно на `±80 bp/месяц`, с пределами `750..1450‰`; начальные индексы 1000‰. Это **гипотеза**, не эмпирическая инфляция.
- Предложение оценивается грубо от `availability_permille`, затем улучшается до 1000‰; продажи ограничены доступностью, вместимостью и коэффициентом `retail_capture_permille=650`.
- Распределение выручки слоям идёт по **потребности каждого слоя по данному SKU**, и его сумма строго равна всей выручке по SKU. Это атрибуция условных магазинов, а не настоящие кассы с полным `A²` и геометрией.
- `shortage_units` в отчёте означает **неудовлетворённую потребность**, включая внешнюю опцию и невовлечённый спрос; `surplus_units` означает предложение, не проданное условными точками. Поэтому они могут быть положительными **одновременно**: нет доступного конкретному человеку магазина, хотя складской товар существует. Не путать с физическим отсутствием товара на рынке.
- Ни один домохозяйственный платёж не проводится через ledger: цифры `retail_revenue_rub` являются расчётными, а не признанными проводками. Нет автоматического финансирования NPC, налогов, аренды, инфляционных ожиданий, износа инфраструктуры и поведенческой корреляции.
- **Инварианты**, которые проверены: целочисленность, воспроизводимость, 41 SKU, 12 корзин, сумма долей 10000 bp, сумма корзины 1000‰, сумма выручки слоёв, спрос = продано + неудовлетворённое, положительная торговля, ограничение переходов слоёв и отсутствие отрицательных долей.
- **Не проверено:** полноценная макроэкономическая «спираль бедности» при закрытиях предприятий, реальная смерть города через демографию, баланс ledger реального рынка, инфляция на 10 игровых лет. Поэтому 24-месячное прохождение означает «не обнаружена деградация в этих **условиях**», а не гарантию.

### 5. Решения для владельца

| Вопрос | Возможности | Рекомендация |
|---|---|---|
| Сколько слоёв видно игроку | Один усреднённый / четыре / двенадцать | **Четыре** доходных слоя в основной панели; три возрастные группы как фильтр, не показывать 12 чисел одновременно |
| Частота миграции | Каждый день / месяц / год | **Раз в игровой месяц**, показывать стрелку изменения в bp и график за 12 месяцев, суточная волатильность вводит в заблуждение |
| Панель города | Один средний доход / графики состава | «**Состав населения**»: 4 доли дохода, 3 возраста, индекс зарплат, доля сбережений, спрос на 5 востребованных SKU, дефицит и диапазоны покупательной способности; предупреждение `оценка` |
| Премиальный спрос | Жёсткий запрет / плавный переход | Бедным запрет только на явно премиальные группы в первоначальном сценарии; остальным **плавная** зависимость от реального бюджета и цены |
| Защита от бедности | Неограниченные переходы / лимиты | До утверждения реальных социальных трансфертов ограничить `90 bp` на переход и применять только оплаченные зарплаты |
| География | Житель на клетке / районный агрегат | Районная модель из 25, без отдельных NPC, чтобы не сломать производительность Android |
| Достоверность | Объявить числа фактическими / пометить прототип | **Только `balance: draft`**, заменить сценарные 12 корзин данными бюджетных обследований перед балансом беты |

### 6. Риски и критерии приёмки

**Главные риски:** разница **условных игровых ₽ и реального рубля** (`INTEGER_MATH` задаёт отдельную шкалу), неверное сопоставление 100 ₽ зарплаты с расходами домохозяйств, неконтролируемое двойное начисление дохода, «два спроса» M2+новая модель, искусственная инфляция без инфляции доходов, нормирование 21 не-потребительского SKU, стигматизация возрастных групп, одновременные запасы и неудовлетворённые потребности, конфликт месячного и дневного тика.

Критерии для следующего этапа: согласовать 12 корзин с источниками обследований семей; зафиксировать экономическое равенство зарплат и бюджета `system:market`; заменить допущения об охвате эталоном GDD25 на одном SKU и сравнить с M2; ввести отдельный отключённый по умолчанию feature flag; провести стресс-сценарии падения рабочих мест на 50%, повышения цен вдвое, прекращения поставок и демографического оттока; профиль на реальном размере Уфы без сканирования каждого NPC. Никаких серверных изменений до решения директора.

## Допущения

1. **Числа** в `profiles.json`, `cities.json`, `parameters.json` и в результатах симуляции целиком сценарные. По `REAL_PRICES.md` проверен список/тип/порядок реальных цен, а **не** доли расходов. Не маскируем гипотезы ссылками.
2. Для возраста `families` использовано название группы, объединяющей работающих взрослых и семьи, а не точная демографическая возрастная граница.
3. Разработчик не изменял `tools/sim/__main__.py`, потому что файл вне зоны. Поэтому требуемый буквальный вызов `python -m tools.sim demand-golden` **пока недоступен**. Эквивалент: `python -c 'from tools.sim.demand import rebuild_golden; print(rebuild_golden())'`; директору требуется отдельное разрешение на минимальный CLI-диспетчер для точной команды.
4. Имя новой директории `tools/sim/demand/` перекрывает прежний модуль `tools/sim/demand.py`. Новый `__init__.py` загружает **неизменённый** старый модуль под внутренним именем для совместимости M1/M2. Это прозрачный переходный адаптер; при будущем переносе CLI предпочтительно выделить отдельное имя пакета, чтобы не держать обход импорта.
5. В `docs/spec/TIME_MODEL.md` зафиксирован **1 игровой месяц = 24 реальных часа**, год = 12 суток. Здесь рассматривается ровно 24 игровых месяца по текущему главному документу, без самостоятельно назначенной конверсии реального времени.
