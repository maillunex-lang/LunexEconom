# Правила работы исполнителей V2 (ChatGPT)

Директор проекта (Claude) пишет спецификации (`docs/gdd/`, `docs/spec/`), раздаёт задания, принимает работу. Владелец решает по продукту и подтверждает слияния. Этот файл заменяет правила V1 (они сохранены в `archive/v1`).

## 1. Ветки и слияние
Задание содержит имя ветки. Ветка от свежего `main`; коммиты небольшие и логичные; **в `main` не пушить**: отчёт с SHA и «можно принимать», директор проверяет и сливает. **Постоянное разрешение владельца (2026-11-15):** директор вправе сливать в `main` сам, когда приёмка пройдена (зона файлов соблюдена, тесты и CI зелёные, конфликтов нет, отчёт честный). Остаются ТОЛЬКО по прямой команде владельца: изменения VPS и боевых сервисов (часть C), смена и перенос ключей подписи, финальное переключение V1/V2, вайп мира и удаление данных, публикация релиза не по плану. Перед сдачей синхронизироваться со свежим `main`, разрешить конфликты без потери чужого; дождаться только релевантного CI.

## 2. Безопасность
Не менять боевой сервер, базы, nginx, systemd, ключи; часть C (VPS) только по явному «выполняй часть C» владельца. Секреты не в репозиторий и не в чат. Мир V1 и его база не трогаются, аккаунты не переносятся.

## 3. Архитектура (кратко, подробности в `docs/ARCHITECTURE.md`)
PostgreSQL 16 единственная база (в тестах изолированная); модули-пакеты `server/<модуль>/`; регистрация маршрутов, миграций, тиков и флагов через `server/registry.py`; миграции `YYYYMMDDHHMM_модуль_описание.sql`; единый каталог `server/data/*.json`; деньги целые, двойная запись, идемпотентность по `request_id`; время по `docs/spec/TIME_MODEL.md`.

## 4. Зоны файлов
Исполнитель владеет **только** файлами своего модуля: `server/<модуль>/`, `server/migrations/*_<модуль>_*.sql`, `server/tests/test_<модуль>_*.py`, `server/data/<свои файлы>.json`, `docs/<модуль>.md`, клиентские файлы своего экрана. Общие файлы (`server/registry.py`, `server/game_server.py`, `server/db.py`, `.github/workflows/*`, `docs/PROGRESS.md`) меняются **минимально и аддитивно** (одна-две строки подключения модуля); чужие модули не редактируются, нужные изменения описываются в отчёте.

## 5. Быстрая CI-приёмка (решение владельца от 2026-11-16)

**Для обычного PR достаточно зелёного релевантного GitHub Actions CI на актуальном SHA.** Директор проверяет только зону файлов, отсутствие конфликтов и запрещённых действий; после этого может сливать по уже предоставленному владельцем разрешению. Не требовать повторных ручных прогонов CI, фиксированного числа новых тестов, обязательных скриншотов/видео, визуальных QA-отчётов или полного набора workflow для каждого PR. Проверки должны быть адресными: сервер — server-check, клиент — client-check, сайт — website-check; Android APK и релизные workflow только при изменениях сборки/подписания/релиза или по отдельному запросу. Если релевантная CI-проверка не запущена, пропущена, отменена или работает не на актуальном SHA, PR нельзя считать проверенным.

Критические инварианты серверной экономики, деньги, идемпотентность, миграции, авторизация, секреты и сохранность данных **не упрощаются**: их автоматические тесты остаются в соответствующем CI. Если обнаружен конкретный UI-дефект, допустима адресная ручная проверка, но скриншоты не обязательны для приёмки. Явное разрешение владельца на изменения VPS, данных, ключей и внеплановый релиз остаётся обязательным независимо от CI.

## 6. Клиент
Только Android, горизонтально, safe area, Godot 4.7, стиль Forest Glass, данные с сервера, 2.5D карта и штаб-квартира по `docs/spec/PRODUCT.md`; без постоянных анимаций вне карты.

## 7. Краткая сдача

Достаточно ссылки на PR, SHA и 1–3 предложений о сделанном. Результат релевантного CI берётся из GitHub. Подробный отчёт и вложения только при выявленном риске, сбое или явном запросе владельца.
