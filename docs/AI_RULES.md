# Общие правила работы ИИ-исполнителей (обязательны для каждого задания)

Директор проекта (Claude) раздаёт задания, проверяет отчёты и сливает ветки в `main` **только по команде владельца**. Исполнитель в `main` не пушит.

## 1. Ветка и слияние
1. Создай ветку с именем из задания **от свежего `main`** (`git fetch`, `git checkout -b <ветка> origin/main`). Коммить небольшими логичными коммитами, пуш только в свою ветку.
2. Перед отчётом обнови ветку от свежего `main` (merge), разреши конфликты, не теряя чужих изменений, прогони все тесты.
3. Отчёт: SHA последнего коммита и название ветки, список файлов по зонам, что сделано и как проверено (команды и ключевой вывод), что **не** сделано, найденные проблемы в чужих зонах, что нужно подключить другим. Фраза «можно пушить в main» только после зелёных тестов и зелёного CI ветки.
4. Не заявляй готовность без работающей реализации и тестов. Документы должны соответствовать фактическому коду.

## 2. Безопасность мира
Мир не обнуляй, `citygen --apply --wipe` не запускай, боевую PostgreSQL не используй для экспериментов (только `lunex_ci` или временную SQLite), секреты не в чат и не в репозиторий, на VPS ничего не выкатывай без «да» владельца. Не удаляй существующие API, данные игроков, аккаунты и предприятия; новые механики вводи за настройкой или флагом, по умолчанию совместимо со старым поведением.

Правила для горячих файлов: добавляй **только свои** строки. Маршруты: свой отдельный блок рядом со своим модулем (маркеры `# BEGIN <имя> routes` … `# END <имя> routes`), не переставляй и не форматируй чужое. `production.step_month`: свои вызовы одной-двумя строками (`import x; x.monthly(db, ph, month, now)`), логика в своём модуле. CI: допиши свои тесты в списки, не затирая чужие. `PROGRESS.md`: своя запись сверху. Если нужна правка вне зоны — опиши в отчёте или сделай минимальный хук и назови его.

## 4. Данные и миграции
Новые таблицы создавай функцией `ensure(db, ph)` модуля и подключай в `game_server._prepare` и `postgres_db.init` одной строкой; в `postgres_db.SCHEMA` не добавляй (иначе нужна нумерованная миграция, а номера у параллельных веток столкнутся; если всё же необходимо, назови файл следующим свободным номером и сообщи в отчёте, директор перенумерует при слиянии). Деньги: целые рубли, одна проводка `economy.post` на перевод (сумма проводок 0), идемпотентность по `request_id`, транзакции под мировой блокировкой (SQLite `BEGIN IMMEDIATE`, PostgreSQL advisory lock 20261114). Любые новые расчёты месяца вызывай из `production.step_month` одним вызовом и делай идемпотентными по `month_index`.

## 5. Тесты (обязательны)
- Серверные тесты SQLite (`cd server && python -m unittest discover -s . -p 'test_*.py'`) и PostgreSQL на `lunex_ci` (`LUNEX_DB_ENGINE=postgres`, `test_postgres_*`) для каждого нового модуля; ключевые сценарии, ошибки, идемпотентность, баланс проводок.
- Симулятор баланса: сценарии для своих механик (`docs/BALANCE_PLAN.md`, раздел 5), инварианты 0, красных флагов нет, коридоры `server/balance_targets.py`.
- Клиент: смоук-тесты Godot (`client/tests/*.gd`, всегда `quit()`), пример запуска `godot --headless --path client -s tests/<имя>.gd`; регистрация в `.github/workflows/client-check.yml`.
- Все существующие тесты остаются зелёными (известные давние сбои интерфейса `ui_v1_smoke`, `ui_v1_input`, `ui_v1_gestures`, `ui_main_menu`, `world_027_*` не твои).

## 6. Клиент (если задание его касается)
Только Android, горизонтальная ориентация, полноэкранный интерфейс с учётом выреза и безопасной зоны, Godot 4.7, стиль Forest Glass (см. `client/build_menu.gd`, `client/world_screen.gd`), 2D-режим мира не возвращать, 2.5D-мир остаётся на `client/world.gd`. Данные только с сервера, сервер — источник истины. Экономия батареи: статичный интерфейс, редкое обновление, без постоянных анимаций вне карты.

## 7. Баланс и реализм
Цены и параметры реальные для Башкортостана и разные по городам (`docs/REGIONAL_PRICES.md`, масштаб 1 игровой ₽ = 50 реальных). Параметры выноси в `server/balance.py` или свой модуль с константами, не «магические числа» внутри логики. Игра — экономический тренажёр: объяснимые показатели, воспроизводимость, одинаковые правила для игроков и NPC.

## 8. Документация
Каждый блок: документ в `docs/` (API с примерами запросов и ответов, таблицы, миграции, ограничения, что не сделано), записи в `docs/PROGRESS.md` и своя строка статуса в `docs/EXPANSION_1_0.md` (только статус своего блока).
