# Админка A1

Админка доступна отдельным маршрутом `/admin/*` и не является частью игрового `/api/`. В браузере используется статическая панель `web/admin/`; API адрес задаётся в `web/admin/config.js`.

## Роли

| Роль | Права |
|---|---|
| `viewer` | просмотр обзора, игроков и аудита |
| `support` | просмотр, блокировка игроков и компенсации в пределах `support_compensation_limit` |
| `admin` | права support плюс настройки, флаги, ревизии и откат |
| `owner` | все права, включая выдачу ролей и смену собственного пароля |

Вход выполняется логином/почтой и паролем не короче 14 символов. Сессия хранится только хэшем токена, действует 60 минут и продлевается активностью максимум до 8 часов. Неудачные входы ограничиваются по IP и идентификатору. Второй фактор не используется по решению владельца. Аварийный `X-Admin-Token` сохраняется только для loopback и пишет в аудит actor `admin:loopback`.

## Маршруты A1

`POST /admin/login`, `POST /admin/logout`, `POST /admin/password`, `GET /admin/overview`, `GET /admin/players?q=`, `GET /admin/players/{id}`, `POST /admin/players/{id}/block|unblock|compensate`, `POST /admin/sessions/revoke`, `GET|POST /admin/settings`, `GET /admin/flags`, `GET /admin/revisions`, `POST /admin/revisions/rollback`, `GET /admin/audit`, `POST /admin/roles`.

Компенсация всегда идёт через ledger, требует целую ненулевую сумму, причину, ссылку на обращение и идемпотентный `request_id`. Повтор с тем же request_id не создаёт новую проводку; баланс игрока не может уйти в минус.

## Первый owner и откат

Первого владельца создаёт операторской командой на сервере: `python -m server.platform.accounts_admin grant <логин> owner`. Команда не входит в веб API. Откат настройки выполняется через `POST /admin/revisions/rollback` с номером ревизии; создаётся новая ревизия, история не перезаписывается.

Рекомендуется ограничить отдельный nginx маршрут `/admin/` HTTPS и allow-list адресов. Сама панель не публикуется этим этапом.


## A2: экономика, мир, сервер, алерты

Маршруты: `GET /admin/economy`, `/admin/economy/history?days=N&after=DAY&limit=N`,
`/admin/cities`, `/admin/world/events?after=ID&limit=N`, `/admin/parcels?owner=ID&city=ID`,
`/admin/server`, `/admin/ticks`, `/admin/errors`, `/admin/alerts`.
`POST /admin/cities/{id}/growth` принимает `enabled`, `reason`, `request_id`.
Роли просмотра: `viewer`, `support`, `admin`, `owner`; изменение роста только `admin`, `owner`.
У каждого изменения есть запись в `audit` с IP, actor, ролью, старым/новым состоянием.
Таблицы A2: `admin_daily_stats`, `admin_growth_requests`, `admin_error_log`.

### Принятые допущения

- Обработка каждого игрового дня создаёт один неизменяемый снимок `admin_daily_stats`, конец дня,
  после модулей розницы и предприятий. Прошлые дни до установки A2 не восстанавливаются
  из текущих остатков кошельков: это дало бы ложные исторические данные.
- Активный игрок за сутки/неделю определяется существующими `sessions.created_at`, а не
  действиями в игре; повторные сессии одного игрока учитываются один раз.
- Фактический дневной выпуск изделий выводится из `enterprise_daily_load.load_bp` и
  `enterprise_inventory.output_carry` сразу после штатного обработчика производства
  (порядок 41). Два целых параметра однозначно восстанавливают выпуск с учётом
  дробного остатка по рецепту, без изменений модуля предприятий. Снимок записывается
  в `admin_production_daily` с чеком `admin_production_receipts` идемпотентно.
  Данные до подключения A2 не восстанавливаются из текущих остатков.
- НДС считается по ставке каждой записи `retail_sales_daily.vat_bp` как включённая в выручку
  доля. Выручка и налог считаются за семь последних завершённых игровых дней.
- Список городов отражает именно 20 существующих `world_cities`. Радиус и застроенность
  рассчитываются единственным источником `server.world.core.growth_stats`.
- Изменение `growth_enabled` влияет на существующий алгоритм `grow_month`; алгоритм не
  копируется. Используется идемпотентный ключ с блокировкой строки города.
- Лента `world_events` отфильтрована по версиям существующих событий. В карточках мира
  отдаётся безопасная метаинформация без произвольных JSON-тел событий.
- У городов курсором служит текстовый `id`, у участков естественный составной
  первичный ключ `(px,py)` в формате `px:py`. Это стабильнее смещений (`OFFSET`) и
  соответствует существующей схеме без выдуманного числового `id`.
- `admin_error_log` хранит только категорию ошибки и день, а не сырые трассировки, URL,
  персональные данные или секреты. Сообщения исключений `game_ticks.error` редактируются
  перед выдачей. Архив тиков является первичным источником ошибок тиков.
- Описания алертов на русском. Алерт просрочки предприятия использует накопленные
  `enterprise_build_waits.waiting_days` и `enterprise_arrears`.
- Журнал аудита старых действий A1 может содержать произвольные поля: расширенная карточка
  игрока отдаёт только безопасные метаданные, без старого payload.

### Границы телеметрии A2

- Первичная запись ошибок тиков остаётся в `game_ticks`. A2 копирует их безопасные коды
  в `admin_error_log` при запросе `/admin/errors` и следующем дневном тике. Сырые тексты
  ошибок и трассировки не выдаются наружу.
- Глобальный перехват необработанных исключений **чужих** API-маршрутов в A2 не подключён:
  действующий обработчик исключений находится в `server/game_server.py`, который запрещён
  зоной V2-ADM2. Для полноценного сбора этих событий требуется отдельное разрешённое
  задание на минимальное подключение в `server/game_server.py` с отдельным соединением,
  чтобы диагностическая запись переживала откат игровой транзакции.
