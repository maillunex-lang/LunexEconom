# LunexEconom V2 · подпись, обновления и ресурсные пакеты

Статус: реализация V2-01b в ветке `v2/release`. **Production-развёртывание на VPS не выполнялось. GitHub environment `android-signing` настроен владельцем; секреты не хранятся в репозитории.** Часть C только по прямой команде владельца «выполняй часть C».

## 1. Публичный адрес и маршруты

Android: единственная настройка `client/config/public_base.gd`, по умолчанию `https://rikagro.ru/lunexeconom/v2`. Для доверенной сборки можно переопределить `ProjectSettings`-параметр `lunex/public_base_url`. Веб: единственная настройка `web/config.js`. Все пути сайта относительные (`./styles.css`, `./download/lunex.apk`), не начинаются с `/`. Проверка: `python3 tools/check_website.py`. Не устанавливать cookies на общий домен `rikagro.ru`. Токен авторизации Android хранится в зашифрованном локальном хранилище Android Keystore (AES-GCM) после регистрации/входа.

| URL относительно base | Доставка |
| --- | --- |
| `update.json` и `update.json.sig` | Статические манифест и detached RSA-подпись; `Cache-Control: no-store` |
| `content.json` и `content.json.sig` | Статические манифест и подпись; `Cache-Control: no-store` |
| `download/lunex.apk` | Подписанный APK, поддержка HTTP Range/206 и byte ranges |
| `packs/<name>-<version>.pck` | Неизменяемые проверяемые пакеты; `Cache-Control: public,max-age=31536000,immutable` |
| `api/` | Только прокси к игровому API; не использовать static; запретить кеш токенов |

**План для nginx, будущая часть C, НЕ применять здесь.** В конфигурации общего HTTPS-хоста нужно обслужить отдельными location `/lunexeconom/api/` (reverse proxy игровому сервису), `/lunexeconom/download/` (локальный каталог APK), `/lunexeconom/packs/` (иммутабельные PCK), `/lunexeconom/update.json`, `/lunexeconom/update.json.sig`, `/lunexeconom/content.json`, `/lunexeconom/content.json.sig` (статика с revalidation/no-store) и `/lunexeconom/` (лендинг). **Не создавать** параллельных корневых `/download/` или `/packs/`; это относительные пути внутри `/lunexeconom/`. Провести `nginx -t`, проверить отсутствие конфликтов с остальным содержимым `rikagro.ru`, затем отдельное согласованное развёртывание.

Манифесты содержат **полные HTTPS URL**, которые клиент принимает только в рамках настроенного базового адреса. Перенаправления HTTP отключены, URL с другой схемой, хостом, пользовательскими данными, query/fragment и traversal отклоняются.

## Адрес API и переключение V1/V2

Android получает API-адрес через `PublicBase.api_url()` из `client/config/public_base.gd`. По умолчанию путь `v2/api` относительно `lunex/public_base_url`, то есть `https://rikagro.ru/lunexeconom/v2/api`. Настройка `ProjectSettings` `lunex/api_path` позволяет выбрать `api` после переключения владельцем, без правок сетевой логики. Путь проверяется: запрещены небезопасные схемы, пользовательские данные, query, fragment и traversal; при ошибке клиент не отправляет запрос и показывает сообщение о недоступности сервера. V1 продолжает использовать старый маршрут до отдельного решения владельца. Переопределение ProjectSettings входит в конфигурацию сборки и само по себе не меняет уже установленный APK.

## 2. Создание постоянного APK-ключа: ТОЛЬКО ВЛАДЕЛЕЦ

**Действия ниже выполняет владелец на доверенном устройстве, не на VPS и не в ChatGPT.** Для нового пакетного идентификатора `org.lunex.bashkiria.v2` нужен один неизменный ключ.

```sh
# Пароли вводятся интерактивно, не в командах и не в истории shell.
keytool -genkeypair -v \
  -keystore lunexeconom-release.p12 \
  -storetype PKCS12 \
  -alias lunexeconom-release \
  -keyalg RSA -keysize 4096 \
  -validity 10000 \
  -dname "CN=LunexEconom Android Release"
```

`10000` дней примерно 27 лет. Не использовать debug-ключ, не менять идентификатор пакета. Для текущего Godot 4.7 пароль keystore и пароль ключа должны быть **одинаковыми**. Альтернативу EC поддерживает Android keystore/toolchain, но для этого проекта рекомендован RSA-4096 ради предсказуемой совместимости.

Сделать **две резервные копии вне GitHub и VPS**, в двух независимых зашифрованных хранилищах/офлайн-носителях. Отдельно хранить надёжно записанный пароль и alias, проверить восстановление обоих архивов. **Потеря приватного ключа может навсегда запретить обновление уже установленных APK**, если нет отдельного механизма ротации подписи в соответствующей среде Android.

Скопировать keystore в base64 и добавить через GitHub → Settings → Secrets and variables → Actions → environment `android-signing` (без required reviewers, только ветка `main`). Секреты: `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. Не отправлять пароль/base64 ключа в ChatGPT, git, issue, PR, логи, VPS.

```sh
base64 -w0 lunexeconom-release.p12 > lunexeconom-release.base64
# Это СЕКРЕТ: копировать только в GitHub Secrets, затем убрать временный файл.
# Публичный отпечаток, для фиксации в ops/release_cert_sha256.txt:
keytool -exportcert -rfc -keystore lunexeconom-release.p12 -alias lunexeconom-release \
  | openssl x509 -noout -fingerprint -sha256
```

В `ops/release_cert_sha256.txt` заменить комментарий **публичным** SHA-256 отпечатком сертификата (32 байта, hex); не копировать приватный ключ. `tools/verify_apk_cert.py` отклоняет отсутствие файла, чужую подпись или несколько сертификатов. При тестовом режиме в CI отпечаток вычисляется от одноразового тестового сертификата; выпуск такого APK в production запрещён.

## 3. Отдельный ключ манифестов

**Для V2-A1 владелец использует отдельный RSA-4096 ключ, не совпадающий с Android APK ключом. Актуальный согласованный режим подписи описан ниже в разделе «Подпись манифеста в GitHub Actions».** Если ключ ещё не выпущен, создание и хранение осуществляет владелец через доверенное устройство/защищённый процесс:

```sh
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -out lunex-manifest-private.pem
openssl pkey -in lunex-manifest-private.pem -pubout -out lunex-manifest-public.pem
```

Приватный ключ в GitHub Environment `manifest-signing` после отдельного согласования владельца и в защищённых резервных копиях, не на VPS и не в коде. Публичную часть положить в `client/config/update_public.pem` и зафиксировать в проекте для следующей подписанной сборки. Без неё клиент **не принимает ни update.json, ни content.json** (fail closed).

Отдельные `update.json.sig` и `content.json.sig` это base64 RSA PKCS#1 v1.5/SHA-256 над **точными байтами** канонического JSON (`sort_keys`, compact UTF-8, завершающий newline). Скрипт:

```sh
python3 tools/make_update_manifest.py build/lunex.apk --version v2.0.1 \
  --min-code 1 --notes "Обновление игры" --output build/update.json
python3 tools/sign_update_manifest.py build/update.json \
  --private-key /offline/lunex-manifest-private.pem \
  --public-key /offline/lunex-manifest-public.pem
python3 tools/sign_update_manifest.py build/packs/content.json \
  --private-key /offline/lunex-manifest-private.pem \
  --public-key /offline/lunex-manifest-public.pem
```

**В V2-A1 допускается только защищённый Environment Secret `MANIFEST_SIGNING_KEY` для CI без ручных одобрений, окружение ограничено веткой `main`; на VPS приватный ключ не передавать.** Для релизов альфы подпись выполняется автоматически внутри GitHub Actions после проверки APK. Каждый manifest и `.sig` публикуются атомарно парой после проверки обоих. При ошибке подписи, SHA, размера или скачивания игра удаляет повреждённый файл или сохраняет неполную `.part` для докачки; неподписанное обновление не предлагает.

## 4. Создание релиза и CI

`.github/workflows/android-release.yml` выполняется вручную (и для тегов `v*`). Test-режим CI: создаёт **одноразовый RSA-ключ** на runner, экспортирует релизные APK/AAB, проверяет `apksigner verify --print-certs`, отпечаток, версию, единственный `arm64-v8a`, `jarsigner -verify` для AAB, бюджет APK и публикует GitHub Actions **артефакт с предупреждением TEST-NOT-FOR-RELEASE**. Тестовый APK не является производственным релизом.

Для настоящего альфа-релиза после слияния в `main` используется единый `android-alpha-release.yml`: ключ и публичные отпечатки уже должны быть закреплены; environments без required reviewers и с ограничением `main` настраиваются отдельно. `tools/release_version.py` преобразует строгий тег `vMAJOR.MINOR.PATCH` в Android `versionCode = major*1000000 + minor*1000 + patch` и `versionName` без `v`. Следующая публикация должна иметь более высокий номер; не использовать теги вне схемы, проверять установленные версии. Debug APK подписывается **отладочным** ключом отдельного `android-build.yml` и не публикуется как релиз.

Исторический ручной `.github/workflows/android-publish.yml` сохранён для иных схем выпуска, но альфа-теги `v0.1.N` через него запрещены. Новый `android-alpha-release.yml` проходит окружение `production` без required reviewers. Требует успешный кандидат с **производственным** ключом того же SHA, заново проверяет подпись и размер, создаёт GitHub Release. **CI не имеет SSH-ключа VPS и никогда автоматически не копирует файлы на VPS.** Следующая фаза C, только после команды владельца, делает ручную публикацию GitHub Release APK, подписанных `update.json(.sig)`, `content.json(.sig)`, архивных пакетов и тестирует HTTPS Range/206.

## 5. Поведение приложения

`client/update/manifest_client.gd`: при старте, каждый час, по кнопке «Проверить обновление». При проверенном RSA-манифесте: версия выше текущей → кнопка «Скачать»; `min_version_code` выше установленной → блокирующее окно до успешного обновления. `resumable_download.gd`: последовательные Range-запросы до 512 КиБ, сохранение `.part`, проверка Content-Range, полного размера и SHA-256, автоматическая повторная попытка с паузами 1/2/4/8 сек. Можно включить «Только Wi-Fi», настройка хранится в `user://update_settings.cfg`.

`client/android_plugin/` исходники Android v2 плагина, `client/addons/lunex_installer/` Godot export-plugin. Сборка АAR выполняется CI и подключается при Gradle экспорте. `PackageInstaller` предлагает обновление системному установщику. Если неизвестные приложения запрещены, пользователь сам разрешает установку и повторяет нажатие. `FileProvider` резервный путь, без публичного `file://`. **Android не гарантирует установку APK полностью без действий пользователя.** `USER_ACTION_NOT_REQUIRED` на Android 12+ допустим только при выполнении условий platform/installer-of-record; система вправе потребовать подтверждение.

Android Keystore AES-GCM сохраняет токен авторизации в приложении, не в cookie/открытый домен. `user://`, настройки и токен сохраняются при установке поверх **той же package ID и того же сертификата**. При смене debug → release сертификат отличается: иногда требуется удалить тестовую сборку, **что может удалить данные**. Это не является безопасным обновлением.

## 6. Пакеты ресурсов и оптимизация

`tools/build_packs.py` собирает `client/content/<name>/...` в версионированные `<name>-<version>.pck`, выбирает ресурсные форматы PNG/WebP/JPG/GLB/OGG/WAV/MP3, без скриптов, .tscn, сторонних ссылок и symlinks. Упорядоченные одинаковые входные файлы формируют одинаковый SHA-256 (тест повторной сборки), отдельный `content.json` подписывается офлайн. `core_*` требуются сразу; остальные загружаются после 5 секунд без взаимодействия. Лимит кеша 500 МиБ; проверка размера, SHA-256, атомарный rename, очистка старых версий; `ProjectSettings.load_resource_pack` позволяет подключить готовый пакет без перезапуска. При недоступности пакета базовый клиент продолжает работать со встроенной графикой и заглушками; `pack_ready` сообщает остальным модулям о новой графике.

```sh
python3 tools/build_packs.py --source client/content --output build/packs \
  --version 2.0.1 --godot /path/to/Godot_v4.7.2-stable_linux.x86_64
```

Размер: цель **не более 99 МиБ** на APK `arm64-v8a`. Godot 4.7.2 Android release шаблон (ВСЕ архитектуры) содержит ~104.8 MB; из них ARM64 `libgodot_android.so` сжат ~22.9 MiB. Это **размер шаблона, а не готового APK**. Фактический размер debug и release после сборки записать ниже. Проверка `tools/check_apk_size.py` проваливает CI при превышении `99*1024*1024` байт. Лимит 99 МиБ утверждён владельцем; оптимизация размера остаётся желательной, но не блокирует релиз в пределах лимита.

## 7. Проверки, отмена и ограничения

```sh
python3 -m unittest discover -s tools/tests -v
python3 tools/check_website.py
godot --headless --path client --editor --quit
godot --headless --path client -s tests/smoke.gd
godot --headless --path client -s tests/release_smoke.gd
```

Godot-ресурсный smoke запускается из `tools/tests/test_packs.py`: дважды собирает тестовый `.pck`, проверяет идентичность и делает динамическое подключение/чтение текстуры без перезапуска.
Дополнительная интеграционная проверка `tools/tests/test_network.py` запускает поддельный локальный HTTPS-сервер с одноразовыми тестовыми TLS/RSA ключами, проверяет подпись манифеста, отклонение изменённого содержимого, обязательное обновление, HTTP Range с обрывом и повтором, неверный SHA-256, скачивание и подключение PCK. Это тестовая сеть 127.0.0.1, не production и не новый сервер игры.

Дополнительно до приёмки на реальном Android: вручную проверить установку в системном UI, изменение разрешения неизвестных источников, Wi-Fi-only, переход с ошибочной подписи и SHA, докачку после обрыва, отсутствие потери авторизации, запуск в горизонтальном режиме с safe area. Серверное развертывание остаётся за отдельной частью C.

**Откат:** никогда не подменять подписанный опубликованный APK старым с меньшим versionCode: Android отклонит downgrade. Для отката логики пересобрать старый код под **новым более высоким** номером и подписать тем же APK-ключом. Для отката графики вернуть предыдущий проверенный `content.json` с новой подписью и сохранёнными immutable пакетами. Если потерян ключ подписания манифеста, старое приложение не начнёт доверять новому ключу без нового APK с обновлённым публичным ключом.

## V2-01c: генерация офлайн-ключа и ручная проверка Android

На **личном доверенном компьютере владельца**, не на VPS, запустить из клона репозитория:

```sh
python3 -m pip install cryptography
python3 tools/make_manifest_keypair.py --output-dir "$HOME/lunex-manifest-offline"
```

Скрипт запрещает размещать приватный ключ внутри репозитория, не перезаписывает ключи, сохраняет приватный PEM с правами `0600`, выводит только публичный PEM. Владелец переносит **только** `lunex-manifest-public.pem` в `client/config/update_public.pem`, коммитит публичную часть и делает две защищённые резервные копии приватного ключа вне GitHub, CI и VPS. Приватный PEM не пересылать через чат. До появления публичного PEM проверки манифестов намеренно отклоняются без падения клиента.

Тест реального Android пока **не выполнен**. Ручная приёмка: установить APK с релизной подписью на чистое Android-устройство, войти по email и проверить штаб-квартиру/кошелёк/время; нажать «Проверить обновление» и убедиться, что неподписанный или неверно подписанный `update.json` отклонён без падения; после публикации настоящих подписанных `update.json` и `.sig` проверить предложение новой версии, докачку, SHA-256 и системное подтверждение установки; проверить сохранение данных после установки поверх с тем же сертификатом; проверить отдельно PCK и режим Wi-Fi. Провал: принятие неподписанного манифеста, установка чужого APK, падение, потеря токенов или некорректная обработка отсутствующей сети.

## Выпуск альфы одной командой (V2-A4)

**Единственная точка входа для производственной альфы:** GitHub → **Actions** → **Android alpha release** → **Run workflow** → ветка **main**. Указать:

- `version`: `0.1.N` без `v` (новый номер; существующий тег/релиз не использовать);
- `notes`: утверждённые русские заметки длиной от 1 до 300 символов;
- `min_version_code`: необязательно, по умолчанию код предыдущего опубликованного альфа-релиза (для самого первого релиза 1). Принудительное обновление задаётся сознательно;
- `pipeline_test`: `false` для настоящего релиза, `true` для проверки конвейера **без релиза**.

Альтернативный запуск через GitHub API: `POST /repos/maillunex-lang/LunexEconom/actions/workflows/android-alpha-release.yml/dispatches` с `ref=main` и полями `inputs.version`, `inputs.notes`, `inputs.min_version_code`, `inputs.pipeline_test`. Отдельных `candidate_run_id`, `version_tag` и ручного запуска подписания нет.

### Проверки и порядок операций

1. **Preflight (read-only):** `main` и SHA источника, строгий формат `0.1.N`, монотонный `versionCode=1000+N`, отсутствие повторного тега, уже опубликованные Release, русские заметки 1–300 символов, `min_version_code`. Общая блокировка concurrency не допускает параллельных альфа-выпусков.
2. **Candidate:** переиспользуется `android-release.yml` через `workflow_call`. Только официальный сертификат из `android-signing`; проверка отпечатка из `ops/release_cert_sha256.txt`, package `org.lunex.bashkiria.v2`, версии и versionCode, `arm64-v8a` без других ABI, APK ≤ 99 МиБ, подпись APK, AAB и SHA256SUMS. Кандидат сохраняется только как артефакт этого запуска.
3. **Manifest:** независимо перепроверяются APK/AAB, SHA256SUMS, package/версия/ABI и сертификат. По APK формируется канонический `update.json` с утверждёнными параметрами. Отдельный секрет `MANIFEST_SIGNING_KEY` из environment `manifest-signing` подписывает манифест, и **обязательно** выполняется проверка `update.json.sig` закреплённым `client/config/update_public.pem`. При любой ошибке следующего шага публикации не будет.
4. **Publish:** только когда обе предыдущие стадии успешны и исходный SHA всё ещё соответствует текущему `main`. В `production` повторяются проверки сертификата, файла, SHA и подписи манифеста. GitHub Release сначала создаётся **скрытым черновиком** с пятью файлами: `lunex.apk`, `lunex.aab`, `SHA256SUMS`, `update.json`, `update.json.sig`. Проверяются имена и размеры всех пяти assets; лишь затем выполняется переход в **published, not draft, not prerelease**. При ошибке загрузки остаётся скрытый черновик с пометкой «НЕПОЛНЫЙ ВЫПУСК»; автоматически публиковать или переиспользовать такой тег запрещено.

Это более надёжно, чем публиковать APK, а затем отдельно надеяться на успешную подпись манифеста. В течение проверки **публичного Release ещё нет**. На VPS ничего не копируется: отдельная часть C выполняется только по прямому поручению владельца, с атомарной доставкой пары манифест/подпись и проверкой HTTPS/Range/sha256.

**Тестовый режим:** `pipeline_test=true` использует `ci-test`, генерирует одноразовые Android и RSA-ключи, повторяет сборку и все доступные структурные проверки, сохраняет тестовые артефакты в CI. **Не открывает `production`, не берёт реальные приватные ключи, не создаёт GitHub Release и не делает VPS-деплой.** Для разработки этой ветки push запускает только тестовый режим с автоматически выбранным ещё не занятым номером версии. Тестовая сборка не является обновлением для игроков.

**Проверка результата:** в одном GitHub Actions run должны быть зелёными `preflight`, `candidate`, `manifest`, `publish`. В GitHub Releases найдите ровно пять assets выше, проверьте статус Published (без Draft/Pre-release), номер `v0.1.N` и правильный SHA. В рабочем клиенте проверка обновлений будет возможна только после отдельной публикации файлов на `rikagro.ru` (часть C).

**Откат:** старый выпуск и APK не удаляются. Если обнаружен дефект, подготовить новую исправленную `0.1.(N+1)` с более высоким versionCode и выпустить через тот же workflow. Нельзя заменять asset старого релиза или переиспользовать старый versionCode. При неуспешном запуске без Published Release расследовать проблему и скрытый draft, но не превращать его в публичный релиз вручную.

## Подпись манифеста в GitHub Actions: безопасность V2-A4

Окружения **`android-signing`**, **`manifest-signing`**, **`production`** настраиваются отдельным утверждённым серверным скриптом: **без Required reviewers**, все ограничены deployment branch policy **только `main`**. Это условие запуска боевого режима, не изменение самого workflow. Наличие ключа в GitHub не означает, что политики окружений уже проверены. Важно защитить `main` от произвольной записи и изменения workflows (branch protection и обязательные проверки CI). Ручного подтверждения каждой подписи или выпуска нет.

- APK-ключ хранится только в GitHub Environment Secrets окружения `android-signing`; его публичный отпечаток сверяется с `ops/release_cert_sha256.txt`. Ключ манифестов **другой**, хранится только в секрете `MANIFEST_SIGNING_KEY` окружения `manifest-signing`. Публичный ключ закреплён в `client/config/update_public.pem`. Пароли и PEM в логи, issue или git не писать.
- Временные приватные ключи создаются на runner с правами `0600` (`umask 077`) и удаляются после выполнения. `set -x` запрещён; `id-token` не требуется. `contents: write` разрешён только задаче публикации, остальные работают с `contents: read`.
- В режиме `pipeline_test=true` реальные секреты не используются; публикация заблокирована независимо от входных параметров и выполненных тестов.
- Без успешной проверки APK и RSA-подписи черновик GitHub Release не переводится в опубликованный. Скрытые черновики после сбоя должны разбирать владельцы; автоматическая публикация из них запрещена.
- Смена ключа манифестов требует нового закреплённого публичного ключа в Android-клиенте; потеря ключа APK может лишить пользователей возможности обновляться. У владельца должна быть резервная копия секретов в доверенном хранилище вне GitHub. Не пересоздавать ключи ради тестов.
- На GitHub Release и на сайт нельзя выкладывать тестовый APK из `android-build.yml`, `ci-test` или артефакт `TEST-NOT-FOR-RELEASE`. Старые ручные workflow не предназначены для `v0.1.N`-публикаций.

После публикации проверить на реальном Android: установку релизной `0.1.0`, переход на `0.1.1`, сохранение данных, отклонение неподписанного или изменённого манифеста, SHA-256 скачанного APK, resumable Range-загрузку и системное подтверждение установки.
