# Архитектура LunexEconom V2 (V2-00)

## Приоритет решений и зоны

**Это новый проект по прямому заданию владельца V2-00.** Архивные `docs/AI_RULES.md` и `docs/spec/` сохранены побайтово, как предписано. Часть устаревших правил `AI_RULES.md` (ветки исполнителей, SQLite, защита старого мира в одном runtime) не применима к V2-00, поскольку владелец прямо распорядился создать orphan `main`, использовать только PostgreSQL и не переносить V1. Приоритет: явное решение владельца V2-00, утверждённые ADR-001/002, затем совместимые пункты архивных правил. Изменение утверждённых ADR требует решения владельца.

В дальнейшем каждый исполнитель владеет пакетом `server/<module>/`, своим SQL в `server/migrations/`, `server/tests/` с префиксом модуля и документацией `docs/<MODULE>.md`. `server/game_server.py`, `server/registry.py`, `server/db.py`, `server/platform/`, CI и `ops/` являются общими контрактами: любые изменения согласовывать с директором, не переписывать чужие части. `client/`, `web/`, `docs/spec/` назначаются отдельным исполнителям. Утверждённые спецификации не редактировать в рамках реализации.

## Инварианты

1. **PostgreSQL 16** во всех окружениях, в тестах изолированный экземпляр. SQLite запрещён. Python 3.12+. Независимый PostgreSQL V2, никакого соединения с V1.
2. Точка входа `server/game_server.py` только собирает `Registry` и HTTP-runtime. Пакеты регистрируют маршруты, миграции, тики и флаги через `register(registry)`/`migrations()`; прямые правки чужого модуля недопустимы.
3. Схемы SQL: `server/migrations/YYYYMMDDHHMM_module_description.sql`. Лексикографический порядок; контрольные суммы SHA-256 в `schema_migrations`. Несовпадающая миграция запрещает запуск. Для изменения ранее применённой схемы только новая миграция. Миграции исполняются под PostgreSQL advisory lock.
4. Каталог товаров, рецептов и зданий: только `server/data/*.json`, JSON Schema, API `/catalog`. Дополнение данных без дублирования на клиенте.
5. Деньги: `bigint` (целые игровые рубли), двухсторонние записи из одной атомарной транзакции, ключ `request_id` уникален. Баланс = сумма всех записей. Нельзя генерировать деньги переводом или повтором запроса. Учёт внешних источников/стоков через системные ledger-счета.
6. Время: ADR-001 `docs/spec/TIME_MODEL.md`. 24 реальных часа = игровой месяц, 30 игровых дней по 48 минут. Месячная граница **09:00 в Уфе** (04:00 UTC); денежные расчёты один раз на `month_index`. Суточные обработчики по `day_index`. При догоне применяется идемпотентный `tick_receipts` и единая транзакция. Старт нового мира пока требует настройки `epoch` на ближайшие 09:00.
7. Флаги по уровням: значение из registry → окружение `LUNEX_FLAG_*` → PostgreSQL `runtime_config`. Публичный конфиг: `schema`, `revision`, `payload_b64`, `signature`; RSA PKCS#1 v1.5 SHA-256 и канонический JSON `sort_keys=True`, compact separators, UTF-8, как архивный `docs/LIVE_CONFIG.md` (не переносится). До первой подписи GET `/config` = 503; неподписанный конфиг клиенту не принимается. Подписант и клиентский verifier будут реализованы в отдельной задаче до production.
8. `server/auth.py` и `server/game_server.py` сохраняются как entrypoint-контракты. `ops/update_server.py` разворачивает вложенные пакеты, каталоги JSON и SQL и не включает тесты; проверяет `server-check.yml` для SHA, делает бэкап, рестарт, `/health`, откат. Старый сервис никогда не является целью по умолчанию.
9. Контент и графика оригинальные, без воспроизведения чужих ресурсов. Android-only, ландшафтная ориентация и safe area, UI Forest Glass. Сервер авторитетен, конфигурация Android-клиента не заменяет серверную проверку прав.

## API первой фазы

- `GET /health` → `{ok, database, version, sha}` (503 при недоступной БД).
- `POST /auth/register` `{username,password}` → HTTP 201 и профиль без токена; одинаковый публичный `role=player`.
- `POST /auth/login` → токен с истечением через 30 дней; scrypt с индивидуальной солью, в PostgreSQL только SHA-256 токена.
- `GET /auth/me` заголовок `Authorization: Bearer <token>` → роль и профиль.
- `GET /catalog` → общие JSON-каталоги (пока пустые).
- `GET /config` → 503 до первой подписанной ревизии.

Роли `developer` и `admin` технически предусмотрены колонкой БД, но выдаются только доверенным администратором в будущем; нельзя получить их публичной регистрацией.

## Известные границы V2-00

Нет запуска тиков фоновой службой (только реестр/функция и таблица), нет бухгалтерской сверки для первоначальных остатков, миграционного CLI, боевой защиты от перебора паролей, публичного подписи-контроллера конфигурации и клиентского криптографического verifier. WSGI на `wsgiref` служит только для каркаса. До production требуется сервер приложений, ограничения запросов, токен-ротация и отдельный аудит. Полноценная экономика, города и ресурсы являются следующими фазами. README и CI должны честно отличать каркас от production.
