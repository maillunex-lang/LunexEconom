## Бюджет кадра и первой картинки

Файл `budgets.json`, объект `time` и `render`.

Первая картинка не включает сеть в критический путь:

| Ключ | мс |
|---|---:|
| `first_picture_warm_cache_ms` | 150 |
| `first_picture_cold_local_terrain_ms` | 300 |
| `first_picture_hq_network_budget_ms` | 800 |

Порядок строго такой: тёплый кеш быстрее голой земли, голая земля быстрее ответа сети. Валидатор отвергает другую расстановку.

Почему 300 мс на голую землю: 9 чанков × 144 клетки — целочисленный шум и одна заливка текстуры 12×12 на чанк. Это не сцена из сотен `MeshInstance`. 800 мс на штабной чанк — один проход до API, не десять.

| `max_draw_calls` | 80 |
| `max_triangles_per_frame` | 80000 |
| `max_texture_memory_bytes` | 50331648 |
| `max_building_triangles_lod0` / `lod1` / `lod2` | 400 / 120 / 24 |
| `max_building_glb_bytes` | 81920 |
| `max_visible_objects` | 250 |
| `max_building_nodes` | 120 |
| `max_model_pack_bytes` | 8388608 |
| `shadow_map_px` | 1024 |
| `object_pool_size` | 128 |
| `lod0_cells` / `lod1_cells` / `lod2_cells` | 8 / 24 / 48 |
| `camera_pitch_deg` / `camera_fov_deg` | 55 / 40 |
| `camera_min_height_m` / `camera_max_height_m` | 40 / 800 |
| Высоты стадий, см | 100, 400, 700, 900, 900 |

80 вызовов: до ~25 чанков земли одним MultiMesh, один MultiMesh дорог, один MultiMesh коробок, до 120 ближних моделей, UI отдельно и в бюджет мира не входит. 80000 треугольников при 30 кадрах — запас для Compatibility на среднем Mali/Adreno, не для флагмана. Если замер на телефоне ниже 24, сначала выключаются тени, потом узлы дальше `lod1_cells`.

Пакет 8 МиБ: 42 здания × 80 КиБ = 3440640 байт, если у каждого один GLB. Четыре файла на стадии в этот потолок не влезают (около 13 МиБ). Поэтому стадии по умолчанию не отдельные файлы.

## Трафик

Файл `budgets.json`, объект `traffic`. Валидатор пересчитывает формулы и падает, если записанное число разъехалось.

Допущения верхней оценки:

- Карта открыта у каждого онлайн-игрока весь час. Это хуже ярмарки, не прогноз дня.
- События мира в час: 360, 7200 и 36000. Это 6 в минуту, 2 в секунду и 10 в секунду. Не замер продакшена, а потолок, под который считаем канал.
- Доля событий, попавших в видимую область: 500‰, 500‰ и 200‰. На старте почти все строят в одной Уфе, поэтому половине слушателей событие интересно. При 5000 онлайн города расходятся, доля 200‰.
- Тело события в оценке 480 байт (примеры живого протокола меньше; потолок тела 2048).
- Пустой ответ в оценке 128 байт. Тиков пустого ответа 144 в час = 3600 / 25 с, если игрок всё время висит на длинном опросе и событий ему не пришло. В верхней сумме пустые ответы **прибавляются** к событиям, даже если частый событиями канал пустых ответов не шлёт. Так цифра завышена нарочно.

Формулы, целочисленное деление:

```text
relevant = world_events_per_hour * viewport_share_permille / 1000
client_bytes_per_hour = relevant * assumed_event_bytes
                      + idle_responses_per_hour * assumed_idle_bytes
server_responses_per_hour = online * (relevant + idle_responses_per_hour)
websocket_db_queries_per_hour = world_events_per_hour
```

| Онлайн | События мира / ч | Видимые игроку / ч | Байт на клиента / ч | Ответы сервера / ч | Запросы БД / ч при WebSocket |
|---:|---:|---:|---:|---:|---:|
| 50 | 360 | 180 | 104832 | 16200 | 360 |
| 500 | 7200 | 3600 | 1746432 | 1872000 | 7200 |
| 5000 | 36000 | 7200 | 3474432 | 36720000 | 36000 |

Проверка первой строки: `360 * 500 / 1000 = 180`. Байты: `180 * 480 + 144 * 128 = 86400 + 18432 = 104832`. Ответы: `50 * (180 + 144) = 16200`.

Вывод, который нельзя потерять при реализации:

- 50 человек: около 100 КиБ в час на клиента и 4–5 ответов в секунду на весь сервер. Длинный опрос с потолком 64 это переживает.
- 500 человек: верхняя оценка около 1,7 МиБ в час на клиента и около 520 ответов в секунду, если каждый висит в длинном опросе. На синхронном Waitress так нельзя: 500 висящих потоков по стеку 8 МиБ — это гигабайты. Поэтому сверх 64 ожидающих клиент падает в короткий опрос, а цель 500 слушателей в нагрузочном тесте — про задержку доставки, не про 500 спящих потоков на боевом процессе.
- 5000 человек: десятки миллионов HTTP-ответов в час. Имеет смысл только WebSocket (или другой один приёмник), тогда чтение журнала остаётся 10 запросами в секунду, по числу событий, а не по числу игроков.
- База на длинном опросе читает журнал так же часто, как отвечает. Индекс — первичный ключ `version` плюс `(cx, cy, version)` для фильтра. Полный разбор `jsonb` на каждой проверке «интересен ли чанк» при 500 запросах в секунду не закладывать.

## Примеры событий

Восемь тел в `examples.json`, номера 501…508, строго по возрастанию, `event_id == version`. Каталожный id `bakery` есть в `server/data/buildings.json`, след 2×2.

| id | type | kind | Зачем в наборе |
|---:|---|---|---|
| 501 | `building_added` | `enterprise_construction` | Поставить пекарню, стадия 0, четыре клетки |
| 502 | `building_stage_changed` | `enterprise_stage` | Та же пекарня, стадия 1, тот же узел |
| 503 | `road_added` | `road_build` | Три клетки подъезда |
| 504 | `parcel_owner_changed` | `land_buy` | Участок (1, 0), владелец `17` |
| 505 | `city_growth` | `city_growth` | Уровень 1→2, радиус 12→15, чанки обрезаны |
| 506 | `terrain_edit` | `terrain_edit` | Одна клетка `ground`. В журнал не писать до клиента этапа 1 |
| 507 | `road_removed` | `road_build` | `removed: true`, клетка (8, 8) |
| 508 | `building_removed` | `demolition` | Снять пекарню |

Последовательности того же файла:

| id | Ожидание |
|---|---|
| `build_stage_road_remove` | применяется целиком |
| `remove_missing_building` | отказ `missing_object` |
| `replay_same_event` | второй 501 игнорируется, итог успешный |
| `out_of_order` | отказ `out_of_order` |
| `remove_missing_road` | отказ `missing_road` |

Догонка (`catchup` в том же файле, порог дыры 5000): сплошная страница применяется; дыра, закрытая `scanned`, применяется; дыра без `scanned` — снова запрос; `tip - last > 5000` и флаг `reset` — снимок области; повтор уже виденного id — игнор; пустая страница при `scanned == tip` — сдвиг курсора; номера задом наперёд — протокольная ошибка.

## Что валидатор не доказывает

Он не ходит в PostgreSQL и не рисует кадр. Он ловит только расхождение предложения с собственными формулами и схемой. Замер 150/300/800 мс и 30 кадров делается на телефоне заданием реализации, не этой веткой.
