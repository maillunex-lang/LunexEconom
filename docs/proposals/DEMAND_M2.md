# Спрос M2: районы Уфы и четыре слоя дохода

Черновик чисел для модуля 07. Считает эталонный симулятор `tools/sim`, не сервер. Все числа целые, деление вниз. Балансовые доли помечены `balance: draft` и лежат в `tools/sim/data/districts_ufa.json`. Сервер, клиент и `docs/gdd/**` не менялись. Золотые `tools/sim/golden/m1_*.json` не менялись.

Утверждено и принято как есть: D-01 (четыре слоя), D-02 (спрос по районам), D-04 (`system:market`), D-18 (НДС 1000 bp внутри цены).

## Как воспроизвести

Из корня репозитория:

```
python -m tools.sim run tools/sim/scenarios/m2_two_districts.json
python -m tools.sim run tools/sim/scenarios/m2_competition.json
python -m tools.sim run tools/sim/scenarios/m2_income_layers.json
python -m tools.sim golden
python -m unittest discover -s tools/tests -p "test_sim*"
```

`run` печатает продажи и выручку игрока. Районы, слои и доли магазинов лежат в золотом JSON, поле `days[].demand`. Таблицы ниже сняты оттуда. Проверка:

```
python -c "import json; d=json.load(open('tools/sim/golden/m2_two_districts.json'))['days'][0]['demand'][0]; print(d['population'], d['demand'], d['remainder']);
[print(x['id'], x['population'], x['demand'], x['sold'], x['revenue'], x['unmet']) for x in d['districts']]"
```

Чувствительность среднего слоя центра (население 207000, доля 400 ‰, индекс дохода 1000, эталон 90, R в строке) — та же `demand_units`, что пример 07:

```
python -c "from tools.sim.demand import sensitivity_rows
for row in sensitivity_rows(207000, 2, 400, 1000, 90, 1, [72, 90, 99, 120, 180, 270], [0, 50, 70, 100]):
    print(row['price'], row['rating'], row['demand'])"
python -c "from tools.sim.formulas import demand_units; print(demand_units(207000, 2, 400, 1000, 720, 90, 1, 70, 1000))"
```

Ожидаемая якорная клетка: цена 90, R 70 → 150696. Это средний слой Белой набережной в `m2_two_districts`.

## Город

Суточный спрос города **2 074 555** штук. Остаток переноса между районами **0**: 1 150 000 делится на доли промилле без остатка, а смеси слоёв у районов разные, поэтому общий спрос равен сумме районных, а не одной формуле на весь город.

Для сравнения, один слой на весь город с индексом 1000 (режим M1) даёт **2 093 000**. Четыре слоя с черновыми индексами дают на 18 445 штук меньше: бедных много, их множитель дохода 840, а не 1000.

Пекарня выпускает 100 хлебов в сутки. Самый маленький район, Вокзальный круг, просит 42 193. Спрос ни один район не ограничивает. Ограничение цепочки по-прежнему рецепт, не население. Это тот же вывод, что в `BALANCE_M1.md`, только теперь он виден по районам.

## Чувствительность цены и R

Средний слой Белой набережной, 207 000 жителей, доля 400 ‰, индекс 1000. Это ровно пример 07, поэтому цена 90 и R 70 обязаны давать 150 696.

| Цена | R 0 | R 50 | R 70 | R 100 |
|---:|---:|---:|---:|---:|
| 72 | 118 238 | 143 575 | 153 709 | 168 912 |
| 90 | 115 920 | 140 760 | 150 696 | 165 600 |
| 99 | 114 760 | 139 352 | 149 189 | 163 944 |
| 120 | 112 094 | 136 114 | 145 723 | 160 135 |
| 180 | 104 328 | 126 684 | 135 626 | 149 040 |
| 270 | 92 736 | 112 608 | 120 556 | 132 480 |
| 720 |  |  | 45 208 |  |

Пустые клетки 720 не печатались в сетке R 0/50/100; R 70 посчитан отдельно той же функцией (`price_sens` упирается в 300).

Что видно по формуле, а не по вкусу:

- Цена +10% (90 → 99): `price_delta_bp` = 1000, `price_sens` = 990, спрос 149 189 = 150 696 × 990 // 1000. Минус 1%, как пример 2 в 07.
- Цена ×3 (270): `price_delta_bp` = 20 000, `price_sens` = 800, спрос 120 556. Это не 300. До пола 300 формула доходит при цене 720 (×8), `delta_bp` = 70 000.
- R 70 → 100 на эталонной цене: 150 696 → 165 600, плюс 14 904. R 70 → 0: 115 920. Рейтинг двигает спрос сильнее, чем +10% цены, и слабее, чем смена слоя с низкого на премиум.
- Цена 72 (ниже эталона) чуть поднимает спрос (153 709), потому что P в рейтинге уже упёрт в 100 и дальше дешевизна рейтинг не растит. Растёт только `price_sens` (1020).

## Что поправить в формулах 07

Симулятор следует формуле блока «Правила» и примеру +10%. Где текст 07 сам себе противоречит, в список правок, а не в код.

1. Приёмка, пункт 3: «цена ×3 → price_sens = 300». По формуле ×3 даёт 800. Пол 300 — это ×8 (720 ₽ при эталоне 90). Либо менять пункт приёмки, либо убирать `// 100` из формулы. Второе сломает пример +10% (там как раз выходит 990). Править пункт приёмки.
2. Корзина еды падает от низкого к премиум (550 → 150 ‰), а `income_factor` при любом индексе выше 1000 растит штуки хлеба. Это два разных смысла «богатый ест иначе». Сейчас штуки хлеба считает только индекс. Корзина записана и не применяется. Нужно одно правило: либо корзина умножает `base`, либо индекс, не оба сразу и не текст против текста.
3. Пример «если факторы равны, центр даёт 376 740» верен только при общем множителе. С разными индексами центр даёт 397 836. В текст 07 стоит дописать, что 376 740 — это не прогноз четырёх разных слоёв.
4. Трафик есть у района и нет в формуле спроса. Он входит только в A. Общий трафик района почти сокращается при дележе двух магазинов и никак не сокращается при одном: одинокий магазин берёт весь спрос. Если трафик должен менять штуки, формуле 07 нужна отдельная строка. Если нет — убрать ожидание, что «вокзал продаёт больше жилого при том же населении».
5. Запись A в `docs/sim.md` для M1 режет множители по шагам: `(1000 + traffic*10) // 1000`, затем `appeal // 1000`. Трафик ниже 100 и appeal ниже 2000 обнуляются. M2 считает одним делением на 1 000 000. При traffic 0 и appeal 1000 оба пути дают R, поэтому M1 не сдвинулся. В 07 стоит записать один вариант, иначе сервер и симулятор разъедутся на первом же ненулевом трафике.
6. Сервер `server/retail/core.py` считает город иначе: нет слоёв, нет индекса дохода, два деления подряд, всегда A², средние цена и R по весу A². Это M1-упрощение, оно само так и написано в `docs/retail.md`. В модуль 07 его копировать не нужно. Сервер в этом задании не трогался.
7. D-56 (доли районов) всё ещё открытый вопрос, хотя D-02 уже утверждён. Пока доли черновые, сервер не должен зашивать их константой.
8. Привязка районов к клеткам из 07 в симуляторе не делается: нет ратуши и радиуса в прогоне спроса. Это отдельная работа карты, не формула штук.
9. Рост `delta_pop` из 07 не на чем считать. `world_growth` на сервере поднимает уровень города шагом 10 000 и порогом 6000 bp, это не `growth_bp` из 07. Две формулы роста надо свести, прежде чем писать модуль.

## Сомнения

- Измерительный запас 5 000 000 выше склада магазина (4000) и не проходит через журнал. Иначе конкуренция не видна: оба магазина продают по 4000 и выручка одинакова. На сервере запас должен приехать поставкой.
- Район без полки оценивается как эталонная полка с R 70. Иначе первый магазин по эталону скачком менял бы спрос района. Это допущение, в 07 его нет.
- Магазин на окраине в сценарии двух районов сидит вне зон `grocery_store` (в каталоге только центр и жилой). Симулятор зоны не проверяет, как и M1. Для сервера такую посадку надо либо запретить, либо расширить зоны.
- Непроданный спрос сгорает в те же сутки. «Остаток не теряется» относится только к округлению деления, не к буханкам без магазина.
- Цена 120 почти не проигрывает цене 90 по выручке. Если владелец хочет, чтобы дорогая полка была больно, эластичности 1 и s = 2 мало. Это наблюдение, не правка: эластичность уже в каталоге.
