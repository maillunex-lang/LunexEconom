# Предложение 07. Население и спрос

**Цель:** смоделировать жителей городов, их доходы, расходы и спрос на товары так, чтобы розница из модуля 06 получала реалистичный суточный спрос, зависящий от населения, доходов, цен и качества предложения.

Все расчёты — по правилам `docs/proposals/INTEGER_MATH.md`. Никаких float. Счета не уходят в минус.

## Сущности и данные

- Город: население `pop` (целое), средний доход `income_index_‰` (промилле относительно Уфы, 1000 = ×1.0), доля занятых, качество жилья и услуг (целые 0–100).
- Район города: население района, тип (центр / жилой / окраина), трафик (0–100).
- Слой дохода: 4 слоя (низкий, средний, высокий, премиум). Доли в промилле: 350 / 400 / 200 / 50 (balance: draft).
- Потребительская корзина: набор категорий товаров из каталога. Для каждой категории — базовая доля расходов (промилле) и эластичность (целое из products.json).
- Домохозяйство (агрегат): не хранится поштучно, считается по району и слою.
- Миграция: поток людей между городами по разнице привлекательности (работа, жильё, услуги).

Данные: `city_population` (город, день, pop, layers), `district_demand` (район, товар, день, спрос), `migration_flows`.

## Правила и формулы

Суточный спрос на товар `g` в районе (целочисленный):

```
base = (pop_district * base_per_capita_g) // 1000
income_factor_‰ = 600 + (400 * income_index_layer) // 1000
price_delta_bp = ((price - ref_price) * 10000) // ref_price
price_sens_‰ = clamp(1000 - elasticity * price_delta_bp // 100, 300, 1500)
rating_factor_‰ = 700 + (300 * avg_R) // 100
ad_factor_‰ = таблица ступеней из INTEGER_MATH.md (в M2 = 1000)
demand_g = (base * income_factor_‰ * price_sens_‰ * rating_factor_‰ * ad_factor_‰) // (1000 * 1000 * 1000 * 1000)
```

Применение ad_factor всегда как умножение: промежуточный результат * ad_factor_‰ // 1000. Не деление.

Где base_per_capita_g и elasticity — из каталога (`server/data/products.json`). Для хлеба: unit = piece, base_demand_per_capita = 2, reference_price = 90.

**Пример спроса на хлеб** (район 10 000 жителей, цена = эталон 90, avg_R = 70, средний слой income_index = 1000):
- base = (10000 * 2) // 1000 = 20
- income_factor_‰ = 600 + (400 * 1000) // 1000 = 1000
- price_delta_bp = 0
- price_sens_‰ = 1000
- rating_factor_‰ = 700 + (300 * 70) // 100 = 910
- ad_factor_‰ = 1000
- demand = (20 * 1000 * 1000 * 910 * 1000) // 1_000_000_000_000 = 18 200 штук в сутки

Арифметика проверена вручную дважды. При цене 110 % эталона price_sens_‰ падает, спрос снижается.

Рост населения (в день, целочисленный):
```
delta_pop = (pop * growth_bp) // 1_000_000
growth_bp = housing_quality * 1 + jobs_ratio_‰ // 100 - unemp_‰ // 50
```
growth_bp измеряется в миллионных долях в сутки (1 000 000 = +100 % в сутки), поэтому типичный рост составляет десятки единиц (balance: draft).

**Пример роста** (housing_quality = 80, jobs_ratio_‰ = 600, unemp_‰ = 100, pop = 1 000 000):
- growth_bp = 80*1 + 600//100 - 100//50 = 80 + 6 - 2 = 84
- delta_pop = (1 000 000 * 84) // 1 000 000 = 84 человека в сутки (0,0084 % в сутки)
- За 30 суток: 84 * 30 = 2 520 человек, то есть около 0,25 % за игровой месяц (без дробей).
- Проверка: при pop = 1 000 000 и growth_bp = 84 получаем 84, значит прирост за месяц не превышает 0,3 %.

Занятость: рабочие места = сумма `jobs` по предприятиям из buildings.json. Зарплата = базовая_Уфа * city_wage_index_‰ // 1000 * skill_factor_‰ // 1000 (из 10).

Миграция: 5 ‰ населения в день рассматривает переезд. Вероятность в город B = attractiveness_B * 1000 // sum_attractiveness (целое деление).

## Что считается в суточном тике и что в месячном

**Суточный тик** (после `retail` или перед ним):
1. Обновить население по росту/убыли (целочисленно).
2. Посчитать спрос по районам и товарам (целочисленно).
3. Передать спрос в розницу (модуль 06 использует его вместо упрощённой модели M1).
4. Обновить занятость и средние зарплаты.

**Месячный шаг:**
- Сводка доходов и расходов населения.
- Пересчёт индексов привлекательности городов.
- Миграция (агрегат за месяц).

## Проводки ledger

Население не имеет счетов. Выручка магазинов идёт от `system:market` на компанию (как в 06). Зарплаты — в месячном шаге из `company:<id>` на `system:labor`.

Пример: продажа хлеба на 10 000 ₽ → `{company: +10000, system:market: -10000}`. request_id = `sale:<enterprise>:<day>:<good>`.

Никаких проводок, уводящих счёт в минус.

## API

- `GET /cities/{id}/population` — pop, layers, employment.
- `GET /cities/{id}/demand?day` — спрос по товарам (штуки/кг по unit каталога).
- `GET /world/migration` — потоки.
- `POST /admin/population/adjust` (только админ) — для тестов.

## Что показывает клиент

В штабе и на карте города: население, средний доход, занятость, «спрос на хлеб сегодня», подсказки «почему продажи низкие» (дорого / низкий рейтинг / мало населения).

## Приёмка

1. Район 10000 жителей, цена=90, R=70 → спрос хлеба = 18200 штук.
2. Цена=99 (+10 %), elasticity=1 → price_sens_‰=990, спрос ниже.
3. Рост: pop=1000000, growth_bp=3500 → delta=3500 в день.
4. Население района 0 → спрос 0.
5. Цена в 3 раза выше → price_sens_‰ = 300 (минимум).
6. Два магазина делят спрос пропорционально привлекательности (как в 06).
7. Все деньги через ledger, сумма проводок = 0.
8. В M1 упрощённая модель заменяется этой без поломки розницы.

## Открытые вопросы к директору

1. Сколько слоёв дохода — 3 или 4? Рекомендация: 4. Последствие: более глубокий спрос.
2. Спрос по районам или городу? Рекомендация: по районам. Последствие: локальная конкуренция.
3. Миграция суточная или месячная? Рекомендация: суточная с малым коэффициентом. Последствие: плавнее изменение.
4. Счёт `city:households` или `system:market`? Рекомендация: `system:market`. Последствие: проще леджер.
5. Влияние рекламы в M2? Рекомендация: ad_factor_‰ = 1000 до M3. Последствие: нет лишнего.
6. Базовый рост населения? Рекомендация: через growth_bp. Последствие: прозрачный баланс.
7. Моделировать безработицу? Рекомендация: да, снижает income_factor. Последствие: реалистичнее.
8. Экспорт/импорт населения? Рекомендация: нет в M2. Последствие: проще.

Город A attractiveness = 1200, B = 800. Из 1000 рассматривающих: 600 в A, 400 в B (целое деление).

Рабочие места = sum(jobs). Зарплата в Уфе ≈ 1480 игр. ₽/мес (из 74 000 реальных / 50).

- Население района 0 → спрос 0.
