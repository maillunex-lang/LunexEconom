# CITY_OBJECTS_DATA. Проверяемые данные и расчёты

**Задание:** V2-CITY-DESIGN. **Статус:** balance: draft; без правок сервера, клиента и рабочего VPS. Все показанные здания виртуальные, координаты синтетические, цены игровые.

## Источники и файлы

- tools/sim/data/city_objects_proposed/catalog.json: 22 типа городских объектов; уникальные id, русские названия, 2D footprint, уровни, зоны, услуги 14, сигнал трафика и комфорта, земля bp, стоимость, ежемесячное содержание, model_id, заглушка.
- tools/sim/data/city_objects_proposed/rules.json: версия city-objects-v1, соль шума, число попыток, лимиты, задержка раскрытия, ограничения цен.
- tools/sim/data/city_objects_proposed/districts_ufa.json: 6 районов Уфы из M2, все исходные экономические поля сохранены, добавлен художественный сектор для UI.
- tools/sim/data/city_objects_proposed/examples.json: Уфа, Стерлитамак, Салават; каждый на L1, L2, L3; для каждого уровня полный список объектных id, типы, footprint, координаты, district_id, model_id и SHA256.
- tools/validate_city_objects_proposal.py: чистый воспроизводимый генератор и проверка. Действующий server/world/generator.py загружается только на чтение, world/core.py не импортируется из-за БД-зависимостей; его дорожные формулы воспроизведены и сверены.
- tools/tests/test_city_objects_proposal.py: положительные и негативные тесты.

Проверка: (2*15+1)^2 - (2*12+1)^2 = 31²−25² = 961−625 = 336. Следующее кольцо 39²−31²=560. Одна клетка 20×20 м = 400 м². Школа 2×2 = 40×40 м = 1600 м² в сжатой игровой геометрии. Муниципальный объект не добавляет игроку автоматически население/выпуск/налог. Остановки и небольшие станции имеют меньший footprint, мост и набережная допускаются только в ручной проект при подтверждённых условиях берега и воды.

## Детерминированные эталоны

Сид мира 20261115. Для каждого из трёх городов результаты имеют два вида: полный массив объектов и sha256, записанные в examples.json. Для генерации используется world-v1 SplitMix64, интерпретация любых отрицательных x/y через маску 64 бит. Пример объектов на координатах Уфы доступен из JSON без утверждения реального расположения. Установлен порядок кольцо → слот → попытка, каталог не сортируется по имени, чтобы не менять эталон при переводе имён на другие языки.

Для начала расчёта: радиус L1 = 12; первая итерация выбирает один псевдослучайный вариант из 64×7 попыток на кольцо, затем отбрасывает неподходящую зону, занятую клетку, воду и дорожный каркас. Результат у чистой пары (city, seed, level) фиксирован. Уровень L2 добавляет только кольцо 13..15, L3 добавляет 16..19. При блокировке отдельной клетки canonical placements не пересчитываются заново: исключается только затронутая геометрия, а не «переезжает» соседний объект. Авторитетное подтверждение размещения затем хранится в overrides на сервере. Все числа и координаты проверяются валидатором и отрицательным тестом.

## Экономика города, земля (все числа balance: draft)

| Пример | Выражение целыми | Проверенный результат |
|---|---|---:|
| Налог города, 100000 прибыли, 500 bp | 100000*500//10000 | 5000 |
| Налог государства, 1500 bp | 100000*1500//10000 | 15000 |
| Базовая жилземля Уфы, участок 6×6 | ceil(15000*10000*10000 / 100000000) | 15000 |
| Школа, вклад в цену земли 40 bp, радиус 7, d=2 | 40*(7+1-2)//(7+1) | 30 bp |
| Земля со школой на d=2 | 15000*(10000+30)//10000 | 15045 |
| Земля со школой и ещё 100 bp | 15000*(10000+130)//10000 | 15195 |
| Положительный потолок +1500 bp | 15000*11500//10000 | 17250 |
| Отрицательный пол -800 bp | 15000*9200//10000 | 13800 |
| Строительство школы (каталог) | build_cost_rub | 90000 |
| Аналитическое содержание школы в месяц | monthly_upkeep_rub | 2200 |

Проверка другим способом для школы: 40*6=240; 240//8=30; 15000*10030=150450000; //10000 = 15045. В базовом мире земля 6×6 продаётся как участок, не как 36 отдельных клеток. Сумма bp складывается и ограничивается [-800,+1500], затем применяются обычные правила мирового land index и зон. Пример при прибыли 100000 показывает, что 500 bp городского налога не заменяют 1500 bp федерального. Нельзя считать заведение школы отдельной проводкой налоговой выручки. Нельзя второй раз списывать upkeep поверх уже оплаченной услуги city_services из проекта 14.

Целочисленная модель предотвращает float-дрейф. Реальный баланс и влияние на NPC-спрос и аренду не утверждены. Удобство объекта, demand_signal и traffic_points передаются в future preview, не изменяют M2 сегодня.

## Адаптер GDD22 и граница GDD23 после слияния нового main

Контракт GDD22: событие building_added/occupation либо building_removed/demolition с object_id из пространства city:..., catalog_id=model_id, owner_ref=city:<id>, stage_index=4, x/y/w/h, color_rgb. В отличие от прежнего проекта, признак city_object=true положен в **payload**, не в дополнительное поле закрытой GDD22 схемы object. payload дополнительно содержит cells, district_id, catalog_namespace=city_objects. Длина сериализованного события не больше 2048 байт, ссылка на 1–16 чанков. В tools/tests/test_city_objects_proposal.py есть проверка полного required-набора и разрешённых полей текущей schema. В runtime регистрация нового catalog_namespace и подписанного пакета ещё не реализована.

Для 3D из GDD22 установлен бюджет: модель ≤30 м высотой, ≤400 треугольников, ≤80 КиБ, один материал/атлас, файл buildings/<catalog_id>.glb, пакет map_models ≤8 МиБ. Для дальних инстансов LOD1 ≤120 треугольников, BoxMesh ≤24, дальше не загружать. Все размеры, стили и целые fallback color_rgb записаны в каталоге. Метрики 30 FPS/80 draw calls остаются задачей реального Android профиля, не доказаны этими тестами.

В GDD23 настоящая недвижимость имеет properties, leasable_units, leases, арендные платежи и лимиты компаний. Наши housing_block, office_block и shopping_center пока только муниципальный визуальный слой. Нельзя создавать из этих объектов бесплатные квартиры, арендуемый м², налоги или продажи: договоры появляются только после отдельного согласованного property-проекта и записи в ledger.

## Ограничения, проверяемые факты и честность вывода

Скрипт должен проверить: все числа integer, 22 уникальных типа, ссылки услуг transport/education/health, шесть точных районов M2 с суммой 1000‰, верные радиусы, два идентичных прогона, снапшоты всех 9 наборов, сохранение старых колец, отсутствие пересечения друг с другом, с водой, кольцевыми/осевыми дорогами и межгородским MST, наличие объекта внутри радиуса, лимит 120/город, 18/чанк, 80 клеток footprint/чанк. Для случая частной занятости обеспечивается параметр occupied/reserved с фильтрацией без перестановки других кандидатов.

**Не проверено в данном задании:** живые world_occupied_cells, world_roads SQL, купленные 6×6 участки, правки рельефа, SQL-транзакции, реальный расход городского бюджета, конкурирующие тендеры, Godot-рендер и FPS. Это обязательные будущие интеграционные проверки, а не основания объявлять работающий город.

Команды в корне репозитория:

    python tools/validate_city_objects_proposal.py
    python -m unittest tools.tests.test_city_objects_proposal

На VPS может отсутствовать команда python, тогда эквивалентные проверки выполняются через python3 (без установки пакетов).

## Решения для владельца

1. Временные кварталы вместо реальных муниципальных районов: **рекомендация да** для альфы с ясной маркировкой.
2. Не считать муниципальные объекты в пороге роста: **рекомендация да**.
3. Содержание объектов считать частью уже оплаченных услуг 14: **рекомендация да**, не списывать дважды.
4. Отдельные госзаказы с публикацией за 7 игровых суток и публичным резервом: **рекомендация да**.
5. Городские торговые и жилые кварталы считать декорацией до GDD23: **рекомендация да**.
6. Мост и набережную включать только как утверждённый городской объект после спецпроверки геометрии: **рекомендация да**.
7. Отложить финальные GLB/LOD-бюджеты до согласования GDD22: **рекомендация да**.
