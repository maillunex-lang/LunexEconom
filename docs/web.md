# Статический лендинг V2, Forest Glass

Ветка разработки: `v2/landing`. Лендинг полностью автономен, только на русском языке, без cookies, CDN, внешних шрифтов и трекеров. Никакого подключения к игровым сервисам. Страница рассчитана на размещение **внутри** `https://rikagro.ru/lunexeconom/`, а не в корне `rikagro.ru`. `web/roadmap.json` и `docs/content/**` принадлежат директору; в этой задаче не изменялись.

## Файлы и размещение

Каталог `web/` содержит `index.html`, `styles.css`, `config.js`, `site.js`, `roadmap.json`. Отдельные файлы `update.json` и `update.json.sig` предоставляет владелец после создания **подписанного** выпуска. Информационный `latest.json` в репозиторий не кладётся и скриптом публикации сайта не копируется: его атомарно пишет отдельный серверный скрипт. Пример формата лежит только в `web/tests/fixtures/latest.example.json` и на сайт не публикуется. APK располагается по URL из описания сборки, для V2 обычно `https://rikagro.ru/lunexeconom/v2/download/lunex-0.1.0.apk`; в исходных файлах web/ **нет** APK, нет фиктивного `update.json` и нет боевого `latest.json`.

Владелец отдельно разворачивает статику из архива на целевой сервер только в **части C**, после явной команды. В рабочем дереве развертывания нужно расположить файлы `web/*` в директории, которую будущий согласованный серверный конфиг уже сопоставит `/lunexeconom/v2/`. Ни SSH, ни nginx, ни systemd не настраиваются этой задачей. Пути в HTML, JavaScript и CSS относительны (`./roadmap.json`, `./latest.json`, `./update.json`, `./styles.css`); адрес базовой папки изменяется только в `web/config.js` (на сервере публикация подменяет его на `https://rikagro.ru/lunexeconom/v2`). Рекомендуется проверить доступность страницы с завершающим `/`, чтобы браузер верно разрешал относительные пути. `Cache-Control: no-store` нужен и для `latest.json`, и для подписанного `update.json`.

**Ручная проверка:** `python3 -m http.server 8080 --directory web`, открыть `http://localhost:8080/`. Чтобы воспроизвести реальную подпапку, использовать тестовый сервер в `web/tests/smoke.cjs`. CI строит снимки при 360×800 и 1440×900 в светлой и тёмной темах.

## Последняя проверенная сборка (`latest.json`)

`latest.json` — отдельный **неподписанный** информационный файл для лендинга. Подписанный `update.json` по-прежнему нужен только игре и подписывается владельцем. Сайт не проверяет RSA и не считает JSON доказательством подлинности APK: он показывает версию, дату, размер и SHA-256, чтобы человек мог сверить файл. Неудачная сборка **не должна затирать** уже опубликованный `latest.json`. Поле `previous` дополнительно оставляет прямую ссылку на прошлый APK, если новая проверенная сборка уже опубликована, но игроку нужна предыдущая.

Сайт читает файлы в таком порядке, каждый запрос с `cache: "no-store"`:

1. `./latest.json`, если ответ 200 и объект проходит проверку ниже.
2. Иначе `./update.json` по прежним правилам ссылки.
3. Иначе кнопка ведёт на `window.LUNEX_FALLBACK_RELEASE` и страница не выдумывает версию.

Неизвестные поля игнорируются. Лишнее вложенное поле внутри `previous` тоже игнорируется. Обязательный набор нельзя сокращать: нет `previous` (даже если это `null`) — файл недействителен, сайт переходит к шагу 2.

### Поля

| Поле | Где | Правило |
| --- | --- | --- |
| `schema` | только корень | целое число `1` |
| `channel` | корень и `previous` | ровно `alpha` или `test` |
| `version_name` | корень и `previous` | `MAJOR.MINOR.PATCH`, только цифры и точки, без префикса `v` |
| `version_code` | корень и `previous` | целое от 1 до 2100000000, не строка и не дробь |
| `released` | корень и `previous` | UTC `YYYY-MM-DDTHH:MM:SSZ`, без смещения `+00:00` |
| `apk_url` | корень и `previous` | абсолютный `https`, хост как у `window.LUNEX_PUBLIC_BASE` в `web/config.js`, путь строго внутри каталога этой базы, окончание `.apk`, без логина, пароля, query, fragment и `..` |
| `size` | корень и `previous` | целое число байт, `1…536870912` |
| `sha256` | корень и `previous` | ровно 64 шестнадцатеричных символа; сайт показывает строчные |
| `notes` | корень и `previous` | обычный текст на русском, 1…4000 символов, без управляющих символов; хотя бы одна буква кириллицы. Для альфы по-прежнему достаточно короткой заметки 1…300 |
| `previous` | только корень | `null` или один такой же объект сборки **без** своего `schema` и без вложенного `previous` |

Канал `alpha` — обычная проверенная альфа: кнопка «Скачать для Android». Канал `test` не оформляется как официальная игра: видна плашка «тестовая сборка, не для обычной игры» и отдельная кнопка «Скачать тестовую сборку». Отладочный APK, `ci-test` и артефакт `TEST-NOT-FOR-RELEASE` в `latest.json` не попадают вообще, ни как `alpha`, ни как `test`.

В репозитории база сейчас `https://rikagro.ru/lunexeconom`. После публикации части C она становится `https://rikagro.ru/lunexeconom/v2`, и сервер обязан подставлять `apk_url` уже внутрь этой базы. Пример, который проходит обе проверки пути: `https://rikagro.ru/lunexeconom/v2/download/lunex-0.1.0.apk`.

```json
{
  "schema": 1,
  "channel": "alpha",
  "version_name": "0.1.0",

  "released": "2026-11-15T18:00:00Z",

  "size": 74631872,
  "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "notes": "Первая публичная альфа: карта Башкортостана, штаб-квартира и проверка обновления.",
  "previous": {
```

### Что делает серверный скрипт (пишет другой исполнитель)

1. Берёт последний GitHub Release, который published, не draft и не prerelease, с APK и `SHA256SUMS`.
2. Сверяет SHA-256 скачанного APK с суммами. При любой ошибке, чужой подписи, debug-сборке или пометке `TEST-NOT-FOR-RELEASE` **не трогает** уже лежащий `latest.json`.
3. `version_name` и `version_code` берёт из APK, не вычисляет заново на глаз. `notes` — утверждённый русский текст «Что нового». `channel` для такого релиза — `alpha`.
4. `previous` заполняет восемью полями текущей сборки из прежнего валидного `latest.json` (`channel`, `version_name`, `version_code`, `released`, `apk_url`, `size`, `sha256`, `notes`). Если прежнего файла нет или он невалиден — `previous: null`. Вложенный `previous` не копировать.
5. Пишет `latest.json.new` в каталоге сайта, сбрасывает на диск и атомарно переименовывает в `latest.json`. Отдаёт с `Cache-Control: no-store`. Файл не подписывается и не заменяет `update.json`.

## Актуальный APK

Если `latest.json` недоступен или не проходит проверку, сайт выполняет `fetch("./update.json", {cache:"no-store"})`. Поля формата выпуска из `docs/release.md`: `version_name`, `size` (байты), `released` (ISO-8601), `notes`, `sha256` (64 шестнадцатеричных символа), `apk_url` (полный HTTPS URL), `version_code` и `min_version_code` (последние два нужны игре). Сайт отображает версию, дату по-русски, размер в МиБ, заметки, хеш SHA-256, ссылку на APK и до пяти записей журнала. По умолчанию журнал включает один текущий выпуск. Для будущего списка допускается необязательный `releases` или `history` с `version_name`, `released`, `notes`, но **это расширение не входит в текущую обязательную спецификацию подписанного манифеста** и требует утверждения владельца/директора и согласования с валидатором подписей клиента. Канал у подписанного манифеста не показывается: это не `latest.json`.

Сайт принимает ссылку на APK, только если это абсолютный HTTPS URL с тем же origin, что и `window.LUNEX_PUBLIC_BASE`, и путь строго внутри его директории, оканчивается `.apk`, без credentials, query, hash или path traversal. Подпись RSA браузер не проверяет: **проверять происхождение APK и соответствие SHA-256 пользователь должен самостоятельно; клиент проверяет RSA при обновлении внутри игры**. Не трактовать просто доступный JSON как доказательство подлинности. При недоступном JSON или непрошедшем проверку URL кнопка ведёт на `window.LUNEX_FALLBACK_RELEASE` (`https://github.com/maillunex-lang/LunexEconom/releases/latest`) и не отключается; наличие там релиза сайт не гарантирует. При наличии корректной ссылки кнопка остаётся активной и называется «Скачать для Android». Сообщение об ошибке не содержит выдуманной версии.

**Атомарное обновление выпуска владельцем в части C, после офлайн-подписи:** заранее приготовить APK и вычислить SHA-256, сверить его с `update.json`, подписать точные канонические байты JSON приватным офлайн-ключом, проверить `.sig` публичным ключом и не передавать приватную часть на VPS. Загружать на сервер сначала APK в временное имя и атомарно переименовать после полной передачи, затем подготовить временные `update.json.new` и `update.json.sig.new`. До публикации убедиться, что оба подготовленных файла образуют корректную пару, и затем атомарно переименовать подпись и **последним** манифест (в установленной последовательности «сначала файл, затем подпись» имеется краткое окно несогласованности; безопаснее два временных файла и публикация манифеста последним). Настроить `Cache-Control: no-store` для манифеста и подписи, HTTPS и права доступа, не трогая другие пути домена. Вариант надёжнее для отсутствия окна: переключение целого каталога двух файлов и APK через атомарный симлинк, если будущая схема nginx это поддерживает. Не начинать публикацию до согласования процедуры владельцем.

## Дорожная карта

Данные приходят только из `./roadmap.json`. Все поля читаются как текст через `textContent`, не через `innerHTML`. При отсутствии сети отображается сообщение о недоступности данных, без ложного утверждения актуального процента. Без JavaScript существует статичная копия в HTML, соответствующая `roadmap.json` на 2026-11-15. Её нужно синхронизировать при изменении директором JSON; только директор меняет реальные статусы и проценты. При доступном JS карта отрисовывает 5 вех, карточки фаз и их пункты, управляемые нативным `details`/`summary` с клавиатуры, и легенду.

**Формула готовности:** для N фаз с `progress` от 0 до 100: `P = round((progress₁ + ... + progressₙ) / N)`, веса равные, округление до ближайшего целого (для неотрицательных чисел `Math.round`). На дату исходного файла: `(100 + 100 + 15 + 0 + 0 + 5 + 2 + 0) / 8 = 27,75`, показано **28%**. Вехи в расчёт не входят. Дату обновления берём из `updated`, а не из часов устройства.

В `web/roadmap.json` статус каждой вехи, фазы и пункта ровно `done`, `wip` или `planned`. Прогресс фазы целый 0–100, заголовки непустые, ссылка фазы на milestone действительна. Инфографика CSS: горизонтальная шкала вех, круги на `conic-gradient`, подписи статусов словами. В 360 px шкала прокручивается по горизонтали **внутри собственного блока**, не растягивая страницу. `prefers-reduced-motion` отключает анимации. Тема следует системной и переключается локально, без cookies/localStorage.

**Обновление roadmap:** директор утверждает изменения, корректирует только `web/roadmap.json`, проверяет `python3 tools/check_website.py`, при необходимости обновляет встроенную HTML-копию данных для пользователей без JS, фиксирует commit и запускает `website-check`. Только после этого владелец вручную публикует новую версию файлов отдельной командой. `roadmap.json` следует помещать под временным именем и атомарно переименовывать, не допуская частично записанного JSON.

## Проверки

```sh
python3 tools/check_website.py
python3 -m unittest tools.tests.test_website -v
node --check web/site.js
node --check web/tests/smoke.cjs
```

CI `website-check.yml` ставит Playwright Chromium и снимает страницу при 360×800 и 1440×900 в светлой и тёмной темах для трёх состояний: есть годный `latest.json`, нет `latest.json` но есть `update.json`, нет обоих. Дополнительно проверяются канал `test`, негодный `latest.json` с откатом на манифест, чужой URL APK, отсутствие ошибок консоли и горизонтального переполнения. Также открывает страницу с выключенным JavaScript: виден текст и ссылка на релизы. Артефакт `website-screenshots` хранит PNG. Ручной `website-bundle.yml` проверяет данные, формирует `lunexeconom-website.tar.gz` с `web/` и `SHA256SUMS.txt`, загружает оба как Actions artifact. **Workflow не публикует файлы на VPS и не содержит SSH.** В архив попадает и `web/tests/`; на боевой сайт его класть не нужно, публикация части C копирует только именной список файлов страницы.

## Предложения директору (без изменения формата roadmap.json)

1. Рассмотреть поле `summary` для краткого описания фазы и поле `target_version` для привязки к релизу; пока карта использует существующие `title/status/progress/items`.
2. Рассмотреть генерацию статической HTML-копии из JSON как отдельный CI-артефакт или серверный build step (без клиентской зависимости JS), чтобы no-JS версия не старела.
3. Если потребуется полноценный журнал, утвердить расширение подписанного `update.json` с необязательным `releases` (максимум 5), обновить серверный/клиентский валидатор отдельно, а сайт уже умеет показывать список.
