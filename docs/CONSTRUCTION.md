# EX-04: проекты строительства, материалы, подрядчики, тендеры и ввод жилья

Дата: 15.11.2026. Новая серверная подсистема в ветке `ChatGPT12`, без внедрения на рабочий VPS.

## Флаги и совместимость

- `CONSTRUCTION_PROJECTS_ENABLED=0` (по умолчанию): прежний `POST /build` и существующая трёхзначная `construction_stages.py` работают как до изменений. Без флага нет новых месячных списаний, активаций предприятий, износа и ввода жилья.
- `CONSTRUCTION_PROJECTS_ENABLED=1` **вместе с** `LAND_ENABLED=1`: активен `POST /projects`. Новую систему нельзя использовать без включённой проверки владения землёй.
- Не переопределяет существующий `POST /build`; для старой постройки действует старый момент строительства и старые визуальные стадии. Новые `construction_projects` не регистрируются в старом таймере `construction_stages` и получают свои четыре стадии.
- Два отдельных PostgreSQL/SQLite тестовых окружения. Все схемы добавляются через `ensure`, не уничтожают старые таблицы.
- **Месяц** берётся строго из `clock.state`, без независимых таймеров. При выключенных двух флагах старый симулятор отдаёт тот же `digest`.

## Создание и четыре стадии

Игрок выбирает `object_id` из `GET /catalog/city` либо тип производства (рецепты `goods_catalog`; поддерживаются также старые `warehouse`/`shop`). Каталог определяет сетку, строительство в месяцах, износ и материалы. Цена `city_catalog.cost_in(object_id, city_id)` привязана к городу и `regional_prices`. Для производств применяется базовая цена рецепта × индекс города; схема стройматериалов для производств отдельна от рецепта текущего выпуска (сырьё для фабрики не тождественно материалам её здания).

Город вычисляется сервером из координат; подмена `city_id` отвергается. Требуется участок игрока либо действующая аренда, разрешённая зона, свободные клетки и уже существующий дорожный доступ. Автоматическая выдача бесплатных дорог не допускается. Добывающие предприятия проходят `deposits.gate`. Социальные, образовательные, медицинские и муниципальные объекты заказывает `city`, а не обычный игрок.

При заказе весь расчётный бюджет проекта **резервируется** единой парной проводкой `player:owner → system:project:<id>`. Габариты сразу помечаются в `buildings` и `cells`, чтобы никто не строил поверх. В `building_ops` **нет** строки проекта до ввода, значит фабрика не производит товары во время стройки.

| Этап | `project_stage` | Доля сроков и сметы | Условия |
|---|---|---|---|
| Фундамент | `foundation` | 20% | Материалы по этапу, расход по проводкам |
| Каркас | `frame` | 35% | Проверка остатков и доступности на рынке |
| Отделка | `finishing` | 30% | Поставка материалов и расчёт |
| Ввод | `commissioning` → `complete` | 15% | Регистрация производства / событие ввода жилья |

Доли берутся из `city_catalog.STAGES`, итог 100%. Минимальные сроки проектов берутся из `city_catalog.build_months`, состояние обновляется в ежемесячном `production.step_month` через отдельный модуль. При дефиците поставок проект в статусе `delayed`, с `delay_reason`; без поставок стадия не оплачивается дважды. `project_materials.required` и `used` хранят реальные целые количества.

## Строительные материалы и рынок

Каталог товаров `goods_catalog` является источником ID и референсных товаров: `timber`, `stone`, `cement`, `steel`, `brick` и др.

- Режим `inventory`: строитель расходует только существующие `inventory` владельца. Недостаток останавливает этап.
- `market`: закупки только по опубликованной `market_prices` и имеющемуся предложению; нет бесконечных бесплатных NPC-товаров.
- `mixed` (по умолчанию): сначала склад компании, затем рыночная закупка недостающего.
- `construction_market_purchases(month_index,product,qty)` не даёт нескольким стройкам израсходовать больше рыночного объёма в одном месяце.
- Денежные закупки идут из резервного бюджета в `system:market`, оставшиеся по этапу средства уходят подрядчику или `system:construction`. Все переводы идут через `economy.post`; округление только целочисленное.
- Если бюджет на товары исчерпан, статус `delayed` с `construction_budget_exhausted`; владелец может пополнить его через `POST /projects/fund` либо отменить проект. Прогресс не перескакивает через неоплаченный этап.

**Важно для баланса:** расчётная `cost_in` содержит общий бюджет, из которого оплачиваются и рыночные материалы, и подряд; нет второго списания этой же суммы. Фактическая прибыль подрядчика это оплаченные ему этапы за вычетом собственных издержек, а не весь резерв.

## Подрядчики

`contractors.ensure` создаёт три NPC-компании: «Башстрой», «РегионСтрой», «Малый подряд». Игрок может зарегистрировать строительную компанию, задав имя и мощность 1…20 одновременных заказов. `contractor_orders` хранит согласованную цену, месяц сдачи, штраф, фактически оплаченную сумму и статус. Проверка мощности выполняется при назначении; после ввода мощность освобождается.

Оплата при переходе стадий через `contractors.pay_milestone`. Просрочка создаёт штраф по умолчанию 1% за игровой месяц от договора с ограничением по существующим средствам подрядчика. Возвраты отменённого проекта возвращают неистраченный резерв владельцу за вычетом 5% комиссии с **остатка**; потраченные материалы и выполненные работы повторно не возмещаются. При недостатке материалов, задержке и ремонте отрицательных кошельков не образуется.

NPC-подрядчики и игроки проходят те же проверки свободной мощности при выборе тендера и получают платежи в том же журнале.

## Муниципальные тендеры

Мэр создаёт заявку из `city_catalog` для школы, больницы, парка, остановки и остальных общественных объектов. Каталог задаёт бюджет для данного города; при вводе объект принадлежит `economy.CITY`, платит именно городской кошелёк.

- Мелкий заказ с бюджетом менее **200 000 игровых ₽** направляется напрямую первому доступному NPC-подрядчику после объявления, с немедленным бронированием средств и земельного участка.
- Крупный заказ публикуется на 1…12 игровых месяцев. NPC автоматически подают детерминированные предложения, игроки-подрядчики могут конкурировать по цене и сроку. Ставка выше бюджета отклоняется; улучшение своей ставки возможно только с более низкой ценой.
- Победитель выбирается по **наименьшей цене**, затем сроку и ID при равенстве. В момент выбора ещё раз проверяется мощность и условия строительства. Мэр не может заявить свой подряд в собственный тендер.
- Если город не располагает бюджетом, заявка остаётся `pending_funding` и проверяется при следующем месяце; **деньги не берутся в долг без согласованного правила**. Если к моменту присуждения участок занят либо отсутствует дорожный доступ, состояние `placement_failed`, деньги не списаны; если нет предложений, `no_bids`.
- События и обновление статуса `awarded → complete` фиксируются через месячную обработку.

**Границы текущей реализации:** автоматическое составление самим городом плана строек исходя из дефицита школ/больниц относится к муниципальному директору (EX-07). Сейчас инициатором тендера выступает мэр; автоматизированы выбор малого заказа, NPC-заявки и присуждение. Каталог `city_catalog` пока не содержит полноценного объекта `road`; **дорожные тендеры** и создание сети `roads` по заказу города потребуют согласования с владельцем `server/roads.py` и не реализованы, чтобы не нарушить существующую связность карты. Отсутствие этого блока нельзя считать завершённой интеграцией всех видов муниципального строительства.

## Недвижимость и интерфейс с Grok

При вводе жилого проекта появляется **только одна** запись `construction_housing_supply(project_id,owner,city_id,capacity,commissioned_month,integrated)` и событие `housing_commissioned` в общем журнале `events`, плюс событие обновления стадии. Это точка передачи блоку EX-05 (домохозяйства, `housing_supply` в реализации Grok).

**Контракт интеграции:** Grok или общий интеграционный адаптер должен атомарно взять строки `construction_housing_supply WHERE integrated=0`, создать/обновить `housing_supply` с уникальным `project_id`, сохранить доступную вместимость `capacity`, город `city_id` и собственника; после подтверждения пометить `integrated=1`. Повтор обработки события должен быть идемпотентным. До подключения EX-05 квартиры не выставляются автоматически в каталог продажи/аренды и не генерируют фиктивные платежи. **API управления продажей и арендой квартир здесь ещё нет**, его согласуют по этому контракту с Grok.

В существующем Godot-клиенте поддерживаются визуальные `construction_stage=foundation|frame|complete`; сервер сохраняет полные четыре фазы в `project_stage`, чтобы новый клиент EX-11 мог отрисовать свои модели отделки/ввода. Файлы GLB и клиентские сцены не изменялись.

## Износ, ремонт и сроки

`wear_permille_per_month` берётся из каталога, уменьшает `condition_permille` только **после** ввода, не ниже 0. `/projects/repair` восстанавливает состояние до 1000‰ за плату с проводкой, историю хранит `construction_repairs`. Ремонт не изменяет сведения о проживании, пока EX-05 не подключён.

Время в игре согласно `clock.py`: один реальный день = игровой месяц (настраивается `LUNEX_MONTH_SECONDS`). Смена длительности месяца не меняет индекс месяца и размер оплаты.

## API

Все команды Bearer-авторизованы. При выключенном `CONSTRUCTION_PROJECTS_ENABLED` новые POST-команды недоступны (404 `feature_disabled`), старый `POST /build` не меняется. Общая граница транзакции и `request_id` обязательны для POST-команд.

| Метод | Маршрут | Поля / ответ |
|---|---|---|
| POST | `/projects` | `object_id` (или `kind`), `x`, `y`, `material_mode` (опция), `contractor_id` (опция), `request_id` → `project_id`, `cost`, `stage`, `months`, `materials` |
| GET | `/projects` | До 100 проектов пользователя, статус, стадия, отслеживание нужных материалов |
| POST | `/projects/cancel` | `project_id`, `request_id` → `refund`, `cancellation_fee` |
| POST | `/projects/fund` | `project_id`, `amount`, `request_id` → пополнение резерва |
| POST | `/projects/repair` | `project_id`, `request_id` → `cost`, `condition_permille` |
| GET | `/contractors` | NPC и игроки, мощность, текущая загрузка |
| POST | `/contractors/register` | `name`, `capacity`, `request_id` |
| GET | `/tenders` | Список объявленных и завершённых тендеров |
| POST | `/tenders/create` | `object_id`, `x`, `y`, `months`, `request_id` (только мэр) |
| POST | `/tenders/bid` | `tender_id`, `contractor_id`, `price`, `months`, `request_id` |

Пример `POST /projects`:
```json
{"object_id":"house_wood","x":1,"y":1,"material_mode":"mixed","request_id":"56db0f00-9800-4f00-8000-000000000003"}
```

## Таблицы и события

`construction_projects`, `project_materials`, `construction_market_purchases`, `construction_housing_supply`, `construction_repairs`, `contractors`, `contractor_orders`, `tenders`, `tender_bids`. Из старых таблиц используются без потери строк: `buildings`, `cells`, `chunks`, `events`, `inventory`, `wallets`, `ledger_tx`, `ledger_entries`, `building_ops`, `market_prices`.

Новые события создаются через `chunks.version`, `events.seq` для инкрементального обновления клиента. Защита от повторов/гонок через общий lock игровой транзакции, тот же что у старого `/build`; свои SQL-блокировки не работают отдельно от главной базы.

Текущая ветка сама флаги не включает.
