# ADR-001. Игровое время (утверждено владельцем, 15.11.2026)

## Решение
1. **1 игровой месяц = 24 реальных часа.** В месяце 30 игровых дней: **1 игровой день = 48 реальных минут**, 1 игровой час = 2 реальные минуты.
2. **Границы месяцев в 09:00 по Уфе** (Asia/Yekaterinburg, UTC+5, без перехода на летнее время, то есть 04:00 UTC). Первый игровой месяц нового мира начинается в ближайшие 09:00 по Уфе; месяц N заканчивается в 09:00 следующих суток.
3. Игровой год = 12 месяцев = 12 реальных суток. Отсчёт календаря: январь 2027 (`clock.START_YEAR`), месяц 0.
4. Время одно для всех игроков, управляется сервером (авторитетно); клиент показывает дату и «до нового месяца».

## Следствия для расчёта
- **Месячный шаг** (зарплаты, налоги, проценты, аренда, отчёты, дивиденды) выполняется ровно на границе в 09:00 (лениво при первом запросе после границы, как сейчас, с догоном пропущенных месяцев). Идемпотентен по `month_index`.
- **Суточный тик** (кандидат для ядра 2, см. ECONOMY_CORE_2.md): производство, склады, поставки и розничные продажи считаются по игровым дням (каждые 48 реальных минут). Решение ждёт утверждения.
- **Длительности объектов в игровом времени:** стадия строительства = 1/6 игрового месяца (4 реальных часа, как сейчас), поставка между городами считается в игровых часах (6 часов пути = 12 реальных минут); исследования, обучение, срок аренды и кредита в игровых днях и месяцах.
- **Масштаб «неделя = игровой год»** ChatGPT8 использовал по недоразумению: он **неверен**, правильное соотношение выше.

## Реализация (задание исполнителю, фаза «Часы»)
1. `server/clock.py`: константы `MONTH_SECONDS = 86400`, `ANCHOR_HOUR_LOCAL = 9`, часовой пояс `UTC+5`; `align_epoch(now)` возвращает ближайшее 09:00 по Уфе не позже `now` (или следующее для нового мира); `LUNEX_MONTH_SECONDS` остаётся для тестовых серверов.
2. **Миграция боевого мира без скачка номера месяца:** сейчас `world_clock.epoch` равен моменту первого запроса. Нужна команда оператора `clock_align` (по умолчанию «сухой» режим, показывает, что изменится): перебазировать часы так, чтобы текущий месяц закончился в ближайшие 09:00 по Уфе, `base_index` сохраняется (по образцу существующей перебазировки при смене длины месяца), эффект: один раз месяц будет короче или длиннее 24 часов, это записывается в журнал.
3. Клиент показывает дату и остаток до 09:00 по Уфе, а в подсказках «до нового месяца в 09:00 (Уфа)».
4. Тесты: границы месяцев в 09:00 UTC+5, сдвиг через границу суток и года, перебазировка без потери месяца, поведение при `LUNEX_MONTH_SECONDS` тестового режима.
