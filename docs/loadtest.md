# V2-SEC1. Нагрузочное тестирование API

Инструмент: `tools/loadtest/loadtest.py`, только стандартная библиотека Python. Сценарий каждого виртуального игрока: регистрация → вход → GET чанка карты → попытка покупки участка → попытка постройки при успешной покупке → GET списка своих предприятий. Статус `409` у строительства является игровой валидацией, а не сетевым сбоем; инструмент фиксирует его, не скрывает.

## Изоляция

Работать только с **локальным** HTTP-сервером, поднятым на **отдельной чистой PostgreSQL 16** с `LUNEX_TEST_DATABASE_URL` и `LUNEX_DATABASE_URL`, указывающими на тестовую БД. Не использовать действующую БД и рабочие V1/V2 API. Запуск на `rikagro.ru` и поддоменах заблокирован даже с разрешающим флагом. Для произвольного удалённого URL требуется явный `--i-know-this-is-not-production`, при этом проверять отсутствие производственных данных обязан оператор.

Пример с локальным сервером, не меняя ops/systemd/nginx: в одном терминале `LUNEX_DATABASE_URL=postgresql://USER:PASSWORD@127.0.0.1:5544/lunex_ci LUNEX_TICK_INTERVAL=600 LUNEX_PORT=18777 python -m server.game_server`; в другом `python tools/loadtest/loadtest.py --dry-url http://127.0.0.1:18777 --players 100 --concurrency 10 --report loadtest.json`. Указать настоящие тестовые учетные данные через переменные окружения или защищённый файл, **не коммитить пароль**.

С одного loopback IP штатный лимит регистрации выдаёт `429` после 10 попыток за 15 минут. Для измерения полных потоков можно поднять **только изолированный локальный сервер** с `LUNEX_TRUST_PROXY_REAL_IP=1` и использовать `--simulate-ips`: `python tools/loadtest/loadtest.py --dry-url http://127.0.0.1:18777 --players 100 --concurrency 10 --simulate-ips --report loadtest.json`. Этот режим добавляет детерминированный тестовый `X-Real-IP`; на удалённом URL он запрещён. **Не включать доверие к произвольному X-Real-IP в production.** Реальный nginx обязан сам перезаписывать адрес доверенного клиента.

Скрипт печатает JSON и сохраняет отчёт по `--report`: `players`, `total_requests`, `elapsed_seconds`, `requests_per_second`, `latency_ms.p50/p95/p99`, количество ответов по кодам, разбивку по стадиям и `network_errors`. При `--concurrency 10` ожидаются задержки порядка десятков миллисекунд для простых запросов, но под нагрузкой возможны пики секундной величины. Прогон не заменяет стресс-тесты с профилированием БД, полноценные проверки тиков и многосуточную работу.

## Результаты SEC1, 2026-11-16 (локально, не production)

На отдельном PostgreSQL 16 и локальном Waitress (16 потоков, пул до 15):

| Сценарий | Игроков | Запросов | p50 | p95 | p99 | Коды | Сетевые ошибки |
| --- | ---: | ---: | ---: | ---: | ---: | --- | ---: |
| Обычный loopback | 100 | 139 | 21,82 мс | 803,25 мс | 1920,63 мс | 200×24, 201×15, 409×8, 429×92 | 0 |
| Изолированный local proxy test, `--simulate-ips` | 100 | 592 | 90,09 мс | 3213,68 мс | 3379,47 мс | 200×300, 201×192, 409×100 | 0 |

Второй прогон: 100 успешных регистраций и входов, 100 чтений карты, 92 покупки участков, 100 чтений предприятий, 92 попытки постройки получили `409` (не было допустимого размещения по выбранным координатам), время 32,51 с, 18,21 запроса/с. **Успешная массовая стройка этим сценарием не подтверждена.** Показатели зависят от машины и состояния тестовой базы, являются измерением одного локального прогона, не гарантией SLA.
