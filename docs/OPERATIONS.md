# Operations V2: переход с V1 на V2 (часть C выполнена частично)

> **Состояние на 2026-11-15.** Часть C выполнена по командам владельца: база `lunex_v2` и сервис `lunexeconom-v2` (порт 18777), временный маршрут nginx `/lunexeconom/v2/api/` и статика `/lunexeconom/v2/`, автообновитель V2 (таймер раз в 2 часа, с проверкой CI и откатом), синхронизация подписанных релизов раз в 30 минут (`ops/partc/09_publish_release.sh`, `10_release_sync.sh`, `release_common.py`; приватных ключей на сервере нет). Старая игра V1 остановлена, три её таймера отключены. **Ещё не сделано и только по прямой команде владельца:** отключение автозапуска сервиса V1, обновление образа PostgreSQL V2, перенос основного маршрута `/lunexeconom/api/` на V2 и отключение V1. Текст ниже описывает исходный план и порядок, его запреты остаются в силе.

**Запрет:** до отдельного сообщения владельца «выполняй часть C» не запускать развёртывание, не создавать БД/пользователя, не менять systemd, nginx, автообновление и данные старого мира. Выполнение V2-00 на GitHub само по себе не разрешает менять VPS. Для локальной разработки использовать отдельную непроизводственную среду.

## Порядок будущей части C (только план)

1. Проверить процессы, `systemctl` и конфигурацию nginx без вывода секретов; установить точные пути V1, существующий port, updater и источники резервных копий. До изменения сделать подтверждённую резервную копию старой PostgreSQL средствами `pg_dump -Fc` с проверкой `pg_restore -l`, отдельно архив server/ и nginx-конфигурации; хранить вне изменяемого каталога.
2. Создать в PostgreSQL 16 отдельные **`lunex_v2`** и `lunex_v2_app` с новыми правами исключительно на V2, без доступа к базе V1. DSN хранить вне Git, например в `EnvironmentFile` с правами 0600. Старые аккаунты и мир не копировать.
3. Создать отдельный каталог приложения `/opt/lunexeconom-v2` и state `/var/lib/lunexeconom-v2-update`, пользователь `gamedev` без расширения прав, systemd `lunexeconom-v2.service` с отдельным loopback-портом `18777` (предварительно убедиться, что он свободен). Приложение проверить с `curl -fsS http://127.0.0.1:18777/health`; сервис V1 не трогать.
4. Перед переключением nginx назначить отдельный **временный** маршрут V2 `/lunexeconom/v2/api/` → `127.0.0.1:18777`, старый `/lunexeconom/api/` оставить на V1. Проверить каждый URL, регистрация/вход только в V2, затем в согласованное окно перевести `/lunexeconom/api/` на V2. При этом сохранить старый маршрут `/lunexeconom/v1/api/` → V1 до отдельного решения об отключении. Контролировать обработку префиксов и CORS. Сначала `nginx -t`, затем разрешённый reload.
5. Создать **отдельный** экземпляр updater с `LUNEX_SERVER_DIR=/opt/lunexeconom-v2/server`, `LUNEX_UPDATE_STATE=/var/lib/lunexeconom-v2-update`, `LUNEX_SERVICES=lunexeconom-v2.service`, `LUNEX_HEALTH_URL=http://127.0.0.1:18777/health`. Автообновление V1 остановить/зафиксировать по отдельному решению владельца, исключить возможность получения orphan `main` старым updater. Никогда не указывать каталог/сервис V1 как цель нового updater.
6. Проверить HTTP, журналы, доступ V1 и V2 по отдельным путям. Обновить настройки клиента только после публикации корректного APK. В случае неуспеха восстановить предыдущий nginx upstream и состояние V2 из собственной резервной копии; V1 и её БД оставить нетронутыми.
7. Отключение старого сервиса и старой базы только после пользовательской приёмки новой версии и отдельного разрешения. Архивный Git branch/tag никогда не удалять.

## План отката

Сохранить последнее работающее состояние nginx, systemd и SQL-дамп V1; V2 updater хранит versioned backup под `/var/lib/lunexeconom-v2-update/backups`. При провале health updater автоматически восстанавливает файлы V2 и перезапускает V2. При проблеме с nginx вернуть старую конфигурацию и `nginx -t`, затем reload; V1 живёт независимо. Дамп V1 нужен как аварийная страховка, не как источник миграции аккаунтов.

## CI gate

На каждую новую серверную версию требуется успешный workflow `server-check.yml` точно на целевом SHA. Updater не разворачивает непроверенный SHA и сохраняет состояние для отката. Нельзя использовать «нет workflow → всё в порядке».

## Автообновитель V2: установка и восстановление

**Важная проверка перед ручной заменой:** существующий unit `lunexeconom-v2-update.service` может содержать `ProtectSystem=strict` и `ReadWritePaths`, разрешающий запись только в `/opt/lunexeconom-v2`, state и `/run/lock`. В таком случае атомарная запись в `/etc/lunexeconom-v2/v2.env` будет запрещена systemd, даже при `User=root`. Перед разрешённым развёртыванием администратор должен отдельно проверить `systemctl cat lunexeconom-v2-update.service` и согласовать точечное разрешение записи в каталог env-файла, сохранив остальные ограничения. Этот GitHub-коммит **не изменяет unit и VPS**. До устранения несовместимости не запускать обновитель в боевом режиме.

Обновитель использует только отдельные пути V2. Перед ручной заменой `ops/update_server.py` убедиться, что V1 updater отключён. **Не копировать файл из рабочей ветки на боевой VPS до отдельного разрешения владельца и успешного CI.**

Параметры: `LUNEX_ENV_FILE` (по умолчанию `/etc/lunexeconom-v2/v2.env`), `LUNEX_VENV` (по умолчанию `/opt/lunexeconom-v2/venv`), `LUNEX_SERVER_USER` (по умолчанию `gamedev`). Env-файл должен содержать ровно одну строку `LUNEX_SHA=<40-значный SHA>`. Запись атомарна с сохранением владельца, прав, комментариев и остальных значений. Не показывать содержимое env-файла в отчётах.

После отдельного разрешения владельца: остановить только `lunexeconom-v2-update.timer`, сделать `cp -a /opt/lunexeconom-v2/ops/update_server.py /opt/lunexeconom-v2/ops/update_server.py.backup`, скопировать проверенный файл из принятого коммита в `/opt/lunexeconom-v2/ops/update_server.py`, сохранить исходные права, выполнить `python3 -m py_compile /opt/lunexeconom-v2/ops/update_server.py`, затем `systemctl start lunexeconom-v2-update.service` и проверить `systemctl show lunexeconom-v2-update.service -p Result -p ExecMainStatus`, `journalctl -u lunexeconom-v2-update.service -n 30 --no-pager` и `/health`. После успешной проверки включить таймер.

Откат обновителя: остановить только V2-таймер, восстановить `update_server.py.backup` через `cp -a`, проверить синтаксис, запустить разовую проверку и затем таймер. При несовпадении `deployed-sha` и SHA живого сервера автообновитель **не выполняет развёртывание**: выяснить причину расхождения и согласовать восстановление состояния вручную. Не менять `deployed-sha` вслепую.

При смене `server/requirements.txt` зависимости устанавливаются из проверенного коммита через Python/pip V2 от имени `gamedev` перед перезапуском. При ошибке установки файлы откатываются без перезапуска; изменения уже установленных пакетов pip не откатываются автоматически, поэтому совместимость зависимостей следует проверять отдельно.
